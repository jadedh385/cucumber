# U0.8 · ID sequence service — Design note (G1)

**Spec:** [u0.8-spec.md](u0.8-spec.md) (AC1–AC15, AC4a) · **Status:** G1 passed · 2026-10-23 · signed off by Jade (Owner) after architect review: pass with fixes, all applied ([§13](#13-architect-review-2026-10-23)); [Q1](#9-owner-questions) answered a), Q2 answered b); the [spec wording changes](#10-spec-wording-to-change-at-sign-off) accepted and made in the spec. G2 passed 2026-10-24, signed off by Jade (Owner), contracts accepted ([§14](#14-contracts-fixed-by-the-g2-tests-2026-10-24))
**Stack:** Django 5.2 LTS + PostgreSQL 17 ([ADR-0001](../adr/0001-stack-selection.md)).

The numbers already exist. Plants, batches and events take theirs from the
database (`id`). SKUs and batch numbers come from `issue_next_sku` and
`lock_plants`, each with a row lock (U0.2 design §2.3). U0.8 adds four things:

1. **One package, `cucumber/ids/`**, that turns numbers into IDs and typed text
   back into records. `issue_next_sku` and `lock_plants` move into it.
2. **The database hands out every plant, batch and event number itself.** A
   caller that supplies its own `id` is refused, except the owner (the V.2
   import), and the generator moves past an owner's number by itself (AC13).
3. **SKUs can grow to 4 digits** (Q2): a wider format check and number-aware
   sorting.
4. **`cucumber_check_guards` reports a number generator that is behind** its
   table (AC14), and the concurrency tests prove AC9–AC11.

No screens, no new tables, no new permissions.

`find_by_sku` moves from `plants/services.py` into `ids/lookup.py`.
`former_skus` stays where it is: it lists SKUs and doesn't build them.

**Why a package and not one file (spec AC15 says "one module").** `plants/models.py`
needs the SKU pattern, and the look-up needs the `Plant`, `Batch` and `Event`
models. In one file, that is an import loop. With `formats.py` and
`reading.py` free of models, the models import the pattern and the rest
imports the models. The spec's intent stays the same: one place, and a test
that fails if any other code builds an ID ([§10](#10-spec-wording-to-change-at-sign-off)).

## 2. Formats (`ids/formats.py`, AC1–AC4a)

| Function | Gives | Rule |
|---|---|---|
| `plant_id(42)` | `PLT-0042` | `PLT-` and the number padded to 4 digits |
| `batch_id(117)` | `BAT-00117` | `BAT-`, 5 digits |
| `event_id(1502)` | `EVT-01502` | `EVT-`, 5 digits |
| `sku("PHL", 5)` | `PHL005` | genus code and the number padded to 3 digits |
| `plant_label(sku, plant_number)` | `PHL001`, or `PLT-0042` with no SKU | the base of a batch short name |
| `batch_short_name(sku, plant_number, plant_seq)` | `PHL001 · B003` | `plant_label`, `" · B"`, `plant_seq` padded to 3 digits |
| `sku_number("PHL1000")` | `1000` | the digits after the genus code |

- Padding is a minimum, never a cut (AC2): `plant_id(10000)` is `PLT-10000`,
  `sku("PHL", 1000)` is `PHL1000`, `batch_short_name(…, 1000)` ends `B1000`.
  Python's `f"{n:04d}"` already behaves like this. The tests pin it.
- A number below 1 is a `ValueError`. The database never issues 0, so this
  is a programming error, not something staff can cause.
- These functions take plain values, not model objects, so they never run a
  query. A screen that lists batches passes `plant.sku_id`, `plant.pk` and
  `batch.plant_seq` from one `select_related` query.

**SKU pattern (Q2).** `SKU_PATTERN = r"^[A-Z]{3}(?!000)(?:[0-9]{3}|[1-9][0-9]{3,})$"`.
In words: three capital letters, then either exactly three digits (`001`–`999`)
or four or more digits with no leading zero (`1000` and up). `PHL0005` and
`PHL000` are refused, so every number has one spelling. PostgreSQL and
Python both accept this pattern (the `(?!000)` look-ahead is valid in both).

**SKU order (AC4a).** Within a genus, a longer SKU is a bigger number, and
SKUs of the same length sort the same as text, because there are no needless
zeros. So `SKU_ORDER = ("genus_id", Length("sku"), "sku")` sorts by number
with plain columns, and works on both `Sku` and `Plant` querysets (as
`order_by(*SKU_ORDER)`). `sku_number` is the same order for Python lists.

## 3. Reading an ID back (AC5–AC8)

### 3.1 `read(text) -> Typed | None` (`ids/reading.py`, no database)

First the text is tidied (review L1):

1. Text longer than 64 characters is `None` at once.
2. Unicode NFKC (full-width `ＰＬＴ４２` becomes `PLT42`).
3. Dashes NFKC leaves alone (`‐ ‑ – — −`, U+2010–2014 and U+2212) become `-`.
   Dots used as separators (`· • ∙ ⋅ ・`) become `·`.
4. Spaces trimmed.
5. Upper case **for ASCII letters only**. Python's `upper()` would turn `ı`
   into `I` and `ſ` into `S`, so `pſt-42` could become a plant. Any
   non-ASCII letter left after this step means `None`.

Then it is matched, in this order:

| Kind | Accepted (examples) | Pattern after tidying |
|---|---|---|
| Plant, batch, event | `PLT-0042`, `plt-42`, `PLT0042`, `PLT 42` | `^(PLT\|BAT\|EVT)[\s-]*([0-9]+)$` |
| Batch short name | `PHL001 · B003`, `PHL001 B3`, `PHL001-B003`, `PHL001B3`, `PLT-0042 · B3` | a plant label, then `[\s·-]*B`, then digits |
| SKU | `PHL005`, `phl005`, `PHL5` | `^([A-Z]{3})([0-9]+)$` |

`Typed` is a frozen dataclass: `kind` (`plant`, `batch`, `event`, `sku`,
`batch_name`), and the parts (`number`, `genus_code`, `sku_number`,
`plant_seq`). The SKU in a typed SKU or short name is rebuilt with
`formats.sku()`, so `PHL5` and `PHL05` both mean `PHL005`. That is not a
guess: each number has one spelling (§2).

`read` returns `None` (AC8) for:

- empty or blank text, or anything that matches no row of the table;
- a number of 0, or one too big for its column (more than
  9 223 372 036 854 775 807 for an `id`, more than 2 147 483 647 for a
  `plant_seq`), so the database is never asked something it would refuse with
  an error;
- digits other than `0`–`9`. Patterns use `re.ASCII`, so Thai digits (`๔๒`)
  don't count as digits, even though Python's `int()` would accept them.

`read` never raises.

### 3.2 No genus code may look like an ID prefix (new, AC5a)

If a genus were ever given the code `PLT`, `PLT0042` could mean plant 42 or
SKU `PLT042`. A check on `genera` refuses the codes `PLT`, `BAT` and `EVT`
(`genera_code_not_id_prefix`, §5.4). No genus uses them today (`HYA`, `PHL`,
`ALC`). Genera become editable in U0.9, so the rule has to exist before then.

### 3.3 `look_up(text) -> Found | None` (`ids/lookup.py`)

| Typed | Finds |
|---|---|
| `PLT-…` | the plant with that `id` |
| `BAT-…` | the batch with that `id` |
| `EVT-…` | the event with that `id` |
| SKU | the plant it was issued to, through `skus` (current or former, AC6) |
| Batch short name | the plant (by SKU through `skus`, or by `PLT-` id), then its batch with that `plant_seq` (AC7) |

`Found` is a frozen dataclass: `kind` (`plant`, `batch`, `event`), `record`
(the model instance), and `former_sku` (the SKU typed, when it is no longer
the plant's current one, so a screen can say "PHL005 is now HYA004").

- Voided and retired records are found too. An ID always points at its
  record (S3), and the screen shows the status.
- Nothing found: `None`. The screen's words are `id_not_found`, "No plant,
  batch or event has that ID.", in core `MESSAGES`, with every other
  message, so the Thai translation has one place to look (AC8, review L5).
- One query for each look-up (two for a short name).
- **No permission check.** Reading needs only a signed-in account, and the
  page checks that (U0.6). Phase 1 pages decide where look-ups appear.

## 4. Issuing (`ids/issuing.py`, AC10, AC11)

The two functions move with their contracts unchanged, so callers change
only an import line.

- **`issue_next_sku(plant_id, genus_code, assigned_by) -> str`.** Still
  `require(assigned_by, PLANT_LIFECYCLE)`, and still locks the genus row
  (`FOR NO KEY UPDATE`), so two issues for the same genus take turns while
  other genera carry on (AC10). The highest SKU is now read with
  `order_by(*SKU_ORDER).last()` instead of loading every SKU of the genus,
  and the new one is built by `formats.sku()`. So `PHL999` is followed by
  `PHL1000` (Q2). No gaps: a failed save rolls back its `skus` row, and
  `skus` is append-only.
- **`lock_plants(plant_ids) -> dict[int, int]`.** Locks the plants in `id`
  order and returns each one's next `plant_seq` (highest + 1). Same lock
  order as today (design §3.4 of U0.2: plants first, then batches). No gaps,
  for the same reason as SKUs: batches are never deleted, and a failed save
  rolls back its batch.
- **`plant_seqs(next_seq, plant_ids) -> list[int]` (new, review M3).** Today
  `make_batches` counts `next_seq[plant] + earlier` itself. That counting
  moves here: given the locked `next_seq` and the new batches' plant ids in
  entry order, it gives each new batch its number. `make_batches` only
  inserts. Every batch number is then worked out in `ids/`.

All of these run inside the caller's transaction and `audited()`, as they
do today. The lock-order note at the top of `events/writing.py` (where
`lock_batches` stays) points to `ids.issuing` for the plant lock (review L5).

## 5. The database side

### 5.1 `cucumber_id_from_sequence()` (AC13)

Today `plants.id`, `batches.id` and `events.id` are `GENERATED BY DEFAULT AS
IDENTITY`. That allows any caller to write `INSERT … (id, …) VALUES (500, …)`
and take a number ahead of the generator. `GENERATED ALWAYS` doesn't close
it, because any role may add `OVERRIDING SYSTEM VALUE`. A trigger can't tell
a number the generator gave from one the caller typed, while the column has
a default.

So the column loses its default, and a `BEFORE INSERT` trigger hands out the
number itself:

```sql
-- ID_FROM_SEQUENCE_BODY; TG_ARGV[0] is the sequence, e.g. 'public.plants_id_seq'
BEGIN
  IF NEW.id IS NULL THEN
    NEW.id := nextval(TG_ARGV[0]);
  ELSIF session_user = 'cucumber_owner' THEN
    -- The V.2 import keeps PLT- numbers already in use (Q1): move the
    -- generator past them, so the next new row never collides. The lock
    -- keeps app saves (and a second import) from taking numbers between
    -- the read and the setval (review M1).
    EXECUTE format('LOCK TABLE public.%I IN SHARE ROW EXCLUSIVE MODE', TG_TABLE_NAME);
    IF NEW.id > coalesce(pg_sequence_last_value(TG_ARGV[0]::regclass), 0) THEN
      PERFORM setval(TG_ARGV[0], NEW.id);
    END IF;
  ELSE
    RAISE EXCEPTION '% ids are given by the database, not chosen', TG_TABLE_NAME
      USING ERRCODE = 'restrict_violation',
            CONSTRAINT = TG_TABLE_NAME || '_id_from_sequence';
  END IF;
  RETURN NEW;
END
```

- Like the U0.7 functions, it runs as the caller (not `SECURITY DEFINER`),
  with `search_path` fixed, and its body is pinned by its md5 in
  `expected.py`. `cucumber_app` already has `USAGE` on every sequence (core
  0003's default privileges), which `nextval` needs. It has no `UPDATE` on
  them, so it can't `setval`. A new app-role check keeps it that way (§6).
- Django leaves `id` out of the `INSERT` and reads it back with `RETURNING
  id`, so the ORM works unchanged. `bulk_create` and `DEFAULT` work too. This
  was tried on PostgreSQL 17 while writing this note: a NULL `id` is filled
  before the `NOT NULL` check, `RETURNING` gives the new number, a supplied
  `id` is refused by name, and `pg_get_serial_sequence` still finds the
  sequence (Django's sequence reset uses it).
- Django's model state is unchanged (`BigAutoField`). The migration is
  `RunSQL` only, so `makemigrations --check` stays clean. Any later
  migration that alters one of these `id` columns must keep the trigger and
  the sequence. If it doesn't, the guard check reports it (§6). The module
  docstring says so.
- **Only `cucumber_owner` is let through.** Any other session is refused,
  including the `postgres` superuser that the UAT scripts use. That is
  deliberate, and the runbook says so (review L4).
- **An owner id below the generator is allowed**, as long as no row has it
  (the primary key refuses one that does), and the generator doesn't move.
  The import doesn't need this: it runs on an empty `plants` table
  ([Q2](#9-owner-questions) b), so every kept number is above the
  generator. Refusing it would only make the trigger longer, so it stays
  allowed, for the owner only, and tested.
- Gaps are allowed (AC9). A failed insert has still used its `nextval`.
- The owner's `setval` isn't undone by a rollback (a sequence never is).
  A rolled-back import leaves a gap, never a reuse.

**An id never changes either (review H1).** `cucumber_app` may UPDATE
`plants` and `batches`, and `UPDATE plants SET id = 900 WHERE id = 7` would
succeed on a plant nothing points at yet. A second trigger,
`<table>_id_fixed` (`BEFORE UPDATE` on `plants` and `batches`, function
`cucumber_id_fixed`), refuses any change of `id`, for every role including
the owner:

```sql
-- ID_FIXED_BODY
BEGIN
  IF NEW.id IS DISTINCT FROM OLD.id THEN
    RAISE EXCEPTION '% id % can''t be changed', TG_TABLE_NAME, OLD.id
      USING ERRCODE = 'restrict_violation', CONSTRAINT = TG_TABLE_NAME || '_id_fixed';
  END IF;
  RETURN NEW;
END
```

`events` needs none: it is append-only already.
- **A void or retire never frees a number (AC12).** Nothing is deleted
  (`*_no_delete`, `*_append_only`), and the sequence only moves forward
  except by an owner's `setval`, which §6 watches.

### 5.2 `plants 0003_sku_grows` (AC4)

A Django migration, since the checks are model constraints:

- `plant_sku_format`: removed and added back with the new `SKU_PATTERN`.
- `skus_sku_format`: new, the same pattern on `skus.sku`. Today only
  `plants.sku` has a format check. A wrong SKU could be put in the register
  and only fail when a plant points at it.
- Both models read `SKU_PATTERN` from `ids/formats.py`. The migration file
  holds the pattern as written text, as Django writes it. Changing the
  constant later needs a new migration, which `makemigrations --check` in CI
  would ask for.

Every SKU issued so far should have 3 digits and pass. The old pattern
allowed `XXX000`, though. So the migration first lists any `plants` or
`skus` row that fails the new pattern, and stops with those SKUs named,
instead of failing with a bare constraint error (review L3).

### 5.3 `core 0007_id_sequences` (AC13)

One transaction. For each of `plants`, `batches`, `events`:

```sql
SET LOCAL lock_timeout = '5s';
DO $$
DECLARE at_value bigint; called boolean;
BEGIN
  SELECT last_value, is_called INTO at_value, called FROM public.plants_id_seq;
  ALTER TABLE plants ALTER COLUMN id DROP IDENTITY;      -- drops plants_id_seq
  CREATE SEQUENCE public.plants_id_seq AS bigint OWNED BY plants.id;
  PERFORM setval('public.plants_id_seq',
                 greatest(at_value, coalesce((SELECT max(id) FROM plants), 0), 1),
                 called OR EXISTS (SELECT 1 FROM plants));
END $$;
GRANT USAGE, SELECT ON SEQUENCE public.plants_id_seq TO cucumber_app;
CREATE TRIGGER plants_id_from_sequence BEFORE INSERT ON plants
  FOR EACH ROW EXECUTE FUNCTION cucumber_id_from_sequence('public.plants_id_seq');
CREATE TRIGGER plants_id_fixed BEFORE UPDATE ON plants
  FOR EACH ROW EXECUTE FUNCTION cucumber_id_fixed();
```

- The new sequence keeps the old name and carries on from the old position,
  so the next plant gets the number it would have had. `greatest(…, max(id))`
  repairs a generator that is already behind. On an empty table it starts at
  1 as before.
- `cucumber_app` gets `USAGE, SELECT` on the new sequence by an explicit
  `GRANT`, not only by default privileges, which apply only when the owner
  role itself creates it (review L2).
- Tables are done in the app's lock order, **plants → batches → events**
  (U0.2 design §3.4), so the migration and a save can't deadlock.
- `ALTER TABLE` needs a short exclusive lock on each table. While it waits
  for one, every new query on that table queues behind it, so one slow
  request could stall the pages (review M4). `lock_timeout = 5s` makes the
  migration give up cleanly instead. Nothing is changed, and the deploy can
  be run again. With that, **the app doesn't need to stop** for this
  release. The G5 run on staging confirms it, with the app running.
- Run order: `references 0005` → `plants 0003` → `core 0007` (depends on
  `events 0002`, `batches 0002`, `plants 0003`, `core 0006`).

### 5.4 `references 0005_genus_not_id_prefix` (AC5a)

`CheckConstraint(~Q(code__in=["PLT", "BAT", "EVT"]), name="genera_code_not_id_prefix")`
on `Genus`. It validates against the three seeded genera without trouble.

### 5.5 Rollback

Each migration has an undo:

- **`core 0007`:** drop the five triggers and the two functions. Then, for
  each table in reverse order: read the position and `is_called`, drop the
  sequence, `ADD GENERATED BY DEFAULT AS IDENTITY`, and `setval` the new
  identity sequence to the same position and `is_called`.
- **`plants 0003`:** put back the 3-digit `plant_sku_format` and drop
  `skus_sku_format`. This is refused if a 4-digit SKU exists, which is
  correct: the old code couldn't read it.
- **`references 0005`:** drop the check.

No undo loses data. Going back to the previous release (`2026.10.4`) still
means restoring the pre-deploy copy, as it has since U0.7: the older code
doesn't know these migrations, so the deploy refuses to go back (U0.7 G6).
The G6 rehearsal runs the undo on a scratch database.

## 6. The guard check (AC14, `core/guards.py`, `core/expected.py`)

`expected.py` gains, all made by `core 0007` (`U08 = "core.0007_id_sequences"`):

- three triggers `<table>_id_from_sequence` (`BEFORE INSERT`, argument
  `public.<table>_id_seq`) and two `<table>_id_fixed` (`BEFORE UPDATE`, on
  `plants` and `batches`), with their functions `cucumber_id_from_sequence`
  and `cucumber_id_fixed` (md5, fixed `search_path`);
- `SEQUENCES = {"plants": "public.plants_id_seq", "batches": …, "events": …}`;
- an app-role check `"sequence update"`: `cucumber_app` has `UPDATE` on any
  of those sequences, so it could move a generator (`setval`).

`guards.py` gains `Kind.SEQUENCE`, one guard for each table. For each one it
reads, in **one statement**, the table's `max(id)` (0 when empty) and the
generator's next value: `last_value` when `is_called` is false, otherwise
`last_value + 1`. One statement means a save that commits in between can't
make it look behind (review M2). `max(id)` uses the primary-key index, so
it's instant. After a test flush, the table is empty and the generator
restarted, so the check passes. It fails with one plain line:

| Found | Line |
|---|---|
| sequence missing, or not owned by `<table>.id` | `plants: its number generator public.plants_id_seq is missing` |
| next value ≤ `max(id)` | `plants: the next new one would get id 43, but id 50 is already used; see the release runbook, "Number generator behind"` |
| `id` has a default or is an identity column again (`attidentity <> ''` or `atthasdef`), e.g. after a later `AlterField` | `plants: id has a default again, so callers can choose it; see U0.8 design §5.1` |
| `cucumber_app` lacks `USAGE` on the sequence | `plants: cucumber_app can't take numbers from public.plants_id_seq, so every new plant fails` |

The deploy stops on either, at steps 3b and 5b, as for every guard (U0.7
§8.3). That is about 11 more protections checked, from 111.

The release runbook gains a short section, "Number generator behind". It
says to find out why first (a restore from an old copy? a manual reset?),
then run as the owner, through the migrate service: `SELECT
setval('public.plants_id_seq', (SELECT max(id) FROM plants));`.

## 8. Pages, API, permissions, audit

- **Pages:** none. U1.1 puts the look-up on the plant search page, and later
  units show the IDs.
- **API contract:** the Python functions in §2–§4. There are no HTTP
  endpoints.
- **Permission matrix:** no new action. Issuing an SKU keeps
  `PLANT_LIFECYCLE`. Batch numbers are issued inside `save_operation`, which
  checks `LOG_WORK`, as today. Reading needs only a signed-in account.
- **Audit trail:** nothing new to record. New plants and batches are already
  audited on insert (U0.7), and their `row_pk` is the `id` the new trigger
  gave, because the audit trigger runs after the row is written. Events and
  SKUs are append-only and are themselves the record. The owner's `setval`
  during an import isn't audited: it's an owner SSH action, and the V.2
  import (U1.10) designs its own record.

## 12. How G2 proves it

- **Formats (AC1–AC4, AC4a).** Table tests for every function in §2,
  including `PLT-10000`, `BAT-100000`, `PHL1000`, `B1000` and 0 → `ValueError`.
  A round trip for every number from 1 to 20 000 and a few huge ones:
  `read(plant_id(n)).number == n`, and the same for batch, event, SKU and
  short name. `SKU_ORDER` on a queryset of `PHL001`, `PHL100`, `PHL999`,
  `PHL1000`, `ALC002` gives genus first, then by number.
- **SKU checks (AC4).** Raw SQL on `plants` and `skus`: `PHL005`, `PHL999`,
  `PHL1000`, `PHL12345` are accepted. `PHL0005`, `PHL000`, `PHL01000`,
  `PHL05`, `phl005` are refused by name. `issue_next_sku` after `PHL999`
  gives `PHL1000`.
- **Reading (AC5–AC8).** Table tests, one per row of §3.1. Also: blank,
  `PLT-`, `PLT-0`, `XYZ-12`, `PLT-12A`, a 25-digit number, `PLT-๔๒` (Thai
  digits), full-width text, and a middle dot typed as `•`. `read` never
  raises: one test feeds it a few thousand random strings.
- **Look-up (AC5–AC8, S3).** Each kind found; a voided plant, batch and
  event still found; a former SKU and a short name with a former SKU find
  the plant and batch, with `former_sku` set; nothing found gives `None` and
  makes no more than the expected queries (`django_assert_max_num_queries`).
- **Genus prefix (AC5a).** Raw SQL inserting genus `PLT`, `BAT` or `EVT` is
  refused by name.
- **Never issued twice (AC9–AC11, [Q1](#9-owner-questions)).** These are
  `transaction=True` tests built on `at_the_same_moment` from
  `events/tests/test_concurrency.py`, with 25 connections × 4:
  - 100 plants inserted at once, 100 batches (from 100 intakes on different
    plants), 100 events: 100 different ids each.
  - 100 SKUs into one genus at once: `PHL001`–`PHL100`, no gaps. While one
    genus is held by a lock that waits, an issue into another genus finishes
    first (AC10, "other genera are not held up").
  - 100 batches on one plant at once: `plant_seq` 1–100, no gaps (AC11).
- **Never again (AC12).** Void a plant, a batch and an event, then make new
  ones: the new ids are higher. A former SKU is never issued again (the
  existing U0.2 test, kept).
- **Ids chosen by the caller (AC13).** As `cucumber_app` (`app_db`, raw SQL)
  and through the ORM as the app user (the `test_as_app_user.py` way of
  switching Django's connection), an insert with an `id` into each of the
  three tables is refused (`<table>_id_from_sequence`) and nothing is saved.
  One ORM `create()` as the app user, with no id, succeeds (review M5). The
  rest of the suite runs as the owner, which takes the exception path.
- **The owner path (AC13, Q1, Q2).** These are `transaction=True` tests
  that put the generator back afterwards, because a generator doesn't roll
  back with the test (review M5):
  - an owner insert with `id = 500` succeeds, and the next ordinary insert
    gets 501;
  - an owner insert with an unused id below the generator succeeds and
    moves nothing;
  - while an owner insert holds its table lock, an app insert waits, then
    gets a number past the owner's (review M1).
- **Ids never change (review H1).** `UPDATE … SET id` on `plants` and
  `batches` is refused (`<table>_id_fixed`), as `cucumber_app` and as the
  owner.
- **No test expects an absolute id.** Tests compare ids with each other
  (`new > old`) or read them back. G2 checks the existing suite for this.
- **Generator behind (AC14).** On a throwaway connection: `setval` a
  sequence back below `max(id)`, and `check()` reports exactly that line;
  drop a sequence, and it's reported missing; grant `cucumber_app` `UPDATE`
  on one, and the app-role check reports it; revoke its `USAGE`, and that's
  reported; put an identity back on `plants.id`, and that's reported. Each is
  put back afterwards. A fresh, empty database passes.
- **One place (AC15, review M3).** An AST scan of `cucumber/**/*.py`, leaving
  out `cucumber/ids/`, migrations and tests, plus a text scan of the
  templates. It looks at string literals and f-strings, but not docstrings
  or comments, and fails on:
  - the literal prefixes `PLT-`, `BAT-`, `EVT-` and `· B`;
  - **any zero-padded number format**: `0Nd` in an f-string spec (nested
    specs included), `"%0Nd"`, `"{:0Nd}".format`, and `stringformat:"0Nd"`
    in templates.

  Anything allowed outside `ids/` goes on an explicit allow-list in the
  test, with the reason. Today that is nothing.
- **Migrations.** On a scratch database: insert a few rows, migrate
  `core 0007` forward. The next id is the one that was due, the sequence
  keeps its name, and `pg_get_serial_sequence` finds it. Undo, and the
  identity is back at the same position. Forward again. `plants 0003` undo
  is refused while a 4-digit SKU exists.

Expected size: about 50 new tests and 2 existing test files touched (the
moved imports). That still fits in S.
