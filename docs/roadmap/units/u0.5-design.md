# U0.5 · Authentication — Design note (G1)

**Spec:** [u0.5-spec.md](u0.5-spec.md) (AC1–AC31) · **Status:** Draft · 2026-10-19 ·
architect review done (pass with fixes, all applied, [§13](#13-architect-review-2026-10-19));
waiting on [Owner questions](#11-owner-questions) Q1–Q4
**Stack:** Django 5.2 LTS + PostgreSQL 17 ([ADR-0001](../adr/0001-stack-selection.md)).

Most of U0.5 is Django's own login system, set up carefully. Cucumber adds
four things around it: email login, the wrong-password lock, the absolute
30-day limit with a forced password change, and the Admin's Staff pages.

## 2. How login works

```
phone ─► Cloudflare Access (email code, 30 days) ─► tunnel ─► Cucumber
                                                              │
   ┌──────────────────────────────────────────────────────────┘
   ▼
Account checks middleware ── 30 days since login ──► log out (then as "not signed in")
   │
   ▼
LoginRequired middleware ── not signed in ──► login page (or 401 + HX-Redirect for HTMX)
   │ signed in
   ▼
password change due? ── yes ──► change-password page
   │ no
   ▼
the page
```

### 2.1 Email is the user name (AC3, spec Q1)

Django's `auth_user` logs people in by `username`. Cucumber stores the
**email, trimmed and in lowercase**, in `username`, and the same in `email`.
Then Django's own `ModelBackend` does the check, and it already:

- runs the password hasher for an email with no account, so an unknown email
  takes about as long as a wrong password (AC2);
- turns down a deactivated account the same way as a wrong password (its
  `user_can_authenticate` check), so the message is the same (AC2);
- ends a deactivated person's open session on their next page, because it
  also checks `is_active` when it loads the user for each request (AC23).

The login form trims and lowercases what was typed before the check
(`.strip().lower()`, not `casefold()`, so it matches PostgreSQL's `lower()`).
`username` is already unique in `auth_user`, so two accounts can't share an
email (AC22). The database also insists on it (§3.4), so a path that skips the
service (the shell, a command, later units) can't add `Jade@X.com` next to `jade@x.com`.
Emails longer than 150 characters (the column's size) are refused when an
account is added.

**Name:** one "Name" box, stored in `first_name` (`last_name` stays empty).
Thai names don't split into first and last the English way.

### 2.2 Messages

| Situation | Message | Response |
|---|---|---|
| Wrong password, unknown email, deactivated account | Email or password is wrong. | Login page again, status 200 |
| Locked (email or network address) | Too many tries. Wait 15 minutes or ask the Owner. | Login page again, status 200 |
| Form sent without a valid CSRF token | Django's 403 (U0.10 makes a friendly page) | 403 |

A locked unknown email and a locked real one get the same message (AC8). The
check for a lock runs **before** the password check, so a locked try never
reaches the hasher and doesn't reveal whether the password was right.

## 3. Data model and migrations

### 3.1 `accounts_login_failure` (AC7–AC11)

| Column | Type | Notes |
|---|---|---|
| `id` | bigint | |
| `email_key` | varchar(150) | the trimmed, lowercase email as typed; may match no account |
| `address` | inet, null | where the try came from (§7.2) |
| `at` | timestamptz | default `now()` |

Indexes on `(email_key, at)` and `(address, at)`. No foreign key to
`auth_user`, so unknown emails are counted the same as real ones (AC8).

**What it never holds:** the password typed. The table lives in PostgreSQL,
so both gunicorn workers see the same counts and a restart keeps them (AC10).

### 3.2 `accounts_password_change_due` (AC25)

| Column | Type | Notes |
|---|---|---|
| `user_id` | integer, primary key → `auth_user`, `ON DELETE PROTECT` | a row means "must choose a new password" |
| `since` | timestamptz | when the temporary password was given |

Added when an account is created or given a new password; removed when the
person chooses their own.

**Grants** (same migration, as U0.4a did for flags): `cucumber_app` gets
`SELECT, INSERT, DELETE` on both tables, no `UPDATE`.

### 3.3 The `admin` group

No role group exists in the database yet (tests make their own). `0002`
creates `admin` only, with `get_or_create` (a re-run after an undo finds it). U0.6 adds the other three and the screens to grant
them. Undo leaves the group: removing it would silently strip the Owner's Admin
role, and U0.6 owns groups after this.

### 3.4 Two rules on `auth_user` (AC22, AC31, [Q4](#11-owner-questions))

`0003` adds two checks to `auth_user`:

- `auth_user_no_superuser`: `CHECK (NOT is_superuser AND NOT is_staff)`.
  Cucumber doesn't use either flag: Admin is a group, and Django's admin site
  isn't installed. With the check, neither the app nor any code can make an
  account a superuser; only a reviewed migration that drops the check could.
- `auth_user_username_is_email`: `CHECK (username = lower(btrim(username)) AND email = username)`.
  Email uniqueness and the lowercase rule hold even outside the services.

**Why not column grants as the spec says:** when Django saves a user (a login
stamp, a password change, Django's own forms), it writes **every** column,
`is_superuser` included. Taking UPDATE on that column away from `cucumber_app`
makes those saves fail, unless every save in Cucumber and in Django's forms
lists its columns, which is easy to miss. The check stops the actual danger with
no such catch. Undo drops the check. Insert stays allowed (accounts are added),
DELETE stays refused (U0.2a).

**Before it adds them:** a `RunPython` step (like `core 0004`) lists any account
that would break either check and stops with a readable message, instead of a
raw constraint error. G5 runs it on staging and production first. The test
helper `make_staff` (usernames like `supervisor_1`, no email) changes at G2 to
give each test account an email as its username.

**What is still guarded only in code:** `cucumber_app` may add and remove rows
in `auth_user_groups` (U0.2a housekeeping), so joining the `admin` group is
stopped by `require_admin` in the services, not by the database. The AC28 tests
prove a Tech can't reach any service that changes groups; U0.6 adds the role
screens under the same check.

### 3.5 Rollback

Each migration undoes cleanly: drop the two tables (losing only lock counts
and "change due" marks), drop the check. Rolling the app back to `2026.10.1`
reopens no data pages, because that release has none (only `/health/` and login).

## 5. Middleware

Added after `AuthenticationMiddleware` and `MessageMiddleware`, in this order:

1. **`SessionLimit`** (30 days, AC13): when someone logs in, Django's
   `user_logged_in` signal stores `login_at` in the session as whole seconds
   (after Django has given the new session id). On each request, if
   `login_at` is more than 30 days ago, **missing, or unreadable** (a session
   from before U0.5, or a test's `force_login`), it calls `logout()`. The next
   middleware then treats the request as "not signed in", so a plain page goes
   to login and an HTMX request gets the 401 below: no second redirect path.
2. **`LoginRequired`**: Django 5.2's `LoginRequiredMiddleware`, with one change:
   for an HTMX request (`HX-Request: true`) it answers **401** with
   `HX-Redirect: /accounts/login/?next=…` instead of a redirect, so htmx loads
   the whole login page rather than swapping it into a form (AC19). The `next`
   is the path of the **page** the person was on (htmx's `HX-Current-URL`
   header), not the background request's address, which may be a fragment or
   POST-only; it's used only if `url_has_allowed_host_and_scheme` accepts it,
   otherwise left out. Pages open
   without login only when marked `@login_not_required`: Django's login view
   (already marked) and `health` (marked in U0.5). Static files are served by
   WhiteNoise before this runs. A POST that isn't signed in is turned away
   before any view runs, so nothing is saved (AC20).
3. **`PasswordChangeDue`** (AC25): on each signed-in request it looks up the
   person's row in §3.2 (one primary-key lookup; trivial for a few staff). While
   there is one, every page except change-password and logout goes to
   change-password (HTMX: 401 + `HX-Redirect`, `next` as above). Checking the
   table every time, not a flag saved at login, means any path that adds the
   row (the Staff page, `cucumber_admin`, U0.6, a hand fix) takes effect at once.

### 6.2 The two temporary-password pages

A redirect after POST would have to carry the password to the next page through
Django's messages or the session, which would put it in plain text in
`django_session`. So `/staff/new/` and `/staff/<id>/new-password/` show the result
**directly in the POST's answer**, with `Cache-Control: no-store` so the browser
doesn't keep it. Reloading asks "resend the form?"; resending makes **another**
new password, which is harmless: the last one shown is the one that works. The
password is never put in messages, the session or a log.

## 7. Services (`accounts/services.py`)

Views read a form and call one of these; the rules live here (ADR-0001).

### 7.1 Accounts

| Function | Rule |
|---|---|
| `email_key(text)` | trimmed and lowercased; the one place this happens |
| `require_admin(user)` | raises `PermissionDenied` unless `has_role(user, ADMIN)` (AC28) |
| `add_account(by, name, email)` | Admin only; email valid, ≤ 150 chars, not taken; makes a temporary password (§7.3), marks change due; returns the account and the password |
| `deactivate(by, account)` | Admin only; refuses `by == account` (AC24) |
| `reactivate(by, account)` | Admin only |
| `give_new_password(by, account)` | Admin only; refuses `by == account` (the Admin changes their own on the password page); new temporary password and change-due row in **one transaction**; the person's sessions end because the password changed (AC25) |
| `lift_lock(by, account)` | Admin only; deletes that email's failures (AC11) |
| `password_chosen(user)` | after the person saves their own password: removes the change-due row (AC25, AC26) |

Each writes its log line (§8). Refusals use the U0.2 refusal names, with
messages in the `MESSAGES` table: `account_email_taken` ("Another account
already uses this email."), `account_email_invalid` ("Enter a whole email
address, like name@example.com."), `account_cannot_deactivate_self` ("You can't
deactivate your own account."), `account_cannot_reset_self` ("Change your own
password on the Password page."), `password_same_as_temporary` ("Choose a
password different from the one you were given."). `auth_user_no_superuser`
and `auth_user_username_is_email` are Internal.

### 7.2 Lock (AC7–AC11)

```python
def login_lock(email: str, address: str | None) -> bool:
    """True when this email, or this network address, has tried too often."""

def login_failed(email: str, address: str | None) -> None:
    """Count one wrong try. Never given the password."""

def login_succeeded(email: str) -> None:
    """Clear this email's count, and tidy up old rows (§7.5)."""
```

- **Email:** locked when it has **5 or more** failures in the last **15 minutes**.
  The lock lifts by itself 15 minutes after the 5th failure, because older
  failures stop counting.
- **Address:** locked when it has **50 or more** failures in the last 15 minutes,
  across all emails (AC9). The lab's shared address would need 50 typos in 15
  minutes before anyone else notices.
- **The address** is Cloudflare's `CF-Connecting-IP` header on servers (all traffic
  comes through the tunnel, U0.4b §7) and `REMOTE_ADDR` locally. A bad or missing
  value counts as "no address": the email lock still applies.
- **A try turned away by the lock isn't counted.** Otherwise someone who keeps
  retrying would keep themselves locked forever.
- **Lifting a lock** (Admin) clears the email's count. An **address** lock has no
  button: it lifts by itself after 15 minutes. Anyone past Access could lock a
  colleague (5 tries) or the lab's address (50 tries) for 15 minutes; accepted
  behind Access, and the log lines (§8) show who it came from.
- **`CF-Connecting-IP` is read only on servers** (`IS_SERVER`); locally anyone
  could send it. A test checks both.
- **Two tries at the same moment** could squeeze in a few extra tries (at most
  one per gunicorn thread, 8). Accepted: it doesn't help a guesser.

The login form's `clean()` calls `login_lock` first, then Django's check, then
`login_failed` or `login_succeeded`.

### 7.3 Temporary passwords ([Q2](#11-owner-questions))

Made by Cucumber with Python's `secrets`: 12 letters and digits without look-alikes
(no `0 o 1 l i`), shown in three groups of four (`k7fm-p3xq-w9hd`; the dashes are
part of it). That's about 60 bits: well past any guessing within the lock.
Each one is checked with Django's `validate_password` for that person and made
again in the rare case it fails (for example all digits). It's shown once
(§6.2) and never stored in plain text or logged.

### 7.4 Forms

- **Login:** Django's `AuthenticationForm`, the box labelled "Email"
  (`type=email`, `autocomplete=username`), password `autocomplete=current-password`,
  messages from §2.2.
- **Change password:** Django's `PasswordChangeForm` (current password first,
  then new twice, Django's four rules, AC27), then `update_session_auth_hash` so
  this session stays and the others end (AC26). In the forced change, the new
  password can't be the temporary one, or the Admin would still know it.
- **Add account:** name, email.

### 7.5 Ended sessions (AC16, [Q3](#11-owner-questions))

Each successful login deletes ended sessions (`expire_date` in the past, indexed
by Django) and login failures older than a day. Both are small deletes.

## 8. Log lines (AC30)

Logger `cucumber.accounts` at INFO (the `LOGGING` setting gets a `cucumber`
logger at INFO; Django and the rest stay at WARNING). One line each, with
account **ids**, never the typed email of a failed try (people sometimes type
their password into the email box), never a password or session id:

```
login ok account=12
login failed account=12 address=203.0.113.7
login failed account=unknown address=203.0.113.7
login locked account=12 address=203.0.113.7
logout account=12
account added account=14 by=1
account deactivated account=14 by=1
account reactivated account=14 by=1
password given account=14 by=1
password chosen account=14
lock lifted account=14 by=1
admin command account=1          (cucumber_admin, §9)
```

These are the **audit events** for this unit. U0.7 writes them to `audit_log`.

## 9. `cucumber_admin` command (AC29)

```
ssh -t cucumber-server-remote 'cd ~/cucumber/production && docker compose … run --rm app python manage.py cucumber_admin'
```

It asks for email, name and a password (typed twice, hidden, Django's four
rules). If no account has that email, it adds one in the `admin` group. If one
does, it sets the password, reactivates it, clears its lock and any change-due
row, and adds it to `admin`. If that account **isn't already an Admin**, it first
asks "Make Gene an Admin? [y/N]", so a mistyped email can't quietly promote
someone. It runs as `cucumber_app`, like the app. The Owner runs it on production
(the auto-mode classifier blocks Claude there); the runbook gets the exact line.
