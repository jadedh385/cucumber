# U0.4a · App packaging & deploy — Design note (G1)

**Spec:** [u0.4-spec.md](u0.4-spec.md) (AC1–AC14) · **Status:** G1 passed · 2026-10-13 ·
signed off by Jade (Owner) after architect review (pass with fixes, all applied, [§14](#14-architect-review-2026-10-13))
**Stack:** Django 5.2 LTS + PostgreSQL 17 + Docker Compose ([ADR-0001](../adr/0001-stack-selection.md)).

U0.4a is everything that lives in the repo: the container image, the server
compose file, production settings, the deploy and flag commands, and the
Discord announcement. U0.4b then uses them to set up the MacBook, Cloudflare
and the DNS move.

**New packages:** `gunicorn` (web server), `whitenoise` (serves CSS and

read the compose file). Versions pinned by `uv.lock`; Dependabot keeps them

in `INSTALLED_APPS`, `STATIC_ROOT = BASE_DIR / "staticfiles"`, and

`SecurityMiddleware`. Until now there were no static files at all (the login
page uses an inline style).

## 2. The container image (AC1)

One `Dockerfile`, built in two stages so the final image holds no build tools.
Both stages use the **same pinned `python:3.13-slim` digest** (the multi-platform
one, so it builds on ARM and Intel):

1. **Build stage** (+ uv): `uv sync --locked --no-dev` into `/app/.venv`, copy
   the code, then `collectstatic`. Settings need values to load, so fake ones
   are written **on that `RUN` line only**, never as `ENV` or `ARG` (those stay
   inside the image, and a server missing its real secret key would then start
   with the fake one, defeating AC5):
   ```dockerfile
   RUN DJANGO_ENVIRONMENT=production DJANGO_SECRET_KEY=build-only-... \
       DJANGO_ALLOWED_HOSTS=build.invalid DJANGO_CSRF_TRUSTED_ORIGINS=https://build.invalid \
       DB_USER=none DB_PASSWORD=none python manage.py collectstatic --noinput
   ```
   Building as `production` writes whitenoise's manifest (`staticfiles.json`),
   which staging and production need to find their CSS.
2. **Run stage**: copy `/app` from stage 1, run as a **non-root user**
   `cucumber` (uid 10001), `EXPOSE 8000`.

Default command:

```
gunicorn cucumber.wsgi --bind 0.0.0.0:8000 --worker-class gthread
  --workers 2 --threads 4 --timeout 60 --max-requests 1000 --max-requests-jitter 100
```

- **gunicorn** is the standard production server for Django. `gthread` with
  4 threads per worker copes with slow phones on mobile data without tying up
  the whole app. `--max-requests` restarts a worker now and then, so slow
  memory growth never builds up.
- **whitenoise** serves `/static/` from inside the app, with long cache
  headers and compressed copies. No separate web server (nginx, Caddy) is
  needed because Cloudflare sits in front. Tests keep Django's plain storage.
- **Intel build:** the MacBook builds its own (ARM) image at each deploy. CI
  builds on GitHub's Intel (amd64) machines, so every pull request proves the
  image still builds for Intel (staging or production can move to the Asus, a
  mini PC or the cloud without code changes).
- Tests check: `.env` is in `.dockerignore`; the image's environment
  (`docker inspect`) holds no `DJANGO_*` or `DB_*` variable; the user isn't root.

## 3. The server compose file (AC2, AC3)

`deploy/compose.server.yaml` is **one file used by both environments**. What
differs comes from the environment's secrets file and project name. The deploy
and flag commands build the command line; nobody types it:

```bash
docker compose -p cucumber-staging --env-file /Users/sawat/cucumber/staging/secrets.env \
  -f deploy/compose.server.yaml ...
```

The project name prefixes every container, network and volume
(`cucumber-staging-db-1`, volume `cucumber-staging_db-data`), so a staging
command can't reach production's database. **Images are named per
environment too** (`cucumber-staging:2026.10.1`, `cucumber-production:2026.10.1`;
compose reads `image: ${IMAGE_NAME:?}:${CUCUMBER_VERSION:?}`), so clearing old
staging images can never delete production's rollback image.

| Service | Image | Runs as | Restart | Notes |
|---|---|---|---|---|
| `db` | `postgres:17` (pinned multi-platform digest) | PostgreSQL superuser | `unless-stopped` | Named volume `db-data`; `01-roles.sh` creates the two roles on first start (§3.2); log settings as `command:` flags (§5); port `127.0.0.1:${DB_LOCAL_PORT:?}:5432`, this Mac only (staging 5435, production 5436) |
| `migrate` | `${IMAGE_NAME}:${CUCUMBER_VERSION}` | `cucumber_owner` | **`"no"`** | One-off (`profiles: [migrate]`), always run as `docker compose run --rm migrate`. A restart policy here would re-run migrations at every exit and every boot. `--rm` leaves no stopped container holding the owner password |
| `app` | `${IMAGE_NAME}:${CUCUMBER_VERSION}` | `cucumber_app` | `unless-stopped` | gunicorn; port `127.0.0.1:${APP_PORT:?}` (production 8000, staging 8001) for the deploy command's health check; starts after `db` is healthy |
| `tunnel` | `cloudflare/cloudflared` (pinned multi-platform digest) | — | `unless-stopped` | `profiles: [tunnel]`: U0.4b's secrets file sets `COMPOSE_PROFILES=tunnel`; CI and a first try without Cloudflare leave it out. Token given as the `TUNNEL_TOKEN` environment variable, never a `--token` argument (that would show in `ps`). Each environment has its **own tunnel**, which can only reach its own `app` |

Every long-running service also has log rotation (`max-size: 10m`,
`max-file: 3`), so logs can't fill the 25 GB disk. Every required value is
written `${NAME:?NAME missing from secrets.env}`, so compose stops with a
clear message before starting anything.

The database port is opened on both copies, but only on the Mac's own
address (`127.0.0.1`): nothing on the network or the internet can reach it,
and it lets the U0.4b walk-throughs and backups use plain tools.

### 3.1 Who gets which secret (AC6)

The compose file **never uses `env_file:`**, which would hand every secret to
every container. The secrets file only fills in `${…}` values, and each service
gets just the ones it needs:

| Variable | `db` | `migrate` | `app` | `tunnel` |
|---|:-:|:-:|:-:|:-:|
| `POSTGRES_PASSWORD` | ✅ | | | |
| `DB_OWNER_PASSWORD` | ✅ (init script) | ✅ as `DB_PASSWORD` | ❌ | |
| `DB_APP_PASSWORD` | ✅ (init script) | | ✅ as `DB_PASSWORD` | |
| `DJANGO_SECRET_KEY`, hosts, origins, environment | | ✅ | ✅ | |
| `TUNNEL_TOKEN` | | | | ✅ |

The `db` container holds all three database passwords in its environment.
That is accepted: it is the database itself, and only the Mac's admin account
can reach Docker.

**Shell variables can't sneak in.** Compose prefers a variable already set in
the shell over the secrets file, so a stray `export DB_PASSWORD=…` would win
silently. The scripts run `docker compose` with a minimal environment
(`PATH`, `HOME` and `DOCKER_*` only) and an absolute `--env-file` path.
Nothing ever runs `docker compose config` into a log or the screen, since it
prints the filled-in secrets.

### 3.2 Database first start

`01-roles.sh` runs only when the volume is empty. If it fails on the very
first start (e.g. a password missing), the volume is left without roles and
the script never runs again; the runbook says to remove that volume and start
again. Changing a `DB_*_PASSWORD` in the secrets file later doesn't change the
database's password; that needs `ALTER ROLE` (runbook step).

### 3.3 Staging can't starve production (AC3, Q1)

Staging's secrets file sets `APP_MEMORY_LIMIT=512m`, `DB_MEMORY_LIMIT=512m`
and `TUNNEL_MEMORY_LIMIT=128m`; production leaves them out (`0` = no cap).
Each service sets `mem_limit` and an equal `memswap_limit` from them, so the
cap can't be doubled through swap. Docker Desktop's whole Linux VM stays at
4 GB (set 2026-10-11), leaving the other 4 GB to macOS.

**Moving staging later** is the same secrets file and the same commands on
another machine; nothing in the repo names the MacBook.

## 4. Settings and secrets (AC4–AC7, AC9)

### 4.1 The secrets file (AC4)

Each environment's folder on the server (§6) holds `secrets.env`, made from
`deploy/secrets.env.example`, **readable only by the admin account
(`chmod 600`)**. The deploy and flag commands refuse to run if anyone else can
read it, and never print its values. The Owner keeps a copy of each value in
their password manager. `.env.example` (local) and `deploy/secrets.env.example`
(servers) together list every variable; the U0.3 test is extended to check
both, plus every `${…}` in the compose file.

### 4.2 Refusing to start (AC5)

`settings.py` keeps its `required()` helper (U0.3) and adds two variables:

| Variable | Meaning | With debug off |
|---|---|---|
| `DJANGO_ENVIRONMENT` | `local`, `staging` or `production` | Required; any other value refuses to start |
| `DJANGO_CSRF_TRUSTED_ORIGINS` | e.g. `https://cucumber.southeastcanopy.com` | Required on staging and production; each must start with `https://` |

Already required with debug off: `DJANGO_SECRET_KEY`, `DJANGO_ALLOWED_HOSTS`,
`DB_USER`, `DB_PASSWORD`. A missing or blank one stops start-up with a message
naming it, for example:

```
ImproperlyConfigured: DJANGO_CSRF_TRUSTED_ORIGINS must be set when
DJANGO_ENVIRONMENT is production. See deploy/secrets.env.example.
```

Debug can't be turned on when the environment is `staging` or `production`
(refuses to start). The existing CI job and `.env.example` gain
`DJANGO_ENVIRONMENT=local`.

### 4.3 Production security settings (AC7)

Switched on when the environment is `staging` or `production` (not locally,
where there is no HTTPS):

| Setting | Value | Why |
|---|---|---|
| `SECURE_PROXY_SSL_HEADER` | `("HTTP_X_FORWARDED_PROTO", "https")` | Cloudflare ends HTTPS and tells the app; safe because the app's port is open to this Mac only (U0.4b checks the header arrives) |
| `SECURE_SSL_REDIRECT` | `True`, no exceptions | The deploy command's own checks send the HTTPS header (§6.2) |
| `SESSION_COOKIE_SECURE`, `CSRF_COOKIE_SECURE` | `True` | Cookies only travel over HTTPS |
| `SECURE_HSTS_SECONDS` | from `DJANGO_HSTS_SECONDS`: **1 hour** at first, 1 week once U0.4b confirms HTTPS works, then 1 year. `INCLUDE_SUBDOMAINS` on | Phones always use HTTPS for Cucumber; starting short is Django's own advice and costs nothing. Affects only `cucumber…` names, never the website or email |
| `SECURE_HSTS_PRELOAD` | off; check `security.W021` silenced with this reason | Preload works only for a whole domain, and `southeastcanopy.com` isn't ours to preload |
| `CSRF_TRUSTED_ORIGINS` | from the variable | Forms work behind Cloudflare |
| `STORAGES["staticfiles"]` | whitenoise compressed manifest | Long-cached CSS and images |
| `LOGGING` | errors and warnings to the container log, plain one-line format | `docker compose logs` shows them; no request bodies, cookies or settings are ever written. No error emails |

**CI runs the check (AC7):** the new "Container image" job builds the image,
then runs inside it, with fake production values:

```
python manage.py check --deploy --fail-level WARNING
```

`--fail-level WARNING` matters: without it, `check --deploy` only fails on
errors and its security warnings would pass silently. The fake secret key is
at least 50 characters and doesn't start with `django-insecure-` (a shorter one
raises W009); the fake trusted origin is `https://example.invalid`.

## 5. Database connection and logs (AC8)

- The app's connection sets **`lock_timeout = 5s`**:
  `DATABASES["default"]["OPTIONS"] = {"options": "-c lock_timeout=5s"}`. A
  save waiting on another save's lock gives up after 5 seconds instead of
  hanging. Nothing is saved in that case. Until the data-entry screens exist
  it shows the error page; each screen unit turns it into "Busy, please try
  again" (logged to the U1.x screen units in the tracker).
- `CONN_MAX_AGE = 60` with `CONN_HEALTH_CHECKS = True`: connections are reused
  for a minute and checked before use, so a database restart doesn't leave
  broken connections behind (at most 8 per environment). No pooler (out of
  scope).
- **PostgreSQL logs**, set as `command:` flags on the `db` service (a separate
  config file would replace the image's whole config, including the setting
  that lets the app connect):
  ```yaml
  command: ["postgres", "-c", "log_lock_waits=on",
            "-c", "log_min_duration_statement=500ms",
            "-c", "log_min_error_statement=panic"]
  ```
  Lock waits and statements slower than 500 ms are logged.
  `log_min_error_statement=panic` keeps the **text of failing statements** out
  of the log (the error message itself is still logged). **Known limit:**
  Django sends values inside the statement text, so a statement slower than
  500 ms is logged with its values. That is accepted: slow statements are
  reads and reports, the log stays on the admin-only Mac, and switching to
  server-side binding has caveats Django warns about.

## 6. The deploy command (AC10–AC12)

### 6.1 Folders on the server

```
~/cucumber/
├── tools/              git clone on main: where deploy.py and flag.py run from
├── deploy.lock         one lock for both environments
├── production/
│   ├── src/            git clone, checked out at the deployed tag (built from)
│   ├── secrets.env     chmod 600
│   ├── current         the version now running, e.g. 2026.10.1
│   ├── backups/        copies taken before each deploy (last 5 kept, Q4)
│   └── logs/           one file per deploy, plus flags.log (G6 evidence)
└── staging/            the same
```

- Each environment has **its own clone to build from**, so deploying staging
  never moves production's code.
- The scripts run from a **separate `tools` clone on `main`**, so checking out
  a tag never changes the script that is running. They use only Python's
  standard library and run with `uv run --no-dev`, so nothing extra is
  installed on the Mac.
- The root folder is `~/cucumber` unless `CUCUMBER_HOME` says otherwise (CI, §9).

### 6.2 What it does

```bash
cd ~/cucumber/tools
uv run --no-dev python -m scripts.deploy staging 2026.10.1
uv run --no-dev python -m scripts.deploy staging main          # staging only (AC11)
uv run --no-dev python -m scripts.deploy production 2026.10.1  # tags only
```

It is **Python**, not a shell script, so it is readable and unit-tested.

| Step | What it prints | Stops if… |
|---|---|---|
| 0 | `Checking before we start` | another deploy is running (`fcntl.flock` on `deploy.lock`; a crash leaves no stale lock, and two builds at once would strain 8 GB); secrets file missing or readable by others; production asked for anything but a version tag (`next_version`'s pattern, months 01–12); the tag doesn't exist on GitHub; the clone has stray files (`git status --porcelain --ignored`, `.venv` excepted), which would end up in the image |
| 1 | `Getting 2026.10.1 from GitHub` | `git fetch --tags --force` (a re-made tag must move) or checkout fails; `HEAD` isn't exactly the tag's commit |
| 2 | `Building the app (takes 1–3 minutes)` | build fails; nothing has changed yet |
| 3 | `Checking the database fits this version` | the database has migrations this version doesn't know (§6.3); asks before going on |
| 4 | `Saving a copy of the database` | `docker compose exec -T db pg_dump -Fc` fails, or the copy's contents list can't be read (`pg_restore --list`, a basic check, not a tested restore) |
| 5 | `Updating the database (2 changes)` or `(no changes)` | a migration fails (§6.3) |
| 6 | `Restarting the app` | — |
| 7 | `Checking the app answers` | `/health/` isn't "ok" within 60 seconds (§6.3) |
| ✓ | `Done: staging now runs 2026.10.1 (was 2026.09.3). Took 2 min 41 s.` | |

- **Health check from the Mac:** a request to `127.0.0.1:${APP_PORT}` would be
  refused by `ALLOWED_HOSTS` (it only lists the public name) and redirected to
  HTTPS. So the command sends `Host: <first DJANGO_ALLOWED_HOSTS entry>` and
  `X-Forwarded-Proto: https`, exactly what Cloudflare sends.
- **Counting changes:** a tiny `pending_migrations` management command prints
  the number of migrations still to run, and the names of applied migrations
  this version doesn't have. No parsing of Django's human-readable output.
- **Backup:** `-T` matters (without it the binary copy is corrupted). Saved as
  `backups/2026-10-13-1405-before-2026.10.1.dump` with permissions set so only
  the admin can read it (`umask 077`), keeping the last 5. A local safety net,
  not the off-site backup (U0.11).
- **Images:** the last 3 per environment are kept so the previous one is ready
  for rollback; older ones are deleted. After a successful deploy, build cache
  older than a week is cleared (`docker builder prune --filter until=168h -f`),
  since it grows on a 25 GB disk.
- Staff see a gap of about 10 seconds while the app restarts. During step 5 the
  old version runs against the updated database, so **a release's migrations
  must keep the previous release working**: add first, remove in a later
  release. Written into the PR template's checklist. Deploy outside busy lab
  hours ([release process](../release-process.md)).
- Everything printed also goes to `logs/<time>-<version>.log` (Q3). Secret
  values are never printed.

### 6.3 When something fails (AC12)

"The previous version's migrations still match" (AC12) is checked exactly:
the database must have no applied migration that the version being run
doesn't know.

| What failed | New migrations? | What the command does and says |
|---|---|---|
| Steps 0–2 | — | Nothing has changed. `Stopped: <reason>. Staging still runs 2026.09.3.` |
| Step 3: database ahead of this version (e.g. deploying an older tag) | — | `The database has 2 changes this version doesn't know (…). It may not work. Restore an older copy instead, or type yes to go on.` |
| Step 5 (migration) | — | The old version is still running. Says which migrations were applied before the failure; if any: `Restore the copy saved in step 4: backups/…dump` |
| Step 7 (health) | **None** | Puts the previous image back, checks out the previous tag in `src/` again (so later commands use the matching compose file), checks health: `The new version didn't answer, so 2026.09.3 is back. Nothing was lost.` |
| Step 7 (health) | **Some** | Doesn't put the old version back (it may not understand the changed database): `The new version changed the database and isn't answering. Restore the copy saved in step 4: backups/…dump`, plus the container's last 30 log lines |
| First ever deploy | — | No previous version; says so and stops |

Until U0.11 writes the restore runbook, a restore is done with Claude.

## 7. Feature flags (AC13)

**django-waffle**, behind a small command so the Owner never needs Waffle's
own options (whose meanings are easy to get wrong: a new Waffle flag is on for
superusers by default, and its own command leaves group rows behind when
switching off):

```bash
cd ~/cucumber/tools
uv run --no-dev python -m scripts.flag production list
uv run --no-dev python -m scripts.flag production needs_attention on
uv run --no-dev python -m scripts.flag production needs_attention on --group Owner
uv run --no-dev python -m scripts.flag production needs_attention off
```

```
Flags on production
  needs_attention      on for: Owner
  discord_alerts       off
```

- `scripts/flag.py` runs our own management command, **`cucumber_flag`**,
  inside the running `app` container (`docker compose exec -T app`, with
  `CUCUMBER_VERSION` taken from the `current` file). It has fixed meanings:

  | Command | `everyone` | Groups |
  |---|---|---|
  | `on` | on | cleared |
  | `off` | off | cleared |
  | `on --group Owner` | unset (groups decide) | set to the named groups |

  Superusers, staff, percentage and the other Waffle fields are always off.
- It runs as **`cucumber_app`**, so the owner password stays with the
  migration step only (AC6). Migration `core 0005` (depends on Waffle's last
  migration) narrows the default rights U0.2a gave on Waffle's tables to
  exactly what is needed: `waffle_flag` SELECT, UPDATE (no INSERT: flags are
  created by migrations); `waffle_flag_groups` SELECT, INSERT, DELETE; the
  other Waffle tables SELECT only. Undo restores the defaults. Least
  privilege; the U0.6 on-screen switch reuses the same rights.
- **No flag cache.** Waffle caches flags in Django's cache, which is separate
  in every gunicorn worker, so a change could show on some page loads and not
  others. `WAFFLE_CACHE_NAME` points at a `DummyCache` entry in `CACHES`: one
  small query per check, fine at this size, and a change shows on the very
  next page load.
- **Flags are created by the feature's migration** with every field off. The
  command refuses a name that doesn't exist (`No flag called needs_atention.
  Flags on production: needs_attention, discord_alerts`), so a typo can't
  create a new one. `WAFFLE_CREATE_MISSING_FLAGS` stays off and missing flags
  count as off.
- Code checks flags in templates (`{% flag "needs_attention" %}`) and views;
  services stay flag-free unless a rule itself changes.
- Each change prints a line and adds it to `~/cucumber/<env>/logs/flags.log`
  (time, flag, state, groups). The in-app record of who changed what comes
  with U0.7.

## 8. Release announcement (AC14)

`.github/workflows/announce-release.yml` runs on **`release: published`**
(the workflow file and script come from the tagged commit):

- `permissions: contents: read`. The release text is read from the event file
  GitHub provides (`GITHUB_EVENT_PATH`), never pasted into a `run:` line, so
  text in a release can't run commands.
- `scripts/announce_release.py`:
  1. Normalises line endings (GitHub's web editor saves Windows-style ones),
     then takes the **"## For staff"** section only (the technical part stays
     on GitHub). No such section, or it says "None": posts nothing and says so.
  2. Message: `**Cucumber 2026.10.1 is live**`, then the note. Over 2,000
     characters: cuts at the last whole line that fits (a single line longer
     than that is cut hard) and adds `Full notes: <release link>`.
  3. Posts to `DISCORD_RELEASE_WEBHOOK` (GitHub secret) with
     `allowed_mentions: {"parse": []}`, so `@everyone` or a name in a note
     can't ping anyone, and a named User-Agent (Discord refuses Python's
     default one). If Discord says "too many requests", waits the time it asks
     and tries once more. The webhook address is never printed.
  4. Discord error or missing secret → the run fails (red) with a plain
     reason. The release stays published; the Owner posts by hand.
- A **draft** release never triggers it; only pressing *Publish* does.

[release-process.md](../release-process.md) is updated: "one plain HTTPS
request from a small Python script" instead of `curl`.

## 9. CI changes

New job **"Container image"** in `ci.yml`, alongside the existing checks:

1. Build the image (Intel/amd64) (AC1); check it runs as non-root and its
   environment has no `DJANGO_*` / `DB_*` values.
2. Run `check --deploy --fail-level WARNING` inside it with fake production
   values (AC7, §4.3).
3. **Deploy rehearsal:** with `CUCUMBER_HOME` in the runner's temp folder,
   fake staging secrets and no tunnel, run the deploy command with
   **`--source <checkout>`**. That option exists only for staging, is hidden
   from help, and skips the GitHub steps (0's tag check and 1) so the pull
   request's own code is built. Then, sending the same `Host` and HTTPS headers
   as §6.2, check: `/health/` is "ok"; `cucumber.css` is served with a long
   cache header; the login page shows the banner; the app connects as
   `cucumber_app` and its environment has no `DB_OWNER_PASSWORD`; a flag turned
   on shows on the next request with 2 workers; a second deploy finds "no
   changes" (AC2, AC3, AC6, AC9, AC10, AC13).

About 3–4 extra minutes per run, in parallel with the existing job (free plan:
2,000 minutes a month). Dependabot gains the `docker` ecosystem so the pinned
base images get update PRs.
