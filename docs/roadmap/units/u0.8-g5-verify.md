## Timing note (10× today)

[`uat/timing_u0_8.py`](../../../uat/timing_u0_8.py) on this Mac (PostgreSQL 17 in
Docker), 2026-10-24, sandbox data only, in a throwaway database. It reuses
`scripts/timing_10x.py` (`uat/timing_10x.sh` itself did not fit: it times
neither the look-ups nor the ID functions) and adds the ID work. 3,000 plants,
10,001 batches, 362,000 entries, 900 SKUs. **Before** is `main`; **after** is
the same data moved up by the branch's three migrations, which took **0.6 s**
at this size. After the move the generators stood at next 3001, 10002 and
362001, one past each table's `max(id)`, with 122 protections on.

| Action | Before | After |
|---|--:|--:|
| Look up by PLT- id (before: the plain query) | 0.5 ms | 0.5 ms |
| Look up by BAT- id | 0.7 ms | 0.5 ms |
| Look up by EVT- id | 1.3 ms | 0.6 ms |
| Look up by SKU | 0.6 ms | 0.6 ms |
| Look up by short name | 1.2 ms | 1.2 ms |
| `issue_next_sku` | 3.6 ms | 3.8 ms |
| `lock_plants`, 1 plant | 1.4 ms | 1.4 ms |
| `lock_plants`, 5 plants | 1.4 ms | 1.6 ms |
| Save an entry, typical batch (an event) | 7.1 ms | 7.1 ms |
| Save an entry, busy batch | 23.4 ms | 20.5 ms |
| Save a new batch with its intake | 8.8 ms | 7.6 ms |
| Register a plant (plain SQL as the app) | 1.2 ms | 1.5 ms |

Medians. The p95 of the new look-ups is at most 1.6 ms, of `issue_next_sku`
10.4 ms (4.2 before; one slow run in 30), of a new-batch save 12.4 ms (38.3
before). The rest of the `timing_10x` table (split, void, correction, review
queue, `check_projections`) moved by no more than run-to-run noise. Nothing
U0.8 touches is slower in a way a phone user could notice. Before-side
look-ups are the plain queries `main` would have made, because `look_up` is
new: SKU through `find_by_sku`, and for the short name `find_by_sku` plus a
batch query.

The two `uat/` scripts were tidied for ruff and strict mypy (CI checks `uat`)
after these numbers were taken. The tidied timing script was run again on the
branch alone and agrees (look-ups 0.6–1.3 ms, `issue_next_sku` 3.8 ms, new-batch
save 8.3 ms); the seed script was only restyled (types, line lengths) and not
run again.
