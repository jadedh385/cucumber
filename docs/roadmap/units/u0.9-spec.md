# U0.9 · Reference lists — Spec (G0)

**Unit:** [U0.9](../phase-0-foundations.md#u09--reference-lists) · **Size:** S ·
**Deps:** U0.6 (passed G6), U0.7 (passed G6) · **Decisions:** D-06, D-08, D-14 (Resolved); D-22 (Open, treated as an assumption, [Q6](#owner-answers))
**Status:** G0 draft · 2026-10-25 · Q1–Q7 answered; waiting for the Owner's answer to Q8 and sign-off and sign-off

## Goal

The short lists that every coded field draws from (stage, medium, location,
genus, container, count unit, event action) are kept in one place, in the
right order, with rules about who may change them and a record of every
change. A list item that is no longer used is switched off, never removed, so
old records still read correctly.

Most of the lists already exist (U0.2a, U0.7, U0.8). U0.9 is mostly **the
rules for changing them and the one place to read them**, plus the two things
that are missing: the container type list and the seed stage ([Q1](#owner-answers)).

| List | Who changes it | Where it is today | Missing |
|---|---|---|---|
| Stages | Admin: labels (and on/off) | `stages`: `P0 P1 P2 A1 P4` active, `P3 T1 C0` reserved; sort order; **label is the code** | real labels; seed stage ([Q1](#owner-answers)); any way to edit |
| Media codes | Admin: add, label, on/off | `media_codes`: `M001–M004 G001 G002 R001`; **label is the code** | real labels; any way to edit |
| Locations | Admin: label | `locations`: `lab`, `nursery` (D-14) | any way to edit |
| Genus codes | Admin: add, name, on/off | `genera`: `HYA PHL ALC`; code format, `PLT/BAT/EVT` refused (U0.8) | any way to edit |
| Container types | Admin: add, label, on/off | **nothing** | the list |
| Event actions | nobody (fixed) | `Action` in `events/models.py` and the `event_action_valid` check: 14 actions | one place to read it |
| Count units | nobody (fixed) | **nothing** (D-22: arrives with batches, U1.3) | the list `plant`, `vessel`, `mg` |

Already protected by U0.2a and U0.7, and only pinned by U0.9's tests: codes
can't be renamed (`<table>_code_rename`), nothing is deleted
(`<table>_no_delete`), every change writes an `audit_log` row, and switching an
item off needs a reason from the `archive` list (`<table>_reason_required`).

## User stories

| # | As a… | I want… | So that… |
|---|---|---|---|
| S1 | Admin | to change the label of a stage, medium, location, genus or container type | the words on screen match how we talk, without touching the code that records point at |
| S2 | Admin | to add a medium code, a genus code or a container type | a new recipe, genus or pot size can be used the day it arrives |
| S3 | Admin | to switch an item off, with a reason, and back on again | a retired medium stops appearing in dropdowns, but old batches still show it |
| S4 | Tech / Supervisor | dropdowns that show only what is in use, in the right order | I can't pick a medium we no longer make, and stages read P0 → P1 → P2 → A1 → P4 |
| S5 | Owner | a stage for seed that isn't `P0`: `S0 · Seed` ([Q1](#owner-answers)) | seed counted in mg has a true stage and `P0` keeps its meaning |
| S6 | Owner | event actions and count units that nobody can add to, rename or switch off | stock sums and the history never change meaning |
| S7 | Owner | every list change in the audit trail, with who, when, before and after, and why | I can see who switched off what |
| S8 | Developer | one place that gives the lists to every later screen and rule | U0.10's dropdowns and Phase 1's rules don't each keep their own copy |

## Acceptance criteria

**Stages** (SOP §3 Stages; D-06, D-08)

- **AC1** *Given* a fresh database, *then* the stages are `P0` Sterilization / new species introduction, `P1` Multiplication, `P2` Growth, `A1` Acclimatization (hardening off), `P4` Growth maturity (potted plants) — active, in that order — and `P3` Transport, `T1` Digital content, `C0` Clean, reserved (inactive). Every label is words, not the code. `S0` Seed is also active, with sort order before `P0` and no default subculture interval (Q1 a)). The `S0` batch keeps its stage and its `mg` count for life; germinated seedlings move into a new child batch ([Q8](#owner-answers)).
- **AC2** *Given* the stage list, *then* it is read in **sort order**, not code order, and `A1` sits between `P2` and `P4` (D-06). A question such as "is this stage at or after `P4`?" is answered from the sort order.
- **AC3** *Given* any stage, *when* anyone tries to change its code (the app, the ORM, raw SQL, as `cucumber_app` or the owner), *then* it is refused (`stages_code_rename`).
- **AC4** *Given* the Admin edits a stage's label, *then* the label changes and the code and sort order don't. A blank label is refused.
- **AC5** *Given* the Admin tries to add a stage or change a sort order, *then* it is refused by rule name ([Q5](#owner-answers)); that is a migration with its own G0 (U2.5 and U5.2 use the reserved stages).

**Media, genera, container types** (SOP §3 Media codes, Plant source, Reference lists)

- **AC6** *Given* the Admin adds a media code, a genus or a container type with a code and a label (a genus: code and name), *then* it is saved, active, and appears in its dropdown. A code that is blank, written differently from the list's format (media: upper-case letters and digits, `M001`; genus: three upper-case letters, `PLT/BAT/EVT` refused, U0.8 AC5a; container type: format in the G1 design), or already in the list in any letter case, is refused by rule name and nothing is saved.
- **AC7** *Given* the Admin edits the label (a genus: the name) of an item, *then* only the label changes. A blank label, or a genus name already used (`genera_name_unique`), is refused.
- **AC8** *Given* a fresh database, *then* the media codes are `M001–M004`, `G001`, `G002`, `R001` with a label each; the genera are `HYA`, `PHL`, `ALC`; the container types are `250 ml flask`, `magenta box`, `4-inch pot`, `grow bag` (SOP §3) plus `jar`, `disposable cup`, `tray` (D-22), all active. The Admin changes them afterwards; none is a rule.

**Locations** (D-14)

- **AC9** *Given* a fresh database, *then* the locations are `Lab` and `Nursery`, and the Admin can edit their labels. Adding a location or switching one off is refused ([Q5](#owner-answers)); the storage hierarchy is U3.1. "Land" is not a location.

**Switching off, never deleting** (SOP §3 Reference lists; SOP §5 rule 9; U0.7 AC11)

- **AC10** *Given* an item of an editable list, *when* the Admin switches it off with a reason from the `archive` list (and an optional note), *then* it is saved as inactive and the audit row carries the reason code and note.
- **AC11** *Given* a switch-off with no reason, a reason from another list, or a note over 500 characters, *then* it is refused by rule name (`reason_required`, `reason_wrong_list`, `reason_note_too_long`) and nothing is saved. The database refuses it too, so a later screen can't skip it.
- **AC12** *Given* an inactive item, *when* the Admin switches it back on, *then* it is active again; no reason is asked and the audit row shows the change ([Q3](#owner-answers)).
- **AC13** *Given* an inactive item, *then* it is **not** in the list a dropdown is built from, and **is** still found by its code when an old batch, event or plant shows it (label and all). A new record that names an inactive item is refused by rule name (`list_item_inactive`); records already pointing at it are untouched.
- **AC14** *Given* any item of any list, *when* the app, the ORM or raw SQL tries to delete it, *then* it is refused (`<table>_no_delete`), as `cucumber_app` and as the owner.

**Fixed lists** (SOP §3 Counting; D-22)

- **AC15** *Given* the event actions, *then* the list is the fourteen actions the events table already allows, readable in one place, and no role (Admin included) and no service can add, rename or switch one off. A new action is a migration with its own G0.
- **AC16** *Given* the count units, *then* the list is exactly `plant`, `vessel`, `mg`, readable in one place, with the same refusal as AC15. If D-22 changes the units at U1.3 G0 the list changes with it; no batch has a count unit before U1.3 ([Q6](#owner-answers)).

**Who may edit** (SOP §7; U0.6)

- **AC17** *Given* the matrix row "Edit reference lists" (`edit_reference_lists`), *then* only the Admin holds it. A Supervisor, a Tech, a Read Only account, an account with no role and a switched-off account are each refused (`role_not_allowed`, `account_not_active`) on every change in AC4–AC12, and the matrix's generated tests cover the row. Everyone signed in can read the lists through dropdowns ([Q2](#owner-answers)).
- **AC18** *Given* the row changes from "later" to "services" in the matrix, *then* the U0.6 tests that read the matrix pass with no hand-edited expectation.

**Audit trail** (U0.7 AC4, AC11)

- **AC19** *Given* any add, label edit, switch-off or switch-on in AC4–AC12, *then* one `audit_log` row is written in the same transaction: who (the signed-in person), when (database clock), the table and code, `insert` or `update`, before and after, `via`, and for a switch-off the reason code and note. If the audit row can't be written, the change is not saved.
- **AC20** *Given* every change goes through a writer in `cucumber.references`, *then* each runs inside `audited(person, reason=…)` after the permission check; a change with nobody named is refused by the database (`audit_actor_required`). A test fails if a writer skips either.
- **AC21** *Given* a change that fails any rule (a refused code, no reason, wrong role), *then* nothing is saved and no audit row is written.

**One place**

- **AC22** *Given* a later screen or rule needs a list, *then* it asks the `references` service for it (active items in order for a dropdown, one item by code for history, active-or-not test for a write) and does not query the tables or copy the codes itself. A test fails if another module lists stage, location, count-unit or action codes as literals, as the U0.8 AC15 scan does for IDs.

## Out of scope

- **Screens**, pending [Q4](#owner-answers): the list-editing pages and the dropdown component are built with the app shell (U0.10) or later.
- **The reason lists themselves** (`void`, `correction`, `loss`, `retire`, `archive`, `deactivate`): seeded and protected by U0.7; the Admin editing them is not in the roadmap ([Q7](#owner-answers)).
- **Vendors**: copied from Zoho only (D-04, U3.2).
- **The storage hierarchy** under Lab and Nursery (U3.1) and **media recipes and prepared lots** (U3.4, U3.5).
- **Default subculture days** on a stage (`stages.default_subculture_days`; D-11, U2.2, U4.2).
- **Batch columns** that use these lists: `count_unit`, `container_type`, `est_plants_per_vessel` (D-22, U1.3). U0.9 only holds the lists. Also: whether a seed lot must count in mg.
- **Selling units** (D-23, U1.3 G0).
- **New stages, other than seed** (U2.5, U5.2) and **new event actions** (e.g. `sale`, Shopify decisions §2).
- **Translating labels** (D-16). Labels are data, in English; Thai labels are a later decision.
- **Seed to seedling flow** (the child batch and its stage, [Q8](#owner-answers)): U1.5 / U1.6.
- **Loading V.2 codes** into the lists (U1.10).

## What exists already (found in the code, 2026-10-25)

- `references` tables: `genera`, `stages`, `media_codes`, `locations`, `reasons`, `vendors`. Codes are primary keys; each has `active`.
- Database rules (`references 0003`, `core 0006`): code can't change, no delete, audit trigger on each, and `active = false` needs a reason from the **`archive`** list. Reactivating needs none. `stages` also have a unique sort order, and an active stage needs one.
- `references/services.py` is empty. `EDIT_REFERENCE_LISTS` in `accounts/permissions.py` is Admin only, built "later".
- Genus code: three capitals, `PLT/BAT/EVT` refused (U0.8). Genus `name` is unique.
- Seeds label stages and media codes with the code itself.
- **Nothing refuses an inactive item today.** No writer checks `active`; Phase 1 writers don't exist yet.
- No container types table; no `count_unit` anywhere; event actions are in code and a database check.
- The word "deactivate" is used for the lists, but the **reason list** for a list item is `archive`; `deactivate` is for staff accounts (U0.7 §5.1).
