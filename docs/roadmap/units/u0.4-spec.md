# U0.4 · Environments & self-hosted deployment — Spec (G0)

**Unit:** [U0.4](../phase-0-foundations.md#u04--environments--self-hosted-deployment), built as U0.4a + U0.4b · **Size:** L (as two M units) ·
**Deps:** U0.3 · **Decisions:** D-10, D-25, D-26
**Status:** G0 passed · 2026-10-13 · signed off by Jade (Owner)
**Design:** [u0.4a-design.md](u0.4a-design.md) (U0.4a G1 passed 2026-10-13); U0.4b design at its own G1

## Goal

Give Cucumber three places to run, and a safe, repeatable way to put a
version into each:

| Environment | Where | Data | Who reaches it |
|---|---|---|---|
| **Dev** | Any laptop (exists since U0.3) | Throwaway | The developer |
| **Staging** | A second, separate copy on the MacBook for now (D-26, [options compared](#staging-host-options-compared-2026-10-12)) | Practice data only, never a copy of real data | Owner, Claude, staff for UAT (Q1) |
| **Production** | The MacBook Air `cucumber-server` (ADR-0001) | Real data | Owner and staff |

Staff reach staging and production from anywhere through **Cloudflare Tunnel +
Access** (D-10): Cloudflare asks for their email address and sends a 6-digit
code (asked again every 30 days per phone, Q4) before Cucumber's own login
page appears. No port is opened on the
router or the machines.

After U0.4, U0.2a and U0.2b can finish G5 on staging, and every later unit
has a staging copy for its G5 checks.

## The split

- **U0.4a · App packaging & deploy** (M, Deps: U0.3): everything that lives in
  the repo and can be tested on the home network. AC1–AC14.
- **U0.4b · Hosts, Cloudflare & go-live readiness** (M, Deps: U0.4a): setting up
  the MacBook (both copies), moving DNS, the Tunnel and Access, remote management, the
  uptime alert and the restart tests. Mostly Owner + Claude at the keyboard,
  following runbooks. AC15–AC27.

## Acceptance criteria

### U0.4a · App packaging & deploy

**Packaging**

- **AC1** *Given* the repo, *then* one container image runs Cucumber with a production web server (not Django's test server) and serves its own CSS and images; the same image also builds for an Intel machine, so staging or production can move later (D-26, ADR-0001 fallback).
- **AC2** *Given* an environment's compose file, *then* every container in it (app, database, tunnel) has `restart: unless-stopped`, and the database's data lives in a named volume that survives a rebuild (the spike's database didn't restart, see the [setup log](../../runbooks/macbook-server-setup.md#setup-log)).
- **AC3** *Given* staging and production on the same MacBook, *then* each has its own compose project name, database, volume, port and secrets file, so a command for one can never touch the other; and staging is capped in memory so a heavy test can't starve production. Moving staging to another machine later needs no code change.

**Secrets and settings**

- **AC4** *Given* a server, *then* its secrets live in one file outside the repo, readable only by the admin account, and never in git, chat or logs. `.env.example` lists every variable (U0.3 AC13 still holds).
- **AC5** *Given* any required variable missing or blank on a server (secret key, allowed hosts, trusted origins, database user and password, environment name), *when* Cucumber starts, *then* it refuses to start and names the missing variable; it never falls back to a default.
- **AC6** *Given* the running app, *then* it connects as `cucumber_app`; the `cucumber_owner` password is used only by the migration step and is not visible inside the running app container (U0.2a G4).
- **AC7** *Given* production settings, *then* `manage.py check --deploy` reports nothing: HTTPS-only cookies, HSTS, the Cloudflare proxy header, `CSRF_TRUSTED_ORIGINS`, and a logging setup that writes errors without passwords or secrets (U0.3 G4). CI runs this check.
- **AC8** *Given* the app's database connection, *then* a statement waiting for a lock gives up after a set time (`lock_timeout`, U0.2b G4) and PostgreSQL logs errors and slow statements (U0.2a G4).
- **AC9** *Given* staging, *then* every page shows a "Practice data" banner, and production never shows it.

**Deploy**

- **AC10** *Given* a version tag, *when* the Owner runs **one command** on a server (e.g. `deploy staging 2026.10.1`), *then* it: checks out that tag, builds the image, takes a database backup copy, runs migrations as `cucumber_owner`, restarts the app as `cucumber_app`, and checks `/health/`. It prints each step in plain words.
- **AC11** *Given* production, *then* it deploys **only** from a version tag (what runs is exactly what the release notes describe); staging may also deploy `main` for practice.
- **AC12** *Given* the health check after a deploy fails, *then* the command says so in plain words and puts the previous version back, as long as that version's migrations still match; if they don't, it stops and says to restore the backup taken in AC10 (full restore is U0.11).

**Feature flags**

- **AC13** *Given* a flag (django-waffle), *when* the Owner runs `flag <name> on` or `off` on the server, *then* the feature appears or disappears on the next page load, with no redeploy; `flag list` shows every flag and its state. A flag can also be on for one group only (e.g. Owner first).

**Release announcement**

- **AC14** *Given* the Owner publishes a GitHub Release, *then* its "For staff" part is posted to the staff Discord channel, with mentions switched off; if Discord fails, the release stays published and the run shows red ([release process](../release-process.md#the-discord-hook)).

### U0.4b · Hosts, Cloudflare & go-live readiness

**DNS move** (D-25, runbook written at G1)

- **AC15** *Given* the move of `southeastcanopy.com`'s DNS from GoDaddy to Cloudflare (free plan), *then* before the switch every record from the GoDaddy export exists at Cloudflare, with email records and `autodiscover` set to **DNS only**.
- **AC16** *Given* the switch is done, *then* email to and from an outside address works, Outlook on phone and desktop works, the website loads, and Microsoft 365 admin shows no domain issues. *Given* any of these fails, *then* putting GoDaddy's nameservers back undoes the move (nothing at GoDaddy is deleted for 2 weeks).

**Hosts**

- **AC17** *Given* the MacBook with both copies running, *then* free disk and memory are recorded, and the D-26 revisit triggers are written in the runbook.
- **AC18** *Given* the MacBook, *then* the [ADR set-up checklist](../adr/0001-stack-selection.md#set-up-checklist-u04) items done on 2026-10-11 still hold, and the remaining ones are tracked with a due point ([Q3](#owner-answers)).

**Reaching Cucumber**

- **AC19** *Given* a phone off the home Wi-Fi (mobile data), *when* staff open `cucumber.southeastcanopy.com`, *then* Cloudflare asks for their email, sends a code, and only then shows Cucumber's login page. Same for `cucumber-staging.southeastcanopy.com`.
- **AC20** *Given* an email address **not** on the allowed list, *then* no code is sent and Cucumber is never reached.
- **AC21** *Given* an outside port scan of the home internet address, *then* no port leads to either machine (the tunnel connects outward only).
- **AC22** *Given* the Owner away from home, *then* they can reach the MacBook's command line through Cloudflare Access (SSH), with port 22 still closed to the internet.

**Watching and restarting**

- **AC23** *Given* production can't be reached for 5 minutes, *then* the Owner gets an email (free outside check on `/health/`, which answers only "ok" and needs no login).
- **AC24** *Given* the MacBook restarts (power cut or update), *when* someone types the FileVault password, *then* the database, app and tunnel all come back with no other step, and staff can reach Cucumber again. Staging comes back the same way.

**Carried from U0.2a / U0.2b G5**

- **AC25** *Given* staging, *then* the full E2E suite passes against it (not only on a laptop).
- **AC26** *Given* staging, *then* the Owner walk-throughs `uat/u0_2a.sh` and `uat/u0_2b.sh` give the same results there as locally (65 of 65, 42 of 42).
- **AC27** *Given* staging, *then* a release can be rehearsed end to end: deploy a tag to staging, deploy the previous tag back (G6 "rollback rehearsed on staging").

## Out of scope

- Cucumber's own login, staff accounts and rate limiting (U0.5); roles (U0.6). Access is the outer lock only.
- Off-site backups and a full restore drill (U0.11). AC10's copy is a local safety net, not the backup.
- Sandbox data generator and reset (U6.5). Staging starts empty plus what the walk-throughs create.
- A connection pooler (PgBouncer); not needed for a handful of staff. If one is ever added, `check_projections` must stop streaming with `.iterator()` (U0.2b G4).
- An on-screen flag switch (with roles, U0.6).
- Moving the domain's registration away from GoDaddy (only DNS moves).
- Monitoring beyond the uptime check (U6.x).

## Staging host options compared (2026-10-12)

Recorded so the Owner can revisit (D-26). Hours are the Owner's hands-on
time; Claude runs the commands and writes the runbooks. Prices are rough,
checked October 2026; check again before buying.

| Option | Cost | Owner time to set up | Hardware | Downsides |
|---|---|---|---|---|
| **1. Both on the MacBook** (two separate copies) ✅ chosen for now | Free | ~30 min extra | Only what production already needs | A staging mistake or heavy test could slow production; uses ~3–5 GB of the 25 GB free disk |
| **2. MacBook + Asus with Ubuntu Server** | Free | ~2–2.5 h extra, mostly waiting | The Asus (i7-3610QM, 12 GB, 2012), a USB stick ≥ 8 GB, a network cable | A second machine to keep running; old battery, maybe a slow spinning disk |
| **3. MacBook + small cloud server for staging** | ~US$6/month | ~30 min (sign up and pay) | None for staging | A monthly bill |
| **4. Both in the cloud** (ADR-0001's first choice) | ~US$20/month | ~1 h | **None**: no UPS, Ethernet adapter, disk clean-up or FileVault restarts | Monthly bill; data in Singapore, not in the building |

**Most of the hardware effort is production on the MacBook, not staging:**
UPS for the router (~1,500–3,000 THB), USB-C Ethernet adapter (~300–800 THB),
freeing ~80 GB of disk. Only option 4 removes it.

**The Asus can't stay on Windows 10:** its security updates end 2026-10-13
and the CPU (3rd-generation i7) can't run Windows 11. If option 2 is picked,
installing Ubuntu takes one sitting: copy off anything to keep (the install
erases the disk); on the Asus, download Ubuntu Server (~3 GB) and write it to
a USB stick with Rufus (~20 min); restart and choose the USB stick from the
boot menu (Esc or F2); answer about 10 installer screens (network cable, use
entire disk, name and password, tick *Install OpenSSH server*; ~30 min).
Everything after that is done from the Mac over the network. Possible snags:
a BIOS setting to allow booting from USB; slow if it has a spinning disk.

**Domain routes** (needed for the email check in every option):

| Route | Cost | Owner time | Risk |
|---|---|---|---|
| Subdomain of `southeastcanopy.com` ✅ chosen (D-25) | Free | ~1 h together, then a day of checking email | Low but real: a missed record can interrupt email until fixed (quick undo) |
| New domain bought at Cloudflare | ~US$10/year | ~15 min | None to email or the website |

**Revisit when** (D-26): screens arrive for staff UAT (U0.10 G0), the MacBook
runs short of disk or memory, staging work slows production, or getting the
MacBook ready for real data feels like too much (then option 4). Moving
staging is the same set-up on another machine; no code changes.
