## 1. Repository layout

The real app lives at the repo root next to `docs/`. The spike stays on its
own branch and is never merged.

```
.
├── cucumber/                 Django project: settings, urls, wsgi
│   ├── core/                 shared helpers, the health page, base templates
│   ├── accounts/             staff accounts (filled in U0.5)
│   ├── references/           stages, locations, media codes… (U0.9)
│   ├── plants/  batches/  events/   domain (U0.2a, U0.2b)
│   │   ├── models.py  services.py  views.py  urls.py  admin.py
│   │   ├── templates/<app>/
│   │   └── tests/
│   └── settings.py
├── e2e/                      browser tests (Playwright)
├── scripts/                  check.sh, next_version.py, staff_notes.py (+ tests)
├── docker/postgres/init/     01-roles.sh: creates the two database roles
├── .github/workflows/        ci.yml, draft-release.yml
├── compose.yaml              local PostgreSQL 17
├── pyproject.toml  uv.lock   dependencies, tool settings
├── cliff.toml                git-cliff release-notes config
├── .env.example              every setting, no values
└── README.md                 set-up in five steps
```

- **One app per feature** (AC11), each with `services.py` for its rules
  ([ADR-0001](../adr/0001-stack-selection.md#architecture-rule-thin-views-rules-in-services)).
  U0.3 creates the apps empty apart from an `apps.py` and a `tests/` folder.
- `core` holds a **health page** (`/health/` → "ok" plus a database check),
  used by the E2E smoke test now and the uptime alert in U0.4.

## 2. Tools

| Job | Tool | Why |
|---|---|---|
| Python and packages | **uv**, Python 3.13, `uv.lock` committed | Already used in the spike; one tool installs Python and packages, same versions everywhere |
| Lint and format | **ruff** (`ruff check`, `ruff format --check`) | One fast tool for both; readable error lines (AC1) |
| Type checks | **mypy** + **django-stubs** | The standard Django type checker (AC2) |
| Tests | **pytest** + **pytest-django** + **pytest-cov** | Same as the spike; coverage fails under 80 % (AC3, AC4) |
| Frozen clock in tests | **time-machine** | Needed for the Bangkok-midnight date tests (U0.2 design §6) |
| Browser tests | **pytest-playwright**, Chromium at 375 × 812 | Runs inside the same pytest run with Django's `live_server` (AC10) |
| Release notes | **git-cliff** (run with `uvx`, from PyPI) | No third-party GitHub action and no extra install |

Versions are pinned by `uv.lock`; Dependabot proposes updates weekly (AC15).

## 3. One command: `scripts/check.sh`

```bash
uv run ruff format --check .
uv run ruff check .
uv run mypy cucumber scripts
uv run pytest            # unit + integration + e2e, coverage gate in pyproject
```

- Coverage counts `cucumber/` and `scripts/`, excluding migrations and tests;
  `fail_under = 80` lives in `pyproject.toml`, so a plain `pytest` enforces it
  too.
- The same script runs on a laptop, on the MacBook and in CI (AC7). README
  steps: install Docker and uv → `cp .env.example .env` and fill in local
  values → `docker compose up -d --wait` → `uv sync` → `scripts/check.sh`.

## 4. Settings and secrets

- **One `settings.py`** reading environment variables; no settings split.
  Locally, values come from `.env` through `uv run --env-file .env` (no extra
  library). `.env` is git-ignored; `.env.example` lists every variable with no
  values (AC13).
- **Fails closed** (AC12, U0.1 review H2):
  - `DJANGO_DEBUG` must be exactly `1` to turn debug on; missing means **off**.
  - With debug off, a missing `DJANGO_SECRET_KEY`, `DJANGO_ALLOWED_HOSTS` or
    database password stops start-up with an `ImproperlyConfigured` message
    naming the missing variable.
- `TIME_ZONE = "Asia/Bangkok"`, `USE_TZ = True`, `USE_I18N = True` (D-16).

## 5. Database roles in development, tests and CI

`docker/postgres/init/01-roles.sh` (PostgreSQL runs it on first start; CI runs
it as a step) creates:

| Role | Can | Used by |
|---|---|---|
| `cucumber_owner` | owns the database and tables, runs migrations, may create the test database | `manage.py migrate`, the test runner |
| `cucumber_app` | log in only; table rights come from U0.2a's `GRANT`s | the running app; app-user tests |

Passwords come from environment variables, never from the script.

**Tests that must run as the app user** (AC9, U0.2 re-check N4) don't use a
Django `MIRROR` alias, because Django can hand a mirror the main connection
inside a test. Instead a pytest fixture, `app_db`, opens its **own psycopg
connection as `cucumber_app`** to the test database, and **first asserts
`SELECT current_user = 'cucumber_app'`**. Tests using it are transactional
(`@pytest.mark.django_db(transaction=True)`), so the data they check is
committed and visible to that second connection. U0.3 ships the fixture with
its own test; U0.2a uses it for the permission tests.

## 6. CI: `.github/workflows/ci.yml`

Runs on every pull request and every push to `main`.

| Job | Steps |
|---|---|
| **checks** | Check out → set up uv (`astral-sh/setup-uv`) → `uv sync --locked` → `uv run playwright install --with-deps chromium` → start PostgreSQL 17 as a service container → run `01-roles.sh` against it → `scripts/check.sh` |
| **pr-title** (pull requests only) | Fails unless the title matches `^(feat\|fix\|perf\|refactor\|docs\|test\|chore\|ci)(\(.+\))?!?: .+` (AC5). The title is passed through an environment variable, never pasted into the script, so a crafted title can't run commands |

- `permissions: contents: read` at the top; nothing in CI can write to the repo.
- Every third-party action is pinned to a **full commit SHA** (with the
  version in a comment); Dependabot keeps them current.
- Cost: the free plan includes **2,000 CI minutes a month** for private repos.
  A run should take 3–5 minutes, so roughly 400 runs a month fit.
- **Merge rule** (Q1): GitHub can't block a red merge on the free plan. The
  Owner merges only with Claude, who checks both jobs are green first; the PR
  template's "Before merging" boxes record it (AC6). Merges are squash-only,
  titled by the PR (AC6a, already set on the repository).

## 7. Release tooling

- **`cliff.toml`** groups commit titles: `feat` → Added, `fix` → Fixed,
  `perf` → Faster; other types are left out of the notes.
- **`.github/workflows/draft-release.yml`**, started by hand
  (`workflow_dispatch`), with `permissions: contents: write`:
  1. `scripts/next_version.py` reads the existing tags and prints the next
     `YYYY.MM.N` in Bangkok time (first release of a month is `.1`).
  2. `uvx git-cliff --unreleased --tag <version>` writes the technical part.
  3. `scripts/staff_notes.py` lists pull requests merged since the last tag
     (`gh pr list`), takes each body's **Staff note** section, and skips
     "None".
  4. `gh release create <version> --draft --target main` with both parts.
- Both scripts are plain Python with unit tests, so they count toward
  coverage (AC14).
- **Change to the release process:** no `CHANGELOG.md` file. The list of
  GitHub Releases *is* the changelog; a committed file would need a bot commit
  to `main` on every release for no extra benefit.
  [release-process.md](../release-process.md) is updated to match.

## 8. Dependabot: `.github/dependabot.yml`

Two entries, both weekly with updates grouped into one pull request each:
`uv` (Python packages) and `github-actions`. Each Dependabot PR runs CI like
any other and follows the same merge rule (AC15).
