## 1. Repository layout

The real app lives at the repo root next to `docs/`. The spike stays on its
own branch and is never merged.

```
.
├── cucumber/                 Django project: settings, urls, wsgi
│   ├── core/                 shared helpers, the health page, base templates
│   ├── accounts/             staff accounts (filled in U0.5); minimal login template now
│   ├── references/           stages, locations, media codes… (U0.9)
│   ├── plants/  batches/  events/   domain (U0.2a, U0.2b)
│   │   ├── models.py  services.py  views.py  urls.py  admin.py
│   │   ├── templates/<app>/
│   │   └── tests/
│   └── settings.py
├── e2e/                      browser tests (Playwright) + conftest.py
├── scripts/                  check.sh, next_version.py, staff_notes.py (+ tests/)
├── docker/postgres/init/     01-roles.sh: creates the two database roles
├── .github/workflows/        ci.yml, pr-title.yml, draft-release.yml
├── compose.yaml              local PostgreSQL 17
├── pyproject.toml  uv.lock   dependencies, tool settings
├── cliff.toml                git-cliff release-notes config
├── .env.example              every setting, no values
└── README.md                 set-up in six steps
```

- **One app per feature** (AC11), each with `services.py` for its rules
  ([ADR-0001](../adr/0001-stack-selection.md#architecture-rule-thin-views-rules-in-services)).
  U0.3 creates the apps empty apart from an `apps.py` and a `tests/` folder.
- `core` holds a **health page** (`/health/` → "ok", or 503 if the database
  can't be reached), used by the E2E smoke test now and the uptime alert in U0.4.
- `accounts` ships a **minimal `registration/login.html`** so Django's
  `LoginView` has a page to show; U0.5 replaces it with the real screen.

## 2. Tools

| Job | Tool | Why |
|---|---|---|
| Python and packages | **uv**, Python 3.13, `uv.lock` committed | Already used in the spike; same versions everywhere |
| Lint and format | **ruff** (`check` + `format --check`), with the `S` (security) rules on | One tool; readable error lines (AC1); catches hard-coded passwords |
| Type checks | **mypy** + **django-stubs** (plugin set in `pyproject.toml`: `[tool.django-stubs] django_settings_module = "cucumber.settings"`) | The standard Django type checker (AC2). The plugin imports settings, so the required variables must exist (§4) |
| Tests | **pytest** + **pytest-django** + **pytest-cov** | Coverage fails under 80 % (AC3, AC4) |
| Frozen clock in tests | **time-machine** | For the Bangkok-midnight date tests (U0.2 design §6) |
| Browser tests | **pytest-playwright**, Chromium at 375 × 812 | Runs in the same pytest run with Django's `live_server` (AC10, §3) |
| Release notes | **git-cliff**, pinned: `uvx git-cliff==2.14.2` | From PyPI, no third-party action; bumped by hand (Dependabot can't see it) |

Python packages are pinned by `uv.lock`; Dependabot proposes updates weekly (AC15).

## 3. One command: `scripts/check.sh`

```bash
#!/usr/bin/env bash
set -euo pipefail
[ -f .env ] && export UV_ENV_FILE=.env    # local values if present; CI sets env itself
uv run ruff format --check .
uv run ruff check .
uv run mypy cucumber scripts
uv run pytest            # unit + integration + e2e, coverage gate in pyproject
```

- **pytest settings** in `pyproject.toml`: `pythonpath = ["."]` so `scripts/`
  imports in tests; `addopts = "--cov=cucumber --cov=scripts --cov-report=term-missing"`;
  coverage `fail_under = 80`, excluding migrations and tests. A plain `pytest`
  enforces the gate too, and a failure prints the uncovered lines (AC4).
- **E2E with `live_server`** (`e2e/conftest.py`): Playwright's sync API runs an
  event loop, so the conftest sets `DJANGO_ALLOW_ASYNC_UNSAFE=1` (tests only)
  and overrides `browser_context_args` to a 375 × 812 viewport. E2E tests use
  transactional database access.
- **README steps** (AC7): 1) install Docker Desktop and uv; 2) `cp .env.example
  .env` and fill in local values; 3) `docker compose up -d --wait` (database
  init scripts run only on an **empty** volume: if an old spike volume exists,
  `docker compose down -v` first); 4) `uv sync`; 5) `uv run playwright install
  chromium`; 6) `scripts/check.sh`.

## 4. Settings and secrets

- **One `settings.py`** reading environment variables through a single helper,
  `env("NAME")`, so a test can list every variable it reads (AC13). Locally,
  values come from `.env` via `UV_ENV_FILE` (§3); no extra library. `.env` is
  git-ignored; `.env.example` lists every variable with no values.
- **Fails closed** (AC12, U0.1 review H2):
  - `DJANGO_DEBUG` must be exactly `1` to turn debug on; missing means **off**.
  - With debug off, a missing `DJANGO_SECRET_KEY`, `DJANGO_ALLOWED_HOSTS` or
    database password stops start-up with an `ImproperlyConfigured` message
    naming the missing variable.
- **CI** sets these in the workflow's `env:` with clearly fake values
  (`ci-only-not-a-secret`), so mypy's plugin and pytest can import settings.
  They protect nothing and are labelled as such.
- `TIME_ZONE = "Asia/Bangkok"`, `USE_TZ = True`, `USE_I18N = True` (D-16).

## 5. Database roles in development, tests and CI

`docker/postgres/init/01-roles.sh` creates the roles. PostgreSQL runs it on the
first start of an empty volume; CI runs it as a step (§6). It uses `psql -v
ON_ERROR_STOP=1`, and passwords come from environment variables, passed with
`psql -v` and `:'name'` quoting, never written into the script.

| Role | Can | Used by |
|---|---|---|
| `cucumber_owner` | owns the database and tables, runs migrations, `CREATEDB` for the test database | `manage.py migrate`, the test runner |
| `cucumber_app` | log in only; table rights come from U0.2a's `GRANT`s | the running app; app-user tests |

**Tests that must run as the app user** (AC9, U0.2 re-check N4) don't use a
Django `MIRROR` alias, because Django can hand a mirror the main connection
inside a test. Instead a pytest fixture, **`app_db`**:

- depends on `django_db_setup`, takes the test database name from
  `connection.settings_dict`, and opens its **own psycopg connection as
  `cucumber_app`** in autocommit mode;
- **first asserts `SELECT current_user` = `cucumber_app`**;
- **closes the connection in teardown**, so pytest-django's flush and the
  final test-database drop aren't blocked by an open session.

Tests using it are transactional (`@pytest.mark.django_db(transaction=True)`),
so the rows they check are committed and visible to the second connection.
The fixture's own test also checks the server is PostgreSQL 17
(`server_version_num >= 170000`, AC8) and that `cucumber_app` can't create a
table. U0.2a uses the fixture for its permission tests
([U0.2 design §6](u0.2-design.md#6-migration-plan) updated to match).

## 6. CI workflows

**`ci.yml`**: runs on every pull request and every push to `main`.

1. The service container **`postgres:17`** starts first, with a `pg_isready`
   health check. (Service containers start before checkout, so they can't
   read the init script.)
2. Check out (`persist-credentials: false`), set up uv (`astral-sh/setup-uv`),
   `uv sync --locked`, `uv run playwright install --with-deps chromium`.
3. Run `docker/postgres/init/01-roles.sh` against the service with
   `PGHOST=localhost`, `PGUSER`, `PGPASSWORD` and the fake CI passwords.
4. `scripts/check.sh`.

- `permissions: contents: read`; nothing in CI can write to the repo.
- `timeout-minutes: 15`, and a `concurrency` group that cancels an older run
  of the same pull request, so a stuck browser can't use up the free minutes.
- Cost: the free plan includes **2,000 CI minutes a month** for private repos;
  a run should take 3–5 minutes.

**`pr-title.yml`**: its own small workflow on `pull_request` with
`types: [opened, edited, synchronize, reopened]`, so **renaming a PR re-runs
it** without re-running the test suite (AC5). The title is passed through an
environment variable, never pasted into the script, and must match
`^(feat|fix|perf|refactor|docs|test|chore|ci)(\(.+\))?!?: .+`.

- Every third-party action is pinned to a **full commit SHA** (version in a
  comment); Dependabot keeps them current.
- **Merge rule** (Q1): GitHub can't block a red merge on the free plan. The
  Owner merges only with Claude, who checks every job is green first; the PR
  template's "Before merging" boxes record it (AC6). Merges are squash-only,
  titled by the PR (AC6a, already set on the repository).

## 7. Release tooling

- **`cliff.toml`** groups commit titles: `feat` → Added, `fix` → Fixed,
  `perf` → Faster; other types are left out.
- **`.github/workflows/draft-release.yml`**, started by hand
  (`workflow_dispatch`), with `permissions: contents: write, pull-requests:
  read`, checkout with **`fetch-depth: 0`** (full history and tags), and
  `GH_TOKEN: ${{ github.token }}`:
  1. Record the current `main` commit as `SHA`. Everything below uses `SHA`,
     so a pull request merged during the run isn't half-included.
  2. `scripts/next_version.py` prints the next `YYYY.MM.N` in Bangkok time.
     It reads **tags and existing draft releases** (so running twice can't
     reuse a number), accepts only `^\d{4}\.\d{2}\.\d+$`, compares `N` as a
     number (`.10` after `.9`), zero-pads the month (`2026.01.1`), and takes
     "now" as a parameter so tests don't need to fake the clock.
  3. `uvx git-cliff==2.14.2 <last-tag>..SHA --tag <version>` writes the
     technical part to a file.
  4. `scripts/staff_notes.py` takes the pull request numbers from the `(#N)`
     endings of the squash commits in `git log <last-tag>..SHA` (so notes and
     commits always match), reads each body with `gh pr view N --json body`,
     keeps the **Staff note** section and skips "None". Output goes to a file.
  5. **Create the tag `<version>` at `SHA`** (GitHub API), then
     `gh release create <version> --draft --verify-tag --notes-file <file>`.
- **Deploy uses that tag**, so what is deployed is exactly what the notes
  describe; publishing later doesn't move it. **To abandon a draft:**
  `gh release delete <version> --cleanup-tag --yes`.
- PR text only ever goes into files read by scripts, never into `${{ }}`
  inside a `run:` step, so a crafted PR body can't run commands.
- **No `CHANGELOG.md`:** the list of GitHub Releases is the changelog; a
  committed file would need a bot commit to `main` every release.
  [release-process.md](../release-process.md) is updated to match.

## 8. Dependabot: `.github/dependabot.yml`

Two entries, `uv` and `github-actions`, both weekly, grouped into one pull
request each, with **`commit-message: prefix: chore, include: scope`** so the
titles read `chore(deps): …` and pass the title check (AC5, AC15). Each
Dependabot PR runs CI and follows the same merge rule.
