# U0.10a · Shell & kit — Design note (G1)

**Spec:** [u0.10-spec.md](u0.10-spec.md) (U0.10a = AC1–AC26) · **Status:** G1 in progress · 2026-10-28 · draft; architect review pending; Owner questions open
**Stack:** Django 5.2 LTS + PostgreSQL 17 + htmx 2 + Tailwind 4 / daisyUI 5 ([ADR-0001](../adr/0001-stack-selection.md)).

U0.10a gives every page the same look and the same safety catches. It adds:

1. **A CSS build step** with no Node: the Tailwind standalone CLI and
   daisyUI's plugin files compile one stylesheet when the image is built, in
   CI and locally (§3).
2. **htmx and three small static scripts**: the double-tap guard, the "Not
   confirmed" timeout and the failure wording. No inline JavaScript anywhere,
   checked by a template scan (§4).
3. **A Content Security Policy** on every answer (§5).
4. **A new base page**: a bottom bar on a phone, a side menu on a desktop,
   both built from the U0.6 matrix (§6).
5. **The kit**: form, field, dropdown, date, list, detail, empty, error and
   busy, as Django form renderers, includes and a few template tags (§7).
6. **The server's own limits** and what a person sees when one is hit (§8).
7. **Refusals that read well**: the CSRF page, one log line per 4xx, no
   gunicorn control-socket line (§9).
8. **The seven existing pages moved onto the kit**, with the U0.5 G4 fixes
   and Python-side translation (§10).

**No data model change, no migration, no audit event, no new matrix row**
(unless [Q4](#15-owner-questions) adds the practice page's). U0.10b's list
pages are not designed here; §19 lists what they reuse.

## 3. CSS build (AC1, AC2)

### 3.1 Versions and checksums

| Tool | Version (start) | How it arrives | Checked by |
|---|---|---|---|
| Tailwind CSS standalone CLI | 4.3.x | Downloaded from `github.com/tailwindlabs/tailwindcss/releases/download/v<version>/tailwindcss-<platform>` by `scripts/css.py` | SHA-256 per platform (`linux-x64`, `linux-arm64`, `macos-arm64`, `macos-x64`) in `scripts/css.py`; a mismatch stops the build |
| daisyUI plugin | 5.7.x | `daisyui.mjs` and `daisyui-theme.mjs` from the daisyUI release, **committed** under `core/css/vendor/` | SHA-256 of each file against the release's published files, in `core/tests/test_assets.py` |
| htmx | 2.0.x | `htmx.min.js` from the npm package `htmx.org`, **committed** under `core/static/core/vendor/` | SHA-384 against the hash htmx publishes for that version, in `test_assets.py` (AC2) |

The spike ran daisyUI 5.7.47, Tailwind 4.3.3 and htmx 2.0.11. G3 pins the
latest patch of each that has been out at least two weeks, and records
version, source address and hash in one place per tool (the constants above).
Dependabot can't see these three; they are checked by hand at each phase
release gate (carry-forward, §19).

The Tailwind binary (about 100 MB, one per platform) is never committed. The
daisyUI files (two text files) and htmx (one) are committed so the image
build fetches only one thing, and a review can read what changed.

### 3.2 Source CSS

`cucumber/core/css/source.css` is the only stylesheet anyone edits:

```css
@import "tailwindcss" source(none);
@source "../../*/templates";        /* every app's templates */
@source "../kit.py";                /* classes the kit's Python hands to templates */

@plugin "./vendor/daisyui.mjs" { themes: false; }
@plugin "./vendor/daisyui-theme.mjs" {
  name: "cucumber";
  default: true;
  color-scheme: light;
  /* daisyUI's `light`, with: */
  --color-primary: <Cucumber green, Q6>;
  --color-primary-content: <white or near-black, whichever passes 4.5:1>;
  --size-field: 0.275rem;          /* buttons and inputs 44 px tall (AC7) */
  --size-selector: 0.275rem;
}

@layer components {
  /* 16 px text in every input so iOS doesn't zoom (AC7) */
  .input, .select, .textarea { font-size: 1rem; }
  /* the practice banner's long and short wording; the dock's safe area; the list cards (§7.6) */
}
```

- **Fonts:** the system font stack (Tailwind's `--font-sans`). No font files,
  nothing to download, and phones already carry Thai glyphs (D-16).
- **Icons:** inline SVG through `{% icon "home" %}` (`kit/icons/*.svg`, from
  Heroicons, MIT). Inline SVG is markup, not script, so the CSP allows it.
- **Classes live in templates** (and `kit.py`'s small class table). The
  `@source` lines are the whole list of places; a class built from pieces
  (`"btn-" + kind`) would be missed by Tailwind, so the kit spells classes out.
- **No `style=` attribute and no `<style>` element** anywhere (the CSP blocks
  both, §5; the scan in §4.4 refuses them).

### 3.3 Where it is built

`scripts/css.py` (standard library only, like the other server scripts):

- `fetch`: download the pinned CLI for this machine (`platform.system()`,
  `platform.machine()`) into a cache folder (`$CUCUMBER_TOOLS`, default
  `.cache/tools/`), check its SHA-256, mark it executable. Skips when the
  cached file's hash already matches.
- `build`: `fetch`, then `tailwindcss -i cucumber/core/css/source.css -o
  cucumber/core/static/core/cucumber.css --minify`. Fails on a non-zero exit.
- `watch`: the same with `--watch`, for local work.

**Image** (build stage only; the run stage gets the compiled file through
`COPY --from=build /app /app`, never the CLI):

```dockerfile
COPY scripts/__init__.py scripts/css.py scripts/
ENV CUCUMBER_TOOLS=/opt/tools          # outside /app, so the run stage never copies it
RUN /app/.venv/bin/python -m scripts.css fetch     # cached layer: re-runs only when css.py changes
COPY . .
RUN /app/.venv/bin/python -m scripts.css build
RUN … collectstatic …                  # as today
```

The image is built on each server by the deploy command, which already pulls
from Docker Hub, ghcr.io and PyPI; GitHub release downloads are one more host
at build time. Nothing is fetched at run time (AC2).

**CI:** `scripts/check.sh` gains `==> CSS (tailwind)` before the tests, so
the E2E tests see the real stylesheet. The `check` job caches `.cache/tools/`
with `actions/cache` (pinned by SHA, key = hash of `scripts/css.py`). The
`image` job builds as above.

### 3.4 Retiring the old stylesheet

The compiled file keeps the old address, `core/cucumber.css`, so `{% static
'core/cucumber.css' %}` and the existing finder test still hold. G3 deletes
the hand-written file in the same commit that adds the build, and
`.gitignore` gains `cucumber/core/static/core/cucumber.css`. Its few rules
that aren't daisyUI's (the practice banner's long / short wording) move into
`source.css`. A test fails if git tracks that path (so nobody re-adds a
hand-written copy).

### 3.5 Local work: one command

```
uv run python -m scripts.dev
```

starts `scripts.css watch` and `manage.py runserver` together, prints both
outputs, and stops both on Ctrl-C (or when either exits). `scripts/check.sh`
builds the CSS once, so tests never need the watcher. README's local steps
gain this line.

## 4. Scripts (AC2, AC3, AC12–AC14)

### 4.1 htmx

`core/static/core/vendor/htmx.min.js`, loaded with `defer` from `kit/_head.html`,
along with our three scripts. Its settings come from a meta tag (htmx reads
it itself; it is data, not script, so the CSP allows it):

```html
<meta name="htmx-config" content='{"timeout": 20000, "allowEval": false,
  "allowScriptTags": false, "includeIndicatorStyles": false,
  "selfRequestsOnly": true, "historyCacheSize": 0,
  "responseHandling": [{"code": "204", "swap": false}, {"code": "[23]..", "swap": true},
                       {"code": "422", "swap": true}, {"code": "...", "swap": false, "error": true}]}'>
```

- `timeout` is `HTMX_TIMEOUT_MS` from settings (20 000, §8.3), so a test can
  shorten it.
- `allowEval: false`: htmx never runs text as code (event filters, `js:`
  values, `hx-on`); with the CSP it couldn't anyway.
- `includeIndicatorStyles: false`: otherwise htmx adds a `<style>` element,
  which the CSP refuses. The indicator classes are in `source.css`.
- `allowScriptTags: false`: a swapped answer never runs a `<script>`.
- `historyCacheSize: 0`: no page copies in the browser's storage (staff data
  on a shared phone).
- `422` is swapped: a form the service refused comes back with its messages
  next to the fields (§11.2).

### 4.2 `forms.js`: one tap, one request (AC12)

- **Plain forms** (no `hx-post`): on the first `submit` the form gets
  `data-sending`, the submit button gets `aria-disabled="true"` and the
  `is-sending` class (a spinner, "Saving…" read out); any further `submit`
  of that form is cancelled (`preventDefault`). The button is **not**
  `disabled`: a disabled submitter drops its `name=value` from the request.
- **Back:** on `pageshow` with `event.persisted` (the browser's back-forward
  cache) every form loses `data-sending` and its button works again.
- **HTMX forms** carry `hx-sync="this:drop"` (a second request while one is
  sending is dropped) and `hx-disabled-elt="find button[type=submit]"` (htmx
  disables the button and re-enables it when the request ends, however it
  ends). The kit's form template writes both, so no page can forget them.
  `forms.js` leaves these forms alone.
- No timer on plain forms: a plain POST that never answers keeps the browser's
  own loading bar; the person can reload. Every plain form in U0.10a is safe
  to send twice (a second login, password or "add account" gets an ordinary
  answer or refusal). Phase 1 data entry uses HTMX forms with an operation id
  (carry-forward).

### 4.3 `requests.js`: when a request goes wrong (AC13, AC14)

One banner region in the base page, `#request-trouble` (`role="alert"`),
holds the hidden messages, whose words come from the template (so they are
translated, D-16). The script only shows one of them:

| htmx event | Shown | Wording (spec) |
|---|---|---|
| `htmx:timeout` (no answer in 20 s) | not-confirmed | "Not confirmed: check your signal and tap Save again. If it was saved, you'll see *Already saved*." |
| `htmx:sendError` (no connection) | offline | "You're offline or the signal dropped. Nothing was sent." |
| `htmx:responseError`, 503 | busy | "Busy, please try again." |
| `htmx:responseError`, 403 with `Cucumber-Trouble: stale-page` | stale-page | "This page was open too long. Reload it and try again." + Reload |
| `htmx:responseError`, 403 otherwise | no-access | "You don't have access to this page." |
| `htmx:responseError`, other 4xx / 5xx | server-error | "Something went wrong on our side. Tap Save again; if it keeps happening, tell the Owner." |
| `htmx:beforeRequest` | (hides the banner) | |

It never says "not saved" for a timeout (AC13). Save works again in every
case because htmx re-enables the button when the request ends. A 401 with
`HX-Redirect` (login or forced password change, U0.5 §5) is followed by htmx
before any of this.

### 4.4 No inline JavaScript (AC3)

`core/tests/test_no_inline_script.py` reads every template under
`cucumber/*/templates/` and refuses:

- a `<script>` with anything between its tags, or without `src="{% static …%}"`;
- any `on…=` attribute, `hx-on`, `hx-on:…`, `hx-vals` / `hx-vars` with `js:`
  or `javascript:`, an `hx-trigger` with a `[…]` filter, `href="javascript:`;
- any `style=` attribute or `<style>` element (CSP, §5).

Like U0.9's scan, it has self-tests showing each refused pattern is caught
and the allowed `<script src=… defer></script>` passes. Python that builds
HTML (`format_html`) only fills in names, never markup with scripts; the CSP
is the second line, and the E2E watcher (§5.3) the third. No Alpine.js
(spec out of scope).

## 5. Content Security Policy (AC4)

### 5.1 The header

```
Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self';
  img-src 'self' data:; font-src 'self'; connect-src 'self'; form-action 'self';
  frame-ancestors 'none'; frame-src 'none'; object-src 'none'; base-uri 'none'
```

- `img-src data:`: daisyUI draws a few marks (checkbox tick, select arrow) as
  `data:` SVGs in the CSS. G3 checks the compiled CSS; if none remain,
  `data:` is dropped.
- `form-action 'self'`: forms post only here.
- `frame-ancestors 'none'` with the existing `X-Frame-Options: DENY`.
- No `report-uri`: there is nowhere to send reports, and the E2E watcher
  finds breaks first (§5.3).

### 5.2 How it is set ([Q5](#15-owner-questions))

Django 5.2 has no CSP support (Django 6.0 adds `SECURE_CSP` and
`ContentSecurityPolicyMiddleware`).

| | **a) Own middleware** (recommended) | b) `django-csp` 4 |
|---|---|---|
| Size | ~25 lines + tests: build the header once from a settings dict, set it on every answer that has none | A package, its settings and its own middleware |
| Fits Cucumber | One fixed policy; no nonces (no inline scripts, AC3) | Nonces, report-only mode, per-view decorators: none needed |
| Later | The setting is written in Django 6's shape (`SECURE_CSP = {"default-src": ["'self'"], …}`), so moving to Django 6.2 LTS deletes our class and keeps the setting | Remove the package and port its settings |

Placed straight after `SecurityMiddleware`, so error pages, the CSRF page and
the busy page carry it too. WhiteNoise's static answers don't need it.

### 5.3 How E2E catches a break

`e2e/conftest.py` gains an autouse fixture that listens to the page's
console and `pageerror` events. Chromium writes every CSP refusal to the
console ("Refused to … because it violates the following Content Security
Policy directive"). At the end of each browser test, any such line, and any
uncaught script error, fails the test with the line. So every existing and
new E2E test checks the policy on every page it opens, locally and on
staging.

### 5.4 Staging first

The header ships in the code and is on wherever that code runs: staging from
G5, production from G6 (Q6 a). Staging matters because Cloudflare sits in
front of it, not because the code differs: Cloudflare features that rewrite
pages (Email Address Obfuscation on the Staff pages, Rocket Loader, Web
Analytics' injected beacon) would break under the policy. G5 runs the full
E2E suite against staging; any break names the feature, and the fix is a
Cloudflare setting (switched off for both hostnames), recorded in the
runbook. Production gets the same settings before the G6 deploy.

## 6. Base page and menu (AC1, AC5–AC7)

### 6.1 Layout

- `kit/_head.html`: charset, `viewport` (`width=device-width,
  initial-scale=1, viewport-fit=cover`), title with `[Practice]` on staging,
  `cucumber.css`, the htmx config meta, four `<script defer>`.
- **`base.html`** (moved to `core/templates/`; the name stays, so pages and
  tests that look for it are unchanged):
  1. the practice banner (as today, first in the body; U0.5 AC21 kept);
  2. **top bar**: "Cucumber" (link to Home) and the page title; on the right,
     "Signed in as **Jade**" (small); a reserved slot where U1.1's search box
     goes (empty in U0.10a);
  3. `#request-trouble` (§4.3) and Django's messages (`alert` per message,
     `role="status"`);
  4. `main` with the page;
  5. **the menu**: on a phone, a bar fixed to the bottom of the screen
     (daisyUI `dock`), up to four items, each icon + word, 64 px tall plus
     the phone's safe area (`env(safe-area-inset-bottom)`). `main` has
     bottom padding of the same height, so nothing hides behind the bar. On
     a screen 1024 px or wider (`lg`) the same items are a side menu
     (daisyUI `menu`) on the left and the bottom bar is hidden.
- **`kit/bare.html`**: the same head and banner, the top bar with the name

### 6.2 Menu items (AC5)

```python
# accounts/menu.py

    label: str                 # gettext_lazy
    url_name: str
    permission: Permission     # the matrix row that decides who sees it
    icon: str
    marks: frozenset[str]      # url names on which this item is "current"
```

- **Who sees an item:** `may(role, item.permission)`, from the same
  `Standing` the page check used. No second list of roles.

  checks that the view's `cucumber_permission` label is the item's
  `permission`, so the menu can never show a page that refuses the person,
  or hide one that lets them in.
- **Current page:** the item whose `marks` holds
  `request.resolver_match.url_name` gets `aria-current="page"` and daisyUI's

- **Lists** joins with U0.10b (`EDIT_REFERENCE_LISTS`), when its page exists.

- **No role:** a person with no role is allowed only `OWN_ACCOUNT`, so they

- **Pages that skip `RoleRequired`** (404, CSRF page): the context processor
  reads `standing(request.user)` itself when the person is signed in and

  The 500 and busy pages show no menu (§6.1).
- **Two taps from Home** (AC6): every page is a menu item or one tap from one

## 7. Components (AC8–AC11, AC19–AC21)

The kit is Django's own machinery where Django has it, plus a few includes.

### 7.1 Forms and fields (AC11)

- `FORM_RENDERER = "cucumber.core.kit.KitRenderer"`: a `TemplatesSetting`
  renderer with `form_template_name = "kit/form_fields.html"` and
  `field_template_name = "kit/field.html"`. Then `{{ form }}` in any page
  renders every field the kit's way: label, the widget with the kit's classes
  (by `field.widget_type`), help text, the error under the field
  (`aria-describedby`, `aria-invalid`), and the form's own errors on top.
- `kit/field.html` replaces `accounts/_field.html`. Its `help_text|safe`
  gets the comment U0.5 G3 asked for: help text comes from code (Django's
  password rules write HTML lists), never from what a person typed.
- **A refusal next to its field** (AC11): the view catches `Refused` and calls
  `form.add_error(field_for(refusal), refusal.message)`; the bound form keeps
  every answer. Each form that can be refused has a small `REFUSAL_FIELDS`
  table (rule → field), as the Deactivate form already does; a rule not in it
  goes to the form's own errors.
- `kit/form.html` wraps a form: `<form>`, the CSRF token, `{{ form }}` and the
  Save button; for an HTMX form also `hx-post`, `hx-sync="this:drop"`,
  `hx-disabled-elt`, `hx-target="this"` and `hx-swap="outerHTML"`. Pages use
  `{% include "kit/form.html" with form=form save=_("Save") htmx=True %}`.
- **Save button** (`kit/_submit.html`): full width on a phone, primary colour,
  a hidden spinner shown while sending (`is-sending` for plain forms,
  `htmx-request` for HTMX ones), and "Saving…" for screen readers.
- NUL characters (U0.9 G4 L5): Django's `CharField` already refuses a NUL
  (`ProhibitNullCharactersValidator`) with "Null characters are not
  allowed."; that message is Django's own, translated by Django.

### 7.2 Dropdowns from the lists (AC8)


### 7.5 The date field (AC10)

[Q1](#15-owner-questions) a): the date is a dropdown of the eight days it may
be: today and the seven before, in Bangkok time.

```
Date   [ Today · Tue 28 Oct          ▾ ]
       Week 2026-W44
```

- `core/dates.py`: `bangkok_today()` (`timezone.localdate()`, `TIME_ZONE` is
  Asia/Bangkok), `iso_week(day) -> "2026-W44"` (`day.isocalendar()`), and
  `ENTRY_WINDOW_DAYS = 7`, moved here from `events/models.py`, which imports
  it (the number in the database rule doesn't change, so no migration).
- `PickedDateField`: a `TypedChoiceField` whose choices are the eight days,
  made when the form is made: "Today · Tue 28 Oct", "Yesterday · Mon 27 Oct",
  then "Sun 26 Oct" … (Django's date formats, translated). It cleans to a
  `date`. A posted date outside the eight ("tomorrow", a hand-edited form)
  is refused with the `event_within_7_days` / `event_not_in_future` wording.
- **The week** sits under the field in an `<output>`; each option carries
  `data-week`, and `date-week.js` copies the picked option's week into the
  output. The server works out every week; the script does no date maths.
  Without the script the week shown is the first option's; what is saved is
  the date (SOP §4: the week is always worked out, never stored).
- A form opened before midnight and saved after still saves the day picked;
  the service's own check (`event_within_7_days`, Bangkok date of
  `recorded_at`) is the rule (AC10: "the field only stops honest mistakes").
- The time of day an entry gets is Phase 1's (U1.4 carry-forward).

## 8. The server's own limits (AC15)

### 8.1 Values

| Limit | Value | Why |
|---|---|---|
| `lock_timeout` | 5 s (as today) | a save waiting on another save's lock |
| `statement_timeout` | **10 s** | the slowest query at 10× data is a few ms (U0.9 G5); 10 s is a stuck query, not a slow one |
| `idle_in_transaction_session_timeout` | **10 s** | a transaction left open while Python does something else; the longest real gap is password hashing, under 1 s |
| htmx `timeout` | **20 s** | above all three, so the server has answered "Busy" before the phone gives up |
| gunicorn `--timeout` | 60 s (as today) | the worker is restarted after this |
| Cloudflare | 100 s | its own limit (502/524) |

Set in `DATABASES["default"]["OPTIONS"]["options"]` as `-c lock_timeout=5s -c
statement_timeout=10s -c idle_in_transaction_session_timeout=10s`, built from
three named constants. They apply to every connection, migrations included:
a future migration that needs longer writes `SET LOCAL statement_timeout = 0`
itself, in that migration, where a reviewer sees it (as `lock_timeout` today).

### 8.2 What the person sees

`core/busy.py`:

```python
LIMITS = {"55P03": "lock_timeout", "57014": "statement_timeout",
          "25P03": "idle_in_transaction_session_timeout"}

def busy_limit(error: BaseException) -> str | None:
    """The limit that stopped this request, by PostgreSQL error code, or None."""
```

- **`BusyAnswer` middleware** (`process_exception`): when the view's error is
  one of the three, it writes one line and answers 503 with `503.html`.
  It closes the database connection when the server ended it (`25P03`), so
  the session save that follows reconnects instead of failing.
- **Fallback:** `server_error` (`handler500`) asks `busy_limit` about the
  exception being handled, so a limit hit outside the view (a middleware's
  query, the session save) also answers 503 Busy, not 500.
- **One log line** (logger `cucumber.core`, WARNING):
  `busy limit=statement_timeout account=12 path=/staff/3/role/`. The
  request is marked, so the log filter (§9.2) drops Django's own "Service
  Unavailable" line for it.
- **Nothing is saved:** each limit cancels the statement or the session, so
  the transaction rolls back. A resend of an HTMX save is safe: Phase 1's
  operation ids answer "Already saved." (U0.2b).

### 8.3 htmx's timeout

`HTMX_TIMEOUT_MS = 20_000` in settings, written into the htmx config meta
(§4.1); AC13's wording on timeout (§4.3).

## 9. CSRF page, logs, gunicorn (AC16–AC18)

### 9.1 The CSRF page (AC16)

`CSRF_FAILURE_VIEW = "cucumber.core.views.csrf_failure"`:

- renders `csrf.html` on the kit: "This page was open too long. Reload it
  and try again." and a **Reload** button, status 403;
- Reload goes to the page the form was on: the `Referer`, if
  `url_has_allowed_host_and_scheme` accepts it (Django sends a same-origin
  Referer, `Referrer-Policy: same-origin`), else Home. Not the form's
  address: Staff buttons are POST only and would answer 405;
- for an HTMX request it adds `Cucumber-Trouble: stale-page`, so
  `requests.js` shows the same words in the banner (§4.3);
- the reason Django gives is never shown or logged by Cucumber; Django's one
  `django.security.csrf` line ("Forbidden (CSRF token from POST incorrect.):
  /accounts/login/") stays the only line, and it holds no token.

### 9.2 One line per refusal (AC17)

`core/logs.py`: a filter on the console handler.

| Record | Becomes |
|---|---|
| `django.request` 403 | dropped: Cucumber's own `page refused` line covers every 403 (below) |
| any `django.*` record for a 4xx (404, 405, 400, CSRF) | kept, `exc_info` removed: one line |
| a request marked busy (§8.2) | dropped: the `busy` line covers it |
| 500 and other 5xx | kept with the traceback |

- `RoleRequired` raises `PageRefused` (a `PermissionDenied`) after its
  `page refused account=… permission=…` line (unchanged, tested).
- `permission_denied` (`handler403`) logs `page refused account=… rule=…
  path=…` for any **other** 403 (a service's `NotAllowed`), so every 403 has
  exactly one Cucumber line.

### 9.3 gunicorn (AC18)

The `CMD` gains `--no-control-socket` (gunicorn 25.1+ makes the socket under
`$HOME/.gunicorn/`; the home isn't writable). Nobody uses `gunicornc`.

### 10.4 Translation (AC26)

- **Templates:** the check in `test_base_page.py` moves to
  `core/tests/test_translation.py` and covers every template in every app
  (the error pages' words get marked).
- **Python:** every text a person reads goes through gettext:
  - `MESSAGES` values are marked `gettext_noop` (found by `makemessages`) and
    `message_for` returns `gettext(…)` of them; a refusal's message is
    therefore translated when it is raised;
  - form labels, help texts and error messages, `messages.*()` texts and

  `error_messages=` values. A plain string literal there fails the test,
  with file and line. It has self-tests, like U0.9's scan. A second test
  runs `message_for` for every rule under a fake translation (a
  `NullTranslations` that wraps each text in `⟦…⟧`, activated for the test)
  and finds every message wrapped.
- Only English ships (no `.po` files yet, D-16).

## 17. Risks

- **Tailwind misses a class** written only in Python or assembled from
  pieces: the `@source` list (§3.2) and the kit spelling classes out; the
  E2E size checks (44 px, 16 px) fail if a class is missing.
- **Cloudflare rewrites pages** and the CSP blocks it: found on staging at
  G5 (§5.4).
- **htmx or daisyUI change behaviour** in a patch: pinned, hashed, updated by
  hand with the E2E suite (§3.1).
- **The 10 s limits** on a future slow migration or import: the migration
  sets its own (§8.1); U1.10 (V.2 import) decides at its G1.
