## Timing note (10× today)

Today: about 10 staff (Owner, 2026-10-19), each on up to 3 phones or
computers. Tested at 10× on a throwaway database on this Mac (PostgreSQL 17
in Docker), through Django's test client so every middleware and the real
password hasher run: **100 accounts, 300 open sessions, 3,000 ended ones not
yet cleared, 5,000 wrong passwords in the last day and 5,000 older**. 30 runs
each. Run it yourself: `bash uat/timing_10x.sh` (now also times logging in,
`scripts/timing_login.py`).

| Action | Median | p95 |
|---|--:|--:|
| First login after a quiet week (clears ended sessions) | 166 ms | 166 ms |
| Log in, right password | 131 ms | 138 ms |
| Log in, wrong password | 121 ms | 129 ms |
| Open a page, signed in | 3.8 ms | 5.6 ms |
| Staff page, all accounts | 62 ms | 67 ms |
| Give someone a new password (ends their sessions) | 121 ms | 129 ms |

Logging in is ~0.13 s on purpose: checking a password is deliberately slow
work (Django's hasher), so guessing passwords is slow too. Every page opened
afterwards adds under 6 ms for the login checks. Everything is well under
the half-second a phone user would notice. The same run's inventory numbers
match the U0.4b baseline.
