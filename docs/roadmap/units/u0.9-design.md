## 2. Data model and migrations

### 2.1 Tables and rules

**`container_types`** (new, model `ContainerType`):

| Column | Type | Rule |
|---|---|---|
| `code` | text, primary key | `container_types_code_format`: `^[a-z][a-z0-9_]{1,31}$`, e.g. `magenta_box` ([Q2](#10-owner-questions)) |
| `label` | text, not null | `container_types_label_valid` (below) |
| `active` | boolean, `db_default` true | switch-off needs an `archive` reason (trigger, §2.3) |

There is no sort order: the list is shown by label (§3.1).

**New checks on the existing lists** (model constraints, so `makemigrations
--check` keeps them in step):

| Rule | Table | Check |
|---|---|---|
| `media_codes_code_format` | `media_codes` | `code ~ '^[A-Z][A-Z0-9]{2,9}$'`: a capital letter, then 2 to 9 capitals or digits (`M001`, `G002`, `R001`) |
| `<table>_label_valid` | `stages`, `media_codes`, `locations`, `container_types` | `label = btrim(label) AND label <> '' AND char_length(label) <= 100` |
| `genera_name_valid` | `genera` | the same, on `name` |

The patterns live in `lists.py` as constants, as U0.8 did for `SKU_PATTERN`.
The models import them. Python checks them with `re.fullmatch`, so a trailing
newline can't pass (U0.8 G4 LOW, `$` before `\n`).

**"Already in the list in any letter case" (AC6).** Media codes and genus codes
are capitals only and container type codes are lower case only, so two codes
that differ only by letter case can't both pass the format. The primary key
is therefore enough (`<table>_pkey`). A test pins this.

**What stays as it is:** genus codes (`genera_code_format`, three capitals;
`genera_code_not_id_prefix`, U0.8 AC5a); `genera_name_unique`;
`stages_sort_order_unique`; `stages_active_needs_sort_order`;
`<table>_code_rename`, `<table>_no_delete`, the audit and reason triggers on
the five U0.2a lists.

### 2.2 `references 0006_container_types`

- `CreateModel(ContainerType)` with its two checks.
- `AddConstraint` for `media_codes_code_format` and the five label checks.
- **Pre-check first:** `refuse_rows_that_dont_fit(apps, schema_editor)` lists
  every existing media code that fails the new format and every label or name
  that fails the label rule, and stops with them named instead of a bare
  constraint error (U0.8 review L3). Today's seeds all pass. No writer has
  existed, so production holds only seeds.
- `SET LOCAL lock_timeout = '5s'`. Each `AddConstraint` takes a short
  exclusive lock on a small table that `batches` and `events` point at. The
  app is stopped for the deploy, as for U0.7 and U0.8 (release runbook §4), so
  nothing should be waiting. The timeout makes a surprise fail cleanly.
- **Undo:** drop the checks; drop the table. It refuses while
  `container_types` has a row, so it runs only after `0008`'s undo, which
  refuses first when the Admin has added one (§2.4, review M5).

### 2.3 `references 0007_container_type_rules`

`RunSQL`, built from `db_rules` helpers that already exist:

- `no_delete`, `code_rename`, `audit(Audited("container_types", "code"))`,
  `reason_required(SwitchOff("container_types", "active", (("false",
  "archive"),)))`, `truncate_noticed`.
- `GRANT SELECT, INSERT, UPDATE ON container_types TO cucumber_app`. The
  default privileges give only `SELECT, INSERT` (core 0003), and an explicit
  grant doesn't depend on who made the table (U0.8 review L2).
- **Two owner-only triggers** (new function `cucumber_owner_only`, below):
  `stages_order_fixed` on `stages` (no insert, no change of `sort_order`) and
  `locations_fixed` on `locations` (no insert, no change of `active`).

**Why the triggers go here and not in `REFERENCE_LISTS`.** `core 0006` builds
its triggers from `db_rules.REFERENCE_LISTS`, `AUDITED_TABLES`, `SWITCH_OFFS`
and `TRUNCATE_NOTICED_TABLES`. Adding `container_types` to them would change
what `core 0006` makes on a fresh database, which `db_rules.py` forbids (G4
review M2 of U0.2). It would also break, because the table doesn't exist when
`core 0006` runs. So `db_rules` gains separate U0.9 constants
(`U09_AUDITED`, `U09_SWITCH_OFFS`, `U09_TRUNCATE_NOTICED`, `OWNER_ONLY`, and
`U09_FUNCTIONS` for the new function), and
`expected.py` lists each trigger with the migration that makes it
(`U09 = "references.0007_container_type_rules"`). `EDITABLE_TABLES` in
`lists.py` is the app's own list of the six editable tables. `reasons` isn't
one of them ([spec Q7](u0.9-spec.md#owner-answers)).

**`cucumber_owner_only()`.** It runs as the caller, with `search_path` fixed,
and its body is pinned by md5, like the U0.7 and U0.8 functions. Its body goes
in `U09_FUNCTIONS`, **not** in `AUDIT_FUNCTIONS` or `ID_FUNCTIONS`: `core 0006`
and `core 0007` loop over those two, so adding to them would change those
migrations (review L3).
`TG_ARGV[0]` is the rule name and the other arguments are the columns:

```sql
-- OWNER_ONLY_BODY: BEFORE INSERT OR UPDATE; TG_ARGV[0] rule, then columns
BEGIN
  IF session_user = 'cucumber_owner' THEN
    RETURN NEW;  -- a migration, with its own G0 (spec AC5, AC9)
  END IF;
  IF TG_OP = 'INSERT' THEN
    RAISE EXCEPTION '% rows are added by a migration only', TG_TABLE_NAME
      USING ERRCODE = 'restrict_violation', CONSTRAINT = TG_ARGV[0];
  END IF;
  FOR i IN 1 .. TG_NARGS - 1 LOOP
    IF (to_jsonb(NEW) -> TG_ARGV[i]) IS DISTINCT FROM (to_jsonb(OLD) -> TG_ARGV[i]) THEN
      RAISE EXCEPTION '%.% is changed by a migration only', TG_TABLE_NAME, TG_ARGV[i]
        USING ERRCODE = 'restrict_violation', CONSTRAINT = TG_ARGV[0];
    END IF;
  END LOOP;
  RETURN NEW;
END
```

```sql
CREATE TRIGGER stages_order_fixed BEFORE INSERT OR UPDATE ON stages
  FOR EACH ROW EXECUTE FUNCTION cucumber_owner_only('stages_order_fixed', 'sort_order');
CREATE TRIGGER locations_fixed BEFORE INSERT OR UPDATE ON locations
  FOR EACH ROW EXECUTE FUNCTION cucumber_owner_only('locations_fixed', 'active');
```

- **Why the database and not only the service.** Owner Q5 says the order and
  the two locations carry rules: "stage ≥ P4" uses the sort order (U5.2), and
  every Lab batch needs a stage (`batch_lab_needs_stage` names `lab`). No
  writer takes a sort order, so the service refusal guards only the `add`
  call. The trigger also closes raw SQL as `cucumber_app`, the same way
  `code_rename` does for codes.
- **Only `cucumber_owner` is let through**, as in U0.8 §5.1. Migrations and the
  test suite run as the owner, so tests of the database refusal use `app_db`.
- **A BEFORE INSERT trigger fires even when `ON CONFLICT DO NOTHING` would skip
  the row** (review L4). So any helper that seeds `stages` or `locations` as
  `cucumber_app` is refused. The ones that exist (`core/tests/stock.py`,
  `events/tests/test_concurrency.py`, `scripts/timing_10x.py`) run as the
  owner, so they are unaffected. G2 pins the refusal.
- Trigger order on `stages` is alphabetical: `stages_code_rename`, then
  `stages_order_fixed`, then `stages_reason_required`. None of them reads what
  another one sets.
- Switching on a reserved stage (`P3`, `T1`, `C0`) is already refused by
  `stages_active_needs_sort_order`: a reserved stage has no place in the order.
  The service gives the message first (§7).
- **Undo:** drop the seven triggers and the function; revoke the grant.

`expected.py` gains the seven triggers, the function and the
`container_types` grant (`ADD_CHANGE`). The guard check already fails on a
table it doesn't know, so `container_types` must be there. That is about 9
more protections (122 → about 131); G3 gives the exact number.

### 2.4 `references 0008_labels_and_seed` (AC1, AC8)

One `RunPython`. It first checks that the System account exists and stops
naming it if not, so a missing account can't stop the migration halfway with
`audit_actor_required` (review L5; `AS_SYSTEM_SQL` is used here for the first
time). Then it runs `db_rules.AS_SYSTEM_SQL` (System, `via = 'migration'`,
U0.7 review M4), so every row it changes or adds writes an audit row as
System. The settings last for the migration's own transaction. These tables are already audited on production, so a
history that starts with "added by migration" is the true one.

| Change | Rows |
|---|---|
| **Insert stage `S0`**: label `Seed`, `sort_order 0`, `default_subculture_days` null, active | 1 audit `insert` |
| Stage labels | `P0` Sterilization / new species introduction · `P1` Multiplication · `P2` Growth · `A1` Acclimatization (hardening off) · `P4` Growth maturity (potted plants) · `P3` Transport · `T1` Digital content · `C0` Clean. 8 audit `update` rows (`label` before and after) |
| Media code labels | **unchanged**: each label stays its code (`M001` … `R001`), as seeded ([Q1](#10-owner-questions), Owner 2026-10-26). They already pass `media_codes_label_valid`. The Admin gives real labels later through the U0.10 list page. No audit rows |
| Container types ([Q2](#10-owner-questions)) | `flask_250ml` 250 ml flask · `magenta_box` Magenta box · `pot_4in` 4-inch pot · `grow_bag` Grow bag · `jar` Jar · `disposable_cup` Disposable cup · `tray` Tray. All active, 7 audit `insert` rows |

**The S0 sort order.** `P0` is 1 today, so `S0` takes **0**. That keeps
`stages_sort_order_unique` and moves no other row, as SOP §3 already shows
(order 0). The insert runs as the owner, so `stages_order_fixed` lets it
through. Code that assumes `P0` comes first:

- **App code: none.** Nothing reads `min(sort_order)` or treats `P0` as the
  start. The projection takes the stage from the events, not from the order.
- **Tests:** `references/tests/test_reference_tables.py::test_active_stages_run_p0_p1_p2_a1_p4`
  expects `P0 P1 P2 A1 P4`. G2 changes it to start with `S0` (a changed
  existing test, named at G2). `test_reserved_stages_are_inactive_with_no_sort_order`
  and the "no subculture days" test still pass. The test helpers insert `P2`
  with `ON CONFLICT DO NOTHING` and `P9` at 99, so they don't clash.
- **UAT script:** `uat/u0_2a_walkthrough.py:427` checks `P0 P1 P2 A1 P4`. It
  changes at G3 to `S0 P0 P1 P2 A1 P4`.

**Undo** (rolls back in its own transaction, as System):

1. Refuses, saying to restore the copy instead, while:
   - any batch or event uses `S0`;
   - any audit row on one of the codes it changed is **newer than the first
     row `0008` wrote** (by `id`). That is a later change by the Admin. Rows
     from before U0.9 (staging walkthroughs, test set-up) don't count
     (review M5);
   - `container_types` holds a code `0008` didn't seed, or `media_codes` or
     `genera` hold one that wasn't seeded. Otherwise `0008` would undo and
     then `0006` would refuse, leaving a half-undone state (review M5).
2. Puts the stage labels back to their codes (audited updates).
3. Deletes `S0` and the seven container types with `<table>_no_delete`
   switched off for that one statement, as `references 0004`'s undo does.
   `batches.stage_code` and `events.stage_to` are deferred foreign keys to
   `stages`, so it first sets those constraints `IMMEDIATE`, by name, and runs
   the delete in a savepoint, exactly as `0004` does
   (`0004_reason_lists.py:103-107`); otherwise `ENABLE TRIGGER` fails with
   "pending trigger events" (review L1).
4. The list tables' audit trigger doesn't fire on DELETE, so the undo writes
   one `delete` audit row for each row it removes, by hand, as System
   (U0.7 §5.4 style). The trail then reads true.

### 2.5 Run order and rollback

Run order: `references 0006` → `0007` (depends on `core 0007`) → `0008`
(depends on `accounts 0007`, for System). Undo is the reverse: `0008` →
`0007` → `0006`, and is rehearsed on staging at G6. No undo loses data
anyone entered: each one refuses when there is some. **Going back to
`2026.10.5` still means restoring the pre-deploy copy**: the older code
doesn't know these migrations, so the deploy refuses to go back (as since
U0.7).

## 3. Service API (Python; no HTTP at U0.9)

### 3.1 `references/lists.py` (no database)

```python
class ListName(StrEnum):
    STAGES = "stages"
    MEDIA_CODES = "media_codes"
    LOCATIONS = "locations"
    GENERA = "genera"
    CONTAINER_TYPES = "container_types"
    ACTIONS = "actions"  # fixed (§4)
    COUNT_UNITS = "count_units"  # fixed (§4)


class Change(StrEnum):
    ADD = "add"
    LABEL = "label"
    SWITCH_OFF = "switch_off"
    SWITCH_ON = "switch_on"


@dataclass(frozen=True)
class ListRules:
    name: ListName
    allowed: frozenset[Change]
    refused_as: str  # the rule for a change not allowed
    code_pattern: str | None  # None: no codes added
    code_rules: tuple[str, ...]  # checked in order; genera has two
    order: str  # "sort_order", "code", "label" or "fixed"
```

| List | Add | Label | Off / on | Not allowed → | Code format | Order |
|---|:-:|:-:|:-:|---|---|---|
| stages | — | ✅ | ✅ | `stages_order_fixed` | — | sort order (AC2) |
| locations | — | ✅ | — | `locations_fixed` | — | code (`lab`, `nursery`) |
| media codes | ✅ | ✅ | ✅ | — | `media_codes_code_format` | code (`G001` … `R001`) |
| genera | ✅ | ✅ (name) | ✅ | — | `genera_code_format`, then `genera_code_not_id_prefix` | code |
| container types | ✅ | ✅ | ✅ | — | `container_types_code_format` | label |
| actions, count units | — | — | — | `list_fixed` | — | as in `fixed.py` |

This is spec Q5 a). Media codes and genera are listed by code, because staff
know `M001` and `PHL`. Container types are listed by label, because their
codes are only a key.

### 3.2 Readers (`references/reading.py`)

```python
@dataclass(frozen=True)
class Item:
    code: str
    label: str  # a genus's name
    active: bool
    sort_order: int | None  # stages only


def active_items(name: ListName) -> tuple[Item, ...]:
    """A dropdown's items: active only, in the list's order (AC2, AC13). One query."""


def item(name: ListName, code: str) -> Item | None:
    """One item by code, switched off or not (AC13: old records still read)."""


def check_active(name: ListName, *codes: str) -> None:
    """For a write: every code is on the list and active, or Refused.

    list_item_unknown, then list_item_inactive. One query for all codes.
    """


def stage_at_or_after(code: str, than: str) -> bool:
    """Is stage `code` at or after `than` in the sort order (AC2)?

    False for a stage with no place in the order (reserved).
    """
```

- Fixed lists come from `fixed.py` and run no query. `check_active` on a fixed
  list means "is one of the values".
- **No permission check on reading.** Everyone signed in reads the lists
  ([spec Q2](u0.9-spec.md#owner-answers)), and the page checks sign-in (U0.6).
- Not cached. The lists are a few rows each. U0.10 may hold `active_items` for
  the length of a request.
- **No bulk "every item" reader yet** (review L7). AC22 names three reads, and
  nothing in U0.9 calls a fourth. When U0.10's history pages need labels for
  many rows at once, it adds `all_items(name) -> dict[str, Item]` here.
- `check_active` takes no lock. A switch-off that commits during a save is a
  gap of milliseconds, accepted as for a role change (U0.6 §4.1). The save's
  foreign key lock (`FOR KEY SHARE`) and the switch-off's row lock (`FOR NO
  KEY UPDATE`) don't conflict, so neither waits.

### 3.3 Writers (`references/services.py`)

```python
def add_item(
    by: User, name: ListName, code: str, label: str, *, via: str | None = None
) -> Item: ...
def edit_label(
    by: User, name: ListName, code: str, label: str, *, via: str | None = None
) -> Item: ...
def switch_off(
    by: User,
    name: ListName,
    code: str,
    reason: Reason | None,
    *,
    via: str | None = None,
) -> Item: ...
def switch_on(
    by: User, name: ListName, code: str, *, via: str | None = None
) -> Item: ...
```

Every writer does the same steps, in this order, and writes nothing until
step 5:

1. **`require(by, EDIT_REFERENCE_LISTS)`** → `NotAllowed` (`account_not_active`,
   `role_not_allowed`), a 403 (AC17).
2. **Is the change allowed on this list?** If not: `Refused(rules.refused_as)`
   (`list_fixed`, `stages_order_fixed`, `locations_fixed`) (AC5, AC9, AC15,
   AC16).
3. **Inputs.** `code` and `label` are trimmed. The code must fit its
   pattern (`<table>_code_format`; genera also `genera_code_not_id_prefix`).
   The label must pass `<table>_label_valid` (genera: `genera_name_valid`).
   `switch_off` calls `require_reason(reason, "archive")` (`reason_required`,
   `reason_wrong_list`, `reason_note_too_long`), before any transaction opens
   (U0.7 §6). Nothing here is upper-cased for the person: a code written
   differently from the format is refused (AC6).
4. **`with database_refusals(), audited(by, via=via, reason=reason):`**
5. Inside: lock the row (`select_for_update(no_key=True)`), or for `add` check
   the code is free. Then check the rules that need the database:
   `list_item_unknown` (no such code); `<table>_pkey` (code taken, on add);
   `genera_name_unique` (another genus has that name);
   `stages_active_needs_sort_order` (switching on a reserved stage). Then
   save and return the new `Item`.

- A database refusal that slips past the service (two Admins adding the same
  code at once) comes back as `Refused` with the same rule name, through
  `database_refusals`. The service and the database use **the same names**,
  so a test can ask for one name from both paths (as U0.7 did with
  `reason_required`).
- **No change, no row.** Switching off an item already off, switching on one
  already on, or saving the same label changes no column. The audit trigger
  then writes nothing (U0.7 §4.1 step 3) and the writer returns the item as it
  is. A reason is still required for a switch-off, even one already off, so
  the call always means the same thing.
- **`via`:** `app` by default (`audited`'s default). The G5 walkthrough calls
  the writers from `manage.py shell` with `via=ssh_via("manage.py shell")`, so
  the trail doesn't say `app` for a shell session.
- **No lock order to keep.** A writer locks one list row and nothing else.
- The writers import `require` and `audited` by name, so a test can replace
  them (U0.6 §14) and check the order: `require` first, then `audited`
  entered, then the save (AC20).

### 3.4 How Phase 1 writers call it

Any writer that saves a code a **person picked** calls `check_active` for it
after its permission check and before it writes. In the event writers the
place matters (review H1). It goes **after `start_operation`**, so a resend of
an operation that is already saved still gets "Already saved" (`save_once`)
even if its medium has been switched off since. It also goes **after the
entries are built**, because a split builds its entries only then:

```python
# events/services.py, write_operation (today :167-169)
standing = require(recorded_by, Permission.LOG_WORK)
start_operation(operation_id, recorded_by)
entries = entries() if callable(entries) else entries
if picked:  # False only for split (below)
    check_picked(entries)  # check_active per list: media, stage_to, location
...
# write_correction (today :528-529): after start_operation and find_event,
# on the values that differ from the event's current effective values
```

**Carried values are marked, not guessed.** `write_operation` gains
`picked: bool = True`. `split` passes `picked=False`, because every value in
its entries is copied from the parent (`split_entries`: `location_code` and
`stage_to`). The test doesn't rely on the entries being a function. `close`
names no list code.

What counts as picked, and what doesn't:

| Value | Checked? | Why |
|---|---|---|
| an entry's `media_code`, `stage_to`; a new batch's `location_code` (`save_operation`) | ✅ | picked in the form |
| a Correction's `media_code` or `stage_to` **that differs from the event's current effective value** (`current_values`, inside `checked_values`) | ✅ | picked again |
| a Correction's values equal to the current ones, whether left out or sent again (a page may pre-fill them) | — | restated, not picked: a Correction that changes only the quantity of an event whose medium is switched off still works (review M4) |
| a split's location and stage (`split_entries` copies the parent's; `picked=False`) | — | carried, not picked: a batch in a stage that has since been switched off can still be split |
| `batches.stage_code` set by the projection | — | worked out from events |
| the target genus (`reclassify_genus`); a new plant's genus (U1.1) | ✅ | picked |
| a batch's `container_type`, `count_unit` (U1.3) | ✅ | picked |

**This is why `list_item_inactive` has no database rule.** A trigger on
`batches` or `events` can't tell a picked value from a carried one. It would
refuse the split and the Correction above, which the spec keeps working ("records
already pointing at it are untouched", AC13). The database still refuses an

## 4. Fixed lists: in code (AC15, AC16)

`references/fixed.py`. It imports only `django.db.models`, no app models, so
the projection can import it without a cycle:

```python
class Action(models.TextChoices):  # moved from events/models.py, values unchanged
    INTAKE = "intake"
    ...  # the 14 actions; labels stay Django's own ("Stage Change")
    VOID = "void"


class CountUnit(models.TextChoices):  # D-22 as proposed (spec Q6)
    PLANT = "plant", "Plant"
    VESSEL = "vessel", "Vessel"
    MG = "mg", "mg"
```

**In code, not a table.** These values are what stock sums, the event shapes
and the projection are written against. A row someone could add would mean
nothing to that code. In code, the database still holds them through each
table's check (`event_action_valid` exists; U1.3 adds
`batch_count_unit_valid` from `CountUnit.values`). Changing a value changes
that check, so `makemigrations --check` in CI asks for a migration, and that
migration needs its own G0 (AC15). A table would add a sixth protected list,
grants and guards for no gain. `events/models.py` keeps `Action` importable
(`from cucumber.references.fixed import Action`), so callers don't change.
Migrations store the list of choices, not the class, so moving it needs no
migration. **The labels stay exactly as they are** (Django's automatic ones,
e.g. "Stage Change", as `events 0001` records them). New sentence-case labels
would change `choices`, and `makemigrations --check` would ask for an
`AlterField` (review M2). Friendlier wording on screen is U0.10's.

**The refusals:**

| Who tries | How | Refused by |
|---|---|---|
| anyone, through the services | `add_item` / `edit_label` / `switch_off` / `switch_on` on `ACTIONS` or `COUNT_UNITS` | `list_fixed` (after the permission check, so a Tech still meets `role_not_allowed` first) |
| a writer saving an event | an action not in the list | `event_action_valid` (exists) |
| a writer saving a batch (U1.3) | a count unit not in the list | `batch_count_unit_valid` (U1.3) |
| a developer | edits `fixed.py` | the pinning tests (the exact 14 and the exact 3), then `makemigrations --check` |

If D-22 changes the units at U1.3 G0, `CountUnit` changes there with its
check. No batch has a count unit before U1.3 ([spec Q6](u0.9-spec.md#owner-answers)).

## 6. Audit events (AC19–AC21)

No new audit code. The U0.7 trigger writes every row; U0.9 only adds
`container_types` to the audited tables (`core/audit.py` `AUDITED`, and the
trigger in §2.3).

| Change | `action` | `before` | `after` | `reason_code`, `note` | Person, `via` |
|---|---|---|---|---|---|
| `add_item` | `insert` | — | the whole row (`code`, `label`/`name`, `active`) | — | the Admin, `app` |
| `edit_label` | `update` | `{label: old}` (genus: `name`) | `{label: new}` | — | the Admin, `app` |
| `switch_off` | `update` | `{active: true}` | `{active: false}` | the `archive` code and the trimmed note | the Admin, `app` |
| `switch_on` | `update` | `{active: false}` | `{active: true}` | — (spec Q3) | the Admin, `app` |

| `0008` undo | `update`; `delete` written by hand (§2.4) | the row | — | — | System, `migration` |

- Every row has `table_name` (the list's table), `row_pk` (the code), `at`
  (the database clock) and `db_user` (set by `audit_log_stamp`), as for
  every audited table.
- One change, one row, in the change's own transaction. If the row can't be
  written, the change isn't saved (AC19). A change with nobody named is
  refused by `audit_actor_required` (AC20).
- A refused change writes nothing (AC21). Steps 1–3 of §3.3 run before the
  transaction opens, and a refusal in step 5 rolls back everything,
  the audit row included.
- **Reason handling:** only `switch_off` takes a reason. `audited(reason=…)`
  sets it, and `cucumber_reason_required` checks it again in the database
  (AC11). `switch_on` passes none: the trigger asks a reason only when moving
  *into* an off value.

## 8. One place (AC22)

An AST scan, like U0.8's `test_one_place`, over `cucumber/**/*.py` (leaving
out `cucumber/references/`, migrations and tests), plus a text scan of the

docstrings or comments, and fails on a literal equal to:
