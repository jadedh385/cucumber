# U0.8 · ID sequence service — Spec (G0)

**Unit:** [U0.8](../phase-0-foundations.md#u08--id-sequence-service) · **Size:** S ·
**Deps:** U0.2a (passed G6) · **Decisions:** none blocking
**Status:** G0 in progress · drafted 2026-10-23; Q1–Q2 answered by Jade (Owner) 2026-10-23; waiting for Owner sign-off

## Goal

Every plant, SKU, batch and event gets an ID that people can read, say, type and
print, and that is never handed out twice, even when several people save at the
same moment.

Most of the numbering already exists (U0.2a, U0.2b):

| ID | Example | Where the number comes from today | Missing |
|---|---|---|---|
| Plant | `PLT-0042` | `plants.id` (database identity) | formatting, reading back |
| Batch | `BAT-00117` | `batches.id` (database identity) | formatting, reading back |
| Event | `EVT-01502` | `events.id` (database identity) | formatting, reading back |
| SKU | `PHL005` | highest SKU ever issued for the genus + 1, genus row locked (`issue_next_sku`) | proof under load, growing past 999 |
| Batch number | `PHL001 · B003` | highest `plant_seq` for the plant + 1, plant row locked (`lock_plants`) | formatting, proof under load |

So U0.8 is mostly **one place that turns numbers into IDs and back**, plus the
tests that prove no ID is ever issued twice. No screens: Phase 1 shows the IDs.

## User stories

| S1 | Tech | every plant, batch and event to have a short ID I can read off a label or a screen | I can find it again and tell others which one I mean |

## Acceptance criteria

**Formats** (SOP §3)

- **AC1** *Given* a plant, batch or event, *then* its ID is the prefix, a dash and its number padded with zeros: `PLT-` to 4 digits, `BAT-` and `EVT-` to 5 (`PLT-0042`, `BAT-00117`, `EVT-01502`).
- **AC2** *Given* a number longer than the padding (plant 10 000, batch 100 000), *then* the ID grows (`PLT-10000`) and is never cut short. Two different numbers never give the same ID.
- **AC3** *Given* a batch, *then* its short name is the plant's current SKU, or its `PLT-` ID if it has no SKU, then `· B` and its batch number padded to 3 digits (`PHL001 · B003`, `PLT-0042 · B003`). From 1 000 it grows (`B1000`). The `BAT-` ID never changes; the short name can (promotion, genus reclassification), so labels use `BAT-` (U0.2 design §2).
- **AC4** *Given* an SKU, *then* it is the 3-letter genus code and its number padded to 3 digits (`PHL005`). From 1 000 it grows (`PHL1000`); no SKU already issued ever changes ([Q2](#owner-answers)). The database format check (`plant_sku_format`, and the same on `skus`) allows 3 or more digits, and a number with a needless leading zero (`PHL0005`) is refused, so one number has one spelling.
- **AC4a** *Given* a list of SKUs in one genus, *then* it is sorted by the number, so `PHL1000` comes after `PHL999`, not after `PHL100`.

**Reading an ID back** (lookup)

- **AC5** *Given* a typed `PLT-`, `BAT-` or `EVT-` ID, *then* it finds the record whatever the letter case, with or without the dash, and with or without the leading zeros (`plt-42`, `PLT0042`, `PLT-0042` all find plant 42).
- **AC6** *Given* a typed SKU, current or former, *then* it finds the plant, whatever the letter case (`phl005`). A former SKU still finds the plant it was issued to (U0.2 Q1, `find_by_sku`).
- **AC7** *Given* a typed batch short name (`PHL001 · B003`, `PHL001 B3`, `PHL001-B003`), *then* it finds the batch, using the plant's current or former SKU.
- **AC8** *Given* text that isn't a valid ID (wrong prefix, letters in the number, empty), *then* the lookup finds nothing and says so; it never raises an error to the screen and never guesses.

**Never issued twice** (SOP §3: "global, sequential, never reused or restarted")

- **AC9** *Given* 100 creates of the same kind at the same moment (plants, batches, events), *then* there are 100 different IDs. Gaps are allowed: a save that fails can use up a number.
- **AC10** *Given* 100 promotions or reclassifications into the **same genus** at the same moment, *then* there are 100 different SKUs, numbered on from the highest SKU ever issued for that genus, with no gaps. Other genera are not held up.
- **AC11** *Given* 100 batches created for the **same plant** at the same moment (subculture, split, intake), *then* they get 100 different batch numbers, with no gaps.
- **AC12** *Given* a voided or retired plant, a voided batch, or a voided event, *then* its ID and batch number are never given to anything else (nothing is deleted, D-07). A former SKU is never issued again (U0.2 Q1).
- **AC13** *Given* an insert that supplies its own `id` for a plant, batch or event (as `cucumber_app`, by the ORM or raw SQL), *then* it is refused, so no one can take a number ahead of the sequence. The one exception is the owner-run V.2 import (U1.10), which keeps the `PLT-` numbers already in use ([Q1](#owner-answers)) and then moves the number generator past the highest one.
- **AC14** *Given* the database's number generator for plants, batches or events is behind the highest ID already in its table (a bad restore, a manual reset), *then* `cucumber_check_guards` (U0.7 AC15) reports it and the deploy stops.

**One place**

- **AC15** *Given* the code, *then* formatting and reading back of every ID live in one module, and the SKU and batch number are issued only through it. A test fails if another module builds an ID string itself.

## SOP and deck sources

- SOP §3 IDs: formats, "global, sequential, never reused or restarted"; variant SKUs are not issued IDs.
- SOP §5 rule 1 and U0.2 Q1: static SKU, never reused; a new SKU only on genus reclassification, the old one kept as a former SKU.
- U0.2 design §2 (display IDs come from `id`; the formatter must not cut long numbers), §2.3 (`plant_seq` with the plant row locked).
- Card gate focus: G2 concurrency test.

## Out of scope

- **Variant SKUs** (`PHL001-5`, `PHL001-V`): built from the SKU and the selling unit, not issued (SOP §3). They arrive with selling units (D-23, U1.3).
- **Screens and search boxes.** U0.8 gives the services; U1.1 (plant search) and later units put them on a page.
- **Labels and QR codes** (U4.8, D-18).
- **Choosing when an SKU is issued** (promotion rules, U1.2). U0.8 only issues the number.
- **The V.2 import itself** (U1.10). `PLT-` numbers are in use today ([Q1](#owner-answers)), so U0.8 only makes sure the import can keep them and the numbering continues after the highest.
- **Operation ids.** They are UUIDs made by the form (issue #4), never shown to people.

## Size

**S.** One ID module (format, read back, issue SKU and batch number), the
existing `issue_next_sku` and `lock_plants` moved behind it, the refusal of
caller-chosen ids, the wider SKU format check, one check added to
`cucumber_check_guards`, and the concurrency tests. One small migration (AC4,
AC13). No new tables, no screens.
