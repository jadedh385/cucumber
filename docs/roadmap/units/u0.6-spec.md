# U0.6 · Roles & permissions — Spec (G0)

**Unit:** [U0.6](../phase-0-foundations.md#u06--roles--permissions) · **Size:** M ·
**Deps:** U0.5 (passed G6) · **Decisions:** D-03 (Resolved), D-07 (Resolved)
**Status:** G0 passed · 2026-10-19 · signed off by Jade (Owner); Q1–Q4 answered, all as recommended

## Goal

Give every account one of the four roles from SOP §7 (D-03) and make Cucumber
enforce them **on the server**, in two places:

1. **Pages:** every web address checks the role before it shows or saves
   anything.
2. **Services:** the code that writes plants, batches and events checks the
   person saving, not only the page that called it (U0.2b G4 security H1/H2).
   Until now the services trust their caller (U0.2 design §3.1).

Today only the Admin role exists (U0.5 made the `admin` group), and a new
account has no role, so it sees only the home page. After U0.6 the Admin gives
each account a role on the Staff page, and the master permission matrix lives
in one place in the code. Every later unit adds its own rows to that matrix
at its G1, and the tests for each row are generated from it, so a new page
can't ship without a permission test for every role.

No plant, batch or event screens exist yet (Phase 1). So the page part of
U0.6 covers today's pages (home, password, Staff pages); the service part
covers every service that already writes data.

## Acceptance criteria

**Roles**

- **AC1** *Given* the database after U0.6's migration, *then* four roles exist as Django groups: `admin`, `supervisor`, `tech`, `read_only` (U0.2 design §2.7). U0.5's `admin` group is kept; the other three are added the same way (`get_or_create`, safe to run again).
- **AC2** *Given* any account, *then* it has **at most one** role ([Q1](#owner-answers)). Giving a new role replaces the old one in the same save. An account with no role sees only the home page and its own password page, as in U0.5.
- **AC3** *Given* the matrix below, *then* it is written **once**, in one Python module, and both the pages and the services read it. Nothing else decides who may do what.

Rows marked "later" go into the matrix now so the later unit only adds its page
and service, and the generated tests (AC14) cover them from the first commit.
"Void or correct" spells out SOP §7's "Review / correct / void others'
events"; the card's row said only "add corrections".

**Giving and removing roles** (Owner 2026-10-12, on the card)

- **AC4** *Given* the Admin on the Staff page, *when* they add an account, *then* they must also pick its role (no default). *When* they open an account, *then* they can change its role or remove it (no role).
- **AC5** *Given* a role change, *then* it applies on the person's **next request**: no session, cache or page keeps the old role (roles are read from the database on every request, as `has_role` does today; a test changes a role between two requests of one session).
- **AC6** *Given* a role change, *then* one plain log line records who changed it, for which account, the old role, the new role, and when (as U0.5 AC30: account ids only). U0.7 moves these lines into the audit trail.
- **AC7** *Given* the only active Admin, *then* Cucumber refuses to remove or change their Admin role, as it already refuses to deactivate them (`account_last_admin`). The Admin also can't change their **own** role ([Q3](#owner-answers)), as they can't deactivate themselves (U0.5 AC24).
- **AC8** *Given* a user who isn't the Admin, *when* they open the role page or send its form, *then* it is refused and nothing changes.
- **AC9** *Given* the SSH command `cucumber_admin` (U0.5 AC29), *then* it still makes the first Admin and rescues the Owner; it gives the Admin role and nothing else.

**Pages**

- **AC10** *Given* a signed-in user without the right role, *when* they open a page or send its form, *then* the answer is **403** with a plain "You don't have access to this page." on the base page (through the translation function, D-16), and nothing is saved. An HTMX request gets 403 with no page swap.
- **AC11** *Given* the home page, *then* it shows only the links the person's role may use (the Staff link only for the Admin, as now). Hiding a link is a convenience; AC10 is the rule.

**Services** (U0.2b G4 security H1/H2, Owner 2026-10-12)

- **AC12** *Given* any service that saves plants, batches or events (`save_operation`, `split`, `close`, `void`, `correct`, `review`, `reclassify_genus`, `issue_next_sku` and those added later), *then* it checks the person saving against the matrix itself and refuses by rule name (e.g. `role_not_allowed`), even when called directly, not from a page. Read Only and no role can save nothing.
- **AC13** *Given* a person saving, *then*:
  - a **deactivated** account can't save anything, even with a session still open (`account_not_active`);
  - a **Tech** can enter work only under their own name: `staff_id` must be themselves (N7);
  - a **Supervisor** can't void or correct an event that they did (`staff_id`) or saved (`recorded_by`) (D-03, U0.2 M5); review keeps rule 10 as built;
  - **Undo** (a Void by someone who may not void, i.e. a Tech) is allowed only on an event they saved (`recorded_by`), within 10 minutes of its `recorded_at`, measured by the database clock; after that it is refused (`undo_too_late`) and a reviewer fixes it;
  - a **resent** `operation_id` returns the original result only to the person who saved it first; anyone else is refused (U0.2b G4 security L3).

**Tests generated from the matrix** (card: G2 gate focus)

- **AC14** *Given* the matrix, *then* the role × action tests are **generated** from it, not written by hand: for every row and every role (plus "no role" and "deactivated"), one test that it is allowed or refused, for the page and for the service.
- **AC15** *Given* any URL pattern in Cucumber (the U0.5 AC17 walk), *then* a test fails if it isn't linked to a row of the matrix or to the short public list (login, `/health/`, static files). A new page can't ship without a permission row.

**Carried in from the U0.5 G4 review** (MEDIUM and LOW items on the card)

- **AC16** *Given* an email locked **and** the lab's address over its 50-try limit, *when* the Admin presses "Lift the lock", *then* both are lifted, so the page's "can log in again" is true (M6).
- **AC17** *Given* `add_account` or `cucumber_admin`, *then* the service itself refuses a name over 150 characters (today only the form does).
- **AC18** *Given* the database refuses an `add_account` save, *then* the refusal is read by its rule name, so only a taken email says "That email is taken".
- **AC19** *Given* an email typed when adding an account, *then* it is Unicode-normalised (NFKC) before it is stored, as the login form already does.

## Out of scope

- **The audit trail table** (U0.7). Role changes go to the app log (AC6) and
  U0.7 moves them in. U0.7's own acceptance repeats the Undo rule; the U0.6
  tests will already cover it.
- **Plant, batch, event, reference-list, Zoho and dashboard screens** (Phase 1
  and later). Their rows are in the matrix now; each unit adds its page.
- **Per-location or per-batch permissions** (e.g. a Tech only for the Nursery).
  Roles apply to all of Cucumber.
- **Database-level role checks.** Cucumber connects as one database user
  (`cucumber_app`); roles are checked in the app. The database rules from
  U0.2a and U0.5 (no deletes, `auth_user` checks) stay as they are.
- **Django's own per-model permissions** (`auth_permission`). Groups stand for
  roles; the matrix is Cucumber's own.
- **The on-screen feature-flag switch** ([Q4](#owner-answers)). The SSH
  command `cucumber_flag` stays.
- **2FA** (U6.1) and **rate limits on every page** (U6.6).
