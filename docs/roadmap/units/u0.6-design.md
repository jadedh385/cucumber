## 2. The matrix (`accounts/permissions.py`, AC3)

One module holds every "who may do what". Pages, services, templates and the
generated tests all read it; nothing else decides (AC3).

```python
class Role(StrEnum):  # the group names (U0.2 design §2.7)
    ADMIN = "admin"
    SUPERVISOR = "supervisor"
    TECH = "tech"
    READ_ONLY = "read_only"


class Permission(StrEnum):  # one per matrix row
    LOG_WORK = "log_work"
    ...


@dataclass(frozen=True)
class Row:
    permission: Permission
    label: str  # the row's words, as in the spec
    allowed: frozenset[Role | None]  # None = an account with no role
    narrowed_by: str = ""  # the service rule that narrows a "✅ except" cell
    refused_as: str = "role_not_allowed"  # the rule a refused role meets
    built: Built = Built.LATER  # PAGES, SERVICES, BOTH or LATER


MATRIX: tuple[Row, ...] = ...


def may(role: Role | None, permission: Permission) -> bool: ...
```

The rows, exactly the spec's matrix with the home page added to the
signed-in row:

| Permission | Allowed | Narrowed by | Built |
|---|---|---|---|
| `LOG_WORK` (register plant, create batch, log events) | Admin, Supervisor, Tech | N7 for a Tech (§4.2) | services |
| `SPLIT_CLOSE_LOSS` (split, close, record loss, quarantine) | Admin, Supervisor, Tech | N7 for a Tech | services |
| `RELEASE_QUARANTINE` | Admin, Supervisor, Tech | N7 for a Tech | services |
| `UNDO_OWN` (within 10 minutes) | Admin, Supervisor, Tech | `undo_*` rules (§4.2) | services |
| `REVIEW_EVENTS` | Admin, Supervisor | rule 10, as built | services |
| `VOID_OR_CORRECT` | Admin, Supervisor | `fix_own_entry` for a Supervisor | services |
| `REVIEW_VOIDS` | Admin | | services |
| `ENTER_FOR_OTHERS` (N7) | Admin, Supervisor | | services |
| `PLANT_LIFECYCLE` (promote, demote, retire, void, assign SKU) | Admin | | services (SKU only) |
| `RECLASSIFY_GENUS` | Admin | | services |
| `ZOHO_LINK` | Admin | | later |
| `EDIT_REFERENCE_LISTS` | Admin | | later |
| `SEE_ZOHO_REFS` | Admin | | later |
| `VIEW_DASHBOARDS` | all four roles | | later |
| `MANAGE_USERS` (incl. giving roles) | Admin | | pages + services |
| `OWN_ACCOUNT` (home, log out, own password) | all four roles **and no role** | | pages |

**"✅ except" cells** stay ✅ in the matrix. The exception is a rule in the
service (`narrowed_by` names it), because it depends on the event, not only on
the role. The generated tests (§10.1) test the plain cell; each narrowing rule
has its own tests (AC13).

**Roles are steps** (spec Q1): every role allows everything the one below it
does, except where a row says otherwise. The matrix doesn't compute that; each
row lists its roles in full, so a row reads the same as the spec's table.

`has_role` stays in `accounts/services.py`, and the `ADMIN`, `SUPERVISOR` and
`TECH` constants become `Role` members (a `StrEnum` equals its string, so
`"admin" == Role.ADMIN`).

## 3. How a page is checked (AC10, AC11, AC15)

```
request ─► SessionLimit ─► LoginRequired ─► PasswordChangeDue ─► RoleRequired ─► the view
                                                                    │
                     public (login, /health/)  ◄── login_not_required │
                     the view's row allows the role? ── no ──► 403 page
                     the view has no row ───────────────────────► 403 page + error log
```

### 3.1 Labelling a page

```python
@allowed_for(Permission.MANAGE_USERS)
@require_safe
def staff_list(request): ...
```

`allowed_for` only puts the row on the view (`view.cucumber_permission`), the
same way Django's `login_not_required` marks a view. Django's own decorators
copy a view's attributes when they wrap it, so the order doesn't matter.
`LogoutView` is labelled in `urls.py`: `allowed_for(OWN_ACCOUNT)(LogoutView.as_view())`.

**`RoleRequired`** (after `PasswordChangeDue`, in `process_view`):

1. A view marked `login_not_required` goes through (login, `/health/`).
   Static files never get here (WhiteNoise).
2. It reads the person's **standing** from the database: active or not, and
   their role (§4.1). One query per request, kept on the request
   (`request.standing`) so the templates don't ask again. The next request
   reads it again, so a role change applies on the person's next page (AC5).
3. A view **with no row** is refused (403) and logs an error naming the view.
   The URL walk test (AC15) catches this in CI before it ships; in production,
   forgetting a row closes the page instead of opening it.
4. If `may(role, row)` is false: 403, and nothing runs, so nothing is saved
   (AC10).

A deactivated person never reaches this: Django already signs them out on
their next request (U0.5 §2.1), so they go to the login page.

### 3.2 The 403 page

`handler403 = "cucumber.core.views.permission_denied"`, rendering
`403.html` on the base page: "You don't have access to this page." and a link
home, both through `gettext` (D-16), with the Practice-data banner. Status 403.
It shows nothing about which row was missing. `RoleRequired` **raises**
`PermissionDenied` rather than rendering, so `handler403` is the only place a
403 page is made. The test URLconf (`accounts/tests/urls.py`) exports
`handler403` as it does `handler500`, and its test-only view `save_a_row` gets
a row (`LOG_WORK`), so the AC15 walk covers it too.

**HTMX:** the answer is the same 403. htmx 2 swaps nothing on a 4xx answer by
default, so the page stays as it was (AC10). No page uses HTMX yet; U0.10
adds the "not allowed" toast with the rest of the UI kit.

### 3.3 Links on a page (AC11)

A context processor gives every template `allowed`: the set of the person's
permissions (from `request.standing`, no extra query). Pages that don't pass
through `RoleRequired` (login, 404, 500, the CSRF-failure page) have no
`request.standing`; the processor reads it with `getattr(…, None)` and gives
an empty set, so it can never break an error page. The home page shows
the Staff link when `"manage_users" in allowed`. Later units use the same set
for their links. Hiding a link is only a convenience; §3.1 is the rule.

## 4. How a service checks (AC12, AC13)

### 4.1 One check for every service

```python
@dataclass(frozen=True)
class Standing:
    user_id: int | None
    is_active: bool
    role: Role | None


def standing(user: User | AnonymousUser) -> Standing:
    """Active flag and role, read from the database now (one query)."""


def require(user: User | AnonymousUser, permission: Permission) -> Standing:
    """The person's standing, or NotAllowed: account_not_active / role_not_allowed."""


class NotAllowed(PermissionDenied):
    """Refused by role or account state; carries `rule` and `message`. Always 403."""
```

`require` reads the database, not the `User` object the caller holds, so a
session that is still open after a deactivation or a role change can't save
with the old standing (AC5, AC13). An anonymous user, a deactivated account,
Read Only and no role are refused before anything is written.

`NotAllowed` is a `PermissionDenied`, **not** a `Refused`, so the views'
`except Refused` (e.g. `views.py:114, 167, 189`) can't catch it and turn a
403 into a page with a message; it always reaches Django, which answers 403
(AC10). It carries `rule` and `message` like a refusal, for callers and tests
that want the name. `save_once` and `database_refusals` let it through
untouched. `require_admin` goes away; the account services call
`require(by, MANAGE_USERS)`. The existing `admin_only` rule name goes away
too: everything says `role_not_allowed`.

**Where the check runs:** the person's standing is read **once per save**, as
the first line of each `write_*` function, inside the transaction and
**before** `start_operation`. So a deactivated or Read Only person resending a
form is refused, not handed the original result (§4.3). The rows that depend
on the entries are checked with `may()` against that one standing after
`entries()` is built (Split builds its entries after the operation row).

**A role changed during a save:** a role change that commits in the same
moment can't be seen until the next save. Accepted: it's a gap of
milliseconds, and the role change itself can't be lost.

### 4.2 Which service checks what

| Service | Check |
|---|---|
| `save_operation` (and `split`, `close`) | each entry's action → its row (below), `may()` for each row; N7: an entry whose `staff_id` isn't the person saving needs `ENTER_FOR_OTHERS` (`staff_must_be_you`); who did the work must be active **and hold a role that may log work** (`check_staff` today accepts any active account, Read Only and no role included; refused with the existing `staff_not_active`) |
| `void` | the Void tree below |
| `correct` | `require(VOID_OR_CORRECT)`; a Supervisor who did (`staff_id`) or saved (`recorded_by`) any event being corrected is refused (`fix_own_entry`) |
| `review` | `require(REVIEW_EVENTS)`; then rule 10 exactly as built (`may_review`); `reviewer_for` takes the role from `standing`, so a deactivated reviewer is refused. Both checks move inside the `atomic()` block (today they run before it, `reviews.py:162–171`) |
| `review_queue` | empty for anyone without `REVIEW_EVENTS` (as now) |
| `reclassify_genus` | `require(RECLASSIFY_GENUS)` |
| `issue_next_sku` | `require(PLANT_LIFECYCLE)` on `assigned_by` |
| account services | `require(MANAGE_USERS)` (was `require_admin`) |

**Action → row** (`events/permissions.py`):

| Actions | Row |
|---|---|
| `intake`, `subculture`, `stage_change`, `count`, `contamination`, `transfer`, `out` | `LOG_WORK` |
| `split`, `close`, `loss`, `quarantine` | `SPLIT_CLOSE_LOSS` |
| `release` | `RELEASE_QUARANTINE` |
| `void`, `correction` | not through `save_operation`: refused (`event_action_not_here`, Internal) |

A test checks that every `Action` is in this table, so a new action can't be
saved without a row.

**The Void tree.** A Void covers the whole operation (U0.2b Q8). "The people
on it" are every `staff_id` and the `recorded_by` of its events.

```
require(UNDO_OWN)                                   Read Only, no role, deactivated → refused
role is Admin                                       → allowed
role may VOID_OR_CORRECT and isn't on it            → allowed (a Supervisor fixing others' work)
otherwise it is an Undo:
    the person saved the operation (recorded_by)?   no → Supervisor: fix_own_entry · Tech: undo_not_yours
    saved less than 10 minutes ago?                 no → undo_too_late
                                                    → allowed (Undo)
```

- **10 minutes** is `UNDO_WINDOW = timedelta(minutes=10)`, compared in SQL
  against the voided operation's one `operations.recorded_at` row with the
  database's `now()` (D-07, AC13), the same clock that stamped it.
- **A Supervisor's own entry** ([Q4](#11-owner-questions)): the spec says both
  "a Supervisor can't void an event they did or saved" (AC13) and "Undo an
  entry they saved, within 10 minutes: Supervisor ✅" (matrix). This design
  reads them together: within 10 minutes of saving it, a Supervisor may Undo
  their own entry, like a Tech; after that, AC13 applies and another reviewer
  fixes it.
- Every Void, Undo included, already goes to the Admin's queue (rule 10), so
  nothing about review changes.
- These checks run inside `write_void` and `write_correction`, after the
  target is read and **before `lock_batches`** (`services.py:409`), so a
  refused Undo takes no batch locks and writes nothing.

### 4.3 A resent form from someone else (AC13, U0.2b G4 L3)

`save_once` gives a resend the original result (`Already saved`). Its
signature becomes `save_once(operation_id, recorded_by, write)`. The check
sits **only in the "Already saved" branch**, just before `original_result`:
by then the first save has committed (the second waited on the
`operations` primary key), so its `Operation.recorded_by_id` can be read and
compared. Checking earlier, before the insert, would miss a first save still
in flight and leak its result. If the person differs, the answer is
`operation_saved_by_other` (Internal message, logged for the Admin). Two
different people can't send the same `operation_id` by accident (it is a
fresh UUID per form), so this means a copied form, and it must not tell them
what the first save wrote.

The standing check (§4.1) runs before this, so a resend by someone who has
since lost their role or been switched off is refused, not answered.

### 4.4 New rule names (core `MESSAGES`)

| Rule | Message |
|---|---|
| `role_not_allowed` | Your role can't do this. |
| `account_not_active` | Your account is switched off. Nothing was saved. |
| `staff_must_be_you` | You can log only work you did. A Supervisor can log it for someone else. |
| `fix_own_entry` | Another reviewer must fix an entry you did or saved. |
| `undo_not_yours` | You can undo only entries you saved. A reviewer fixes the others. |
| `undo_too_late` | Undo works for 10 minutes after saving. Ask a reviewer to fix this entry. |
| `account_cannot_change_own_role` | You can't change your own role. |
| `account_name_too_long` | A name can be at most 150 characters. |
| `operation_saved_by_other`, `event_action_not_here`, `auth_user_one_role` | Internal |

`admin_only` is removed (§4.1).

## 5. Giving and removing roles (AC2, AC4–AC9)

### 5.1 `set_role(by, account, role)` (`accounts/services.py`)

`role` is a `Role` or `None` (no role).

1. `require(by, MANAGE_USERS)` (AC8).
2. `by == account` → `account_cannot_change_own_role` (AC7, spec Q3).
3. In one transaction:
   - `lock_for_account_change`: lock the account's row **and** the active
     Admins' rows, in one query, in id order, with
     `select_for_update(no_key=True, of=("self",))` (the `writing.py`
     convention, so event inserts by those people aren't blocked).
     `deactivate` and `cucumber_admin` take the same lock, so two Admins
     changing each other at the same moment are taken one at a time, always
     in the same order (no deadlock). The lock **only takes the locks**:
     under READ COMMITTED its own list of Admins may be stale after a wait;
   - read the old role and decide "last active Admin?" with **new queries
     after the locks** (as `is_last_active_admin` does). Same role as now →
     nothing to do, no log line;
   - old role is Admin and the account is the last active Admin →
     `account_last_admin` (AC7);
   - `replace_role`: delete the account's row with
     `User.groups.through.objects.filter(user_id=…)`, then add the new one with
     `through.objects.create(…)`, a **plain INSERT**. Not `groups.add()`/`set()`:
     on PostgreSQL Django writes those as `INSERT … ON CONFLICT DO NOTHING`, so
     a second role would be skipped silently instead of refused (§6.2). One
     save (AC2).
4. One log line (§9).

There is no cache to clear: every request and every save reads the role from
the database (§3.1, §4.1), and nothing about the role is kept in the session
(AC5).

**A deactivated account keeps its role** ([Q3](#11-owner-questions)), so
switching it back on returns it as it was. It counts as an Admin only while
active (as `account_last_admin` does today).

### 5.2 Adding an account (AC4)

`add_account(by, name, email, role)`: the role is required and is one of the
four (the form has no default; "no role" isn't offered when adding). The
account and its role are saved in the same transaction as today's
change-due row. The log gets `account added` and then `role changed … from=none`.

### 5.3 The last Admin (AC7)

Two paths can leave Cucumber without an Admin: deactivating (refused since
U0.5) and changing the role (refused here). Both use
`lock_for_account_change` and `is_last_active_admin`. Removing the role from
a **deactivated** Admin is allowed: they aren't counted.

### 5.4 `cucumber_admin` (AC9)

It now **replaces** any role the account has with Admin (one role per
account), through the same internal `replace_role` as `set_role`, without the
Admin check (it runs on the server over SSH, U0.5 §9). It still asks
"Make Gene an Admin? [y/N]" before promoting someone. It never gives any
other role. Log: `role changed account=… from=tech to=admin by=command`.

## 6. Data model and migrations

No new tables. Roles stay Django groups (spec: out of scope, Django's own
per-model permissions are unused).

### 6.1 `0005_roles` (AC1)

Adds `supervisor`, `tech`, `read_only` with `get_or_create`, as `0002` did
for `admin` (a re-run after an undo finds them).

**Undo:** refused while any account holds one of the three roles (a
`RuntimeError` naming how many), as core `0004` refuses an undo with data:
dropping a group would silently take people's roles away. Also refused while
any feature flag is on for one of them (deleting the group would silently
drop it from `waffle_flag_groups`). With neither, the three groups are
deleted. `admin` stays (U0.5 §3.3).

### 6.2 `0006_one_role` (AC2, [Q1](#11-owner-questions))

The database itself keeps "at most one role per account":

```sql
CREATE UNIQUE INDEX auth_user_one_role ON auth_user_groups (user_id);
```

This only works if **every group is a role**, which is true today and is
what Q1 asks the Owner to keep: feature flags would be switched on for a role
(`cucumber_flag … on --group supervisor`), never for a hand-made group such
as "Lab". If the Owner wants other groups, the rule becomes a trigger that
looks at group names instead (Q1 b).

- **Before it adds the index:** a `RunPython` step lists any account in more
  than one group and stops with a readable message (as `0003` does). There
  are none on staging or production today; G5 checks first.
- **Two Admins giving roles to the same person at once:** `set_role` locks
  the account first (§5.1), so the second waits and then sees the first's
  change. The index is the backstop for a **plain INSERT** from any other
  path (raw SQL, `through.objects.create`); it refuses with
  `auth_user_one_role` (Internal).
- **What the index can't catch:** Django's `groups.add()` and `groups.set()`
  on PostgreSQL use `ON CONFLICT DO NOTHING`, so a second group is skipped
  without an error. So nothing in Cucumber calls them on users: `cucumber_admin`
  (`:87`) uses `replace_role`; the test helper `make_staff`
  (`core/tests/stock.py:46`), `uat/u0_2b_walkthrough.py:85` and
  `scripts/timing_10x.py:154` change to it too. A code-search test refuses
  `groups.add` / `groups.set` on a user outside tests of this rule.
- **Grants:** none change. `cucumber_app` already may add and remove rows in
  `auth_user_groups` and only read `auth_group` (core `0003`), so the app can
  give roles but never create a new group.

### 6.3 Rollback

`0006` undo drops the index. `0005` undo is refused while the three roles
are held (§6.1). Rolling the app back to the U0.5 release with roles in place
is safe: that release reads only `admin` and `supervisor` (in rule 10), and
none of its pages save events.

## 8. Carried in from the U0.5 G4 review (AC16–AC19)

- **AC16, "Lift the lock" lifts a network lock too** ([Q2](#11-owner-questions)).
  The person's own tries while the network was locked weren't counted (U0.5
  §7.2), so their email may have no failures to point at the address. So
  `lift_lock` deletes the email's failures **and** the recent failures of
  every address at or over the 50-try limit (at most the lab's one or two
  addresses). Then the page's "Gene can log in again." is true. Side effect:
  everyone else on that network gets a clean count too, and so would an
  address a guesser is using. Before deleting, each lifted address is logged
  with its count (deleting the rows removes that evidence), and both deletes
  run in one transaction.
- **AC17:** `add_account` and `cucumber_admin` refuse a name over 150
  characters (`account_name_too_long`), not only the form.
- **AC18:** `add_account` reads a database refusal by its rule name
  (`rule_of`): only `auth_user_username_key` (the email's unique rule) says
  "Another account already uses this email."; any other is Internal and logged.
- **AC19:** `email_key` applies Unicode NFKC before trimming and lowercasing.
  It is the one place emails are made into keys, so adding, logging in, the
  lock and `cucumber_admin` all agree (Django's login form already does NFKC).
  Two guards: every stored username must already equal `email_key(username)`,
  or that account couldn't log in (the `0006` `RunPython` step checks it and
  names any that don't; G5 runs it on staging and production first); and NFKC
  can make a key longer, so a key over 150 characters is cut to 150 before it
  goes into `LoginFailure.email_key` (`max_length=150`) instead of failing the
  insert. A test checks `email_key(email_key(x)) == email_key(x)`.

## 10. How G2 proves it

### 10.1 Tests generated from the matrix (AC14, AC15)

The tests read `MATRIX`; none of the role × row cases are written out by hand.

- **People:** one account for each role, one with no role and one
  deactivated Tech (`make_staff` gets a `read_only` role and a "no role"
  helper).
- **Services:** a test-only table, `PROBES`, gives each row marked `services`
  one small function that tries that action as a given person on stock data
  (a probe for `LOG_WORK` saves a count, one for `VOID_OR_CORRECT` voids
  another person's entry, and so on). For every row × person the test expects
  "saved" if `may()` says so and, if not, `account_not_active` for the
  deactivated person and the row's `refused_as` rule for the rest, with
  nothing written. `refused_as` is `role_not_allowed` except
  `ENTER_FOR_OTHERS` (`staff_must_be_you`). The `VOID_OR_CORRECT` probe is a
  **Correction**, so a Tech meets `role_not_allowed` and not the Void tree's
  `undo_not_yours`, which has its own tests. A test fails if a row marked `services` or
  `both` has no probe.
- **Pages:** every URL pattern is resolved, its row read from the view, and
  each person sends GET (and POST for POST pages, with the CSRF check on and
  a stock account id). Allowed → not 403; refused → 403 with the page's text
  and no change in the database.
- **AC15:** the same URL walk fails for any pattern whose view has no row and
  isn't in the public list (login, `/health/`).
- **"Later" rows** have no page or service yet; a test checks their cells
  match the spec, so the later unit only adds its probe.
