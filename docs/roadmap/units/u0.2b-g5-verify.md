## Timing note (10× a small nursery)

Today, roughly (Owner, 2026-10-12): 300 plants, 1,000 open batches, 100
entries a day. Tested at 10×, on a throwaway database on the MacBook dev
machine (PostgreSQL 17 in Docker): **3,000 plants, 10,000 batches, 362,000
events** (a year at 10×), a review backlog of **7,000 events** (a week at 10×),
and one busy batch with 2,000 events. 30 runs each.

| Action | Median | p95 |
|---|--:|--:|
| Save an entry, typical batch (~36 events) | 9 ms | 15 ms |
| Save an entry, busy batch (~2,000 events) | 32 ms | 69 ms |
| Split | 9 ms | 24 ms |
| Void | 8 ms | 11 ms |
| Correction | 11 ms | 14 ms |
| Mark one queue item reviewed | 5 ms | 17 ms |
| Review queue, 7,090 items waiting | 1.6 s | 1.6 s |
| `check_projections`, all 10,030 batches (nightly) | 13.6 s | — |

Every save is far under the half-second a phone user would notice. The review
queue is the one slow spot: 0.5 s loading the waiting events and 1.1 s on the
"dated before a count" flag, which reads each queued batch's history. At
today's volume the same backlog is ~0.16 s. **Logged to U1.8** (review queue
screen): show the queue a page at a time and work out flags only for that page.
