| Name | Goes to | Cloudflare proxy |
|---|---|---|
| `cucumber.southeastcanopy.com` | Production tunnel → `http://app:8000` on the MacBook | Proxied (orange) |
| `cucumber-staging.southeastcanopy.com` | Staging tunnel → `http://app:8000` on the Asus | Proxied |

**One level only.** Names are `cucumber-ssh.…`, not `ssh.cucumber.…`.
Cloudflare's free certificate covers `southeastcanopy.com` and one level
below it (`*.southeastcanopy.com`); a second level needs a paid certificate,
and phones would show a certificate error.

**Only Cucumber's names go through Cloudflare's proxy.** Email and the website
keep working as now: for them Cloudflare only answers "where is it" and never
carries their traffic. That keeps the move's risk to "a record was missed",
which §5 checks.

## 4. The DNS move (AC15, AC16)

The domain stays registered at GoDaddy; only the list of records ("DNS")
moves. Written out step by step in `docs/runbooks/dns-move.md`.

### 4.1 Before the switch (nothing changes for anyone yet)

0. **Lock down both accounts.** After the move, whoever holds the Cloudflare
   account controls email delivery (`MX`), the tunnels and Access, and GoDaddy
   still controls which nameservers are used. On **GoDaddy and Cloudflare**:
   two-step login with an authenticator app (not SMS), recovery codes saved
   in the password manager. GoDaddy's domain lock stays on. The Owner is the
   only member of the Cloudflare account.
1. **Export from GoDaddy:** Domain → DNS → *Export zone file*. Saved on the
   Owner's Mac **outside the repo**, plus a screenshot of GoDaddy's DNS page
   as a second record.
2. **DNSSEC check:** GoDaddy → Domain → DNSSEC. If it is **on**, turn it off
   and wait 2 days before the switch, or the domain stops working everywhere.
   (It can be turned on again at Cloudflare afterwards, §16.)
3. **Add the site at Cloudflare** (free plan) and **import the zone file**,
   with *Proxy imported DNS records* **unticked**. Don't rely on Cloudflare's
   own scan: it misses names it can't guess, such as the DKIM keys
   `selector1._domainkey` and `selector2._domainkey`. It can also add records
   GoDaddy doesn't have, which `check_dns.py` can't see, so Cloudflare's DNS
   export is also compared with GoDaddy's, line by line, and any extra is
   deleted.
4. **Set every imported record to DNS only (grey).** The import proxies some
   by default. The email records (`MX`, `autodiscover`, DKIM, SPF `TXT`, and
   Microsoft's `_sip`, `_sipfederationtls`, `lyncdiscover` if present) and the
   website (`@`, `www`) must all be grey.
5. **Run `check_dns.py`** (§5) against one of the two nameservers Cloudflare
   assigned. It must say *all records match* before the switch. This output
   is AC15's evidence.
6. **Website check:** the website is GoDaddy Websites + Marketing, hosted by
   GoDaddy. Its `@` and `www` records are copied exactly (grey), and GoDaddy's
   site settings must not say the domain has to use GoDaddy's nameservers. If
   they do, **stop**: the fallback is a new domain bought at Cloudflare (spec,
   "Domain routes", ~US$10/year), decided with the Owner. Two more checks:
   - **Microsoft 365 bought through GoDaddy?** If so, GoDaddy stops managing
     its DNS records after the switch. Record that, and read GoDaddy's
     guidance for moving nameservers before going on.
   - **GoDaddy domain forwarding on `@` or `www`?** Forwarding only works on
     GoDaddy's nameservers. If it is used, replace it with a Cloudflare
     redirect rule (that one record must then be proxied, the only exception
     to "all grey"), or stop and decide with the Owner.

### 4.2 The switch

- **When:** a weekday morning the Owner can watch email for the rest of the
  day (Q4).
- GoDaddy → Domain → Nameservers → *I'll use my own* → the two Cloudflare
  names. Cloudflare emails when the site is active (minutes to a few hours,
  48 h at worst).
- **Nothing is deleted at GoDaddy for 2 weeks.** GoDaddy keeps its DNS
  records while unused, so the undo is putting its nameservers back.

### 4.3 Checks after the switch (AC16)

Same day, recorded in the runbook's log:

| Check | How |
|---|---|
| Email in | Send from a personal Gmail to a company address; it arrives |
| Email out | Reply from Outlook; it arrives at the Gmail, not in spam |
| Outlook | Opens and syncs on the Owner's phone and desktop (uses `autodiscover`) |
| Microsoft 365 | Admin centre → Settings → Domains → `southeastcanopy.com`: no issues shown |
| Website | `https://southeastcanopy.com` and `www.` load on a phone on mobile data, no certificate warning |
| Switched | `dig NS southeastcanopy.com @1.1.1.1` shows Cloudflare's two names |
| Records | `check_dns.py` again, both against a Cloudflare nameserver (`--server`) and the public internet (no `--server`). The public run alone can be answered from GoDaddy's cached records, which also match |

The next morning: email again, both directions.

### 4.4 Undo

If a check fails and the fix isn't clear within an hour: GoDaddy →
Nameservers → *GoDaddy default*. **Undo isn't instant:** it spreads the way
the switch did, usually within hours, up to 48 h. That is why §4.1 step 5
must pass first, and why the switch is on a day email can be watched.

- `.com` nameserver records are cached for up to 48 h, so some resolvers keep
  asking Cloudflare after an undo. **Keep the Cloudflare site for at least
  48 h after any undo.**
- **During the 2-week window, every record change is made at both GoDaddy
  and Cloudflare,** so either set of nameservers gives the same answers.

## 5. The DNS checker (AC15)

```bash
uv run --no-dev python -m scripts.check_dns ~/Documents/southeastcanopy.com.txt \
  --server <one of Cloudflare's assigned nameservers>   # leave out after the switch
```

- Reads the GoDaddy zone file: `A`, `AAAA`, `CNAME`, `MX`, `TXT`, `SRV`,
  `CAA`. Any other type is listed as *not checked*, never skipped silently.
  `NS` and `SOA` are left out: they are meant to change.
- Asks for each name and type with `dig +short` (`@server` when given) and
  compares the answers with the export as sets: order doesn't matter, names
  are compared without the trailing dot and case, `TXT` parts are joined.
- **Catches a proxied record:** a proxied `A` or `CNAME` answers with
  Cloudflare's addresses instead of the export's, so it shows as different,
  with the hint "is it set to DNS only?".
- Prints one line per record (`ok`, `missing`, `different: expected … got
  …`), then *all records match* or *N problems*, and exits non-zero on any
  problem.
- Long `TXT` values (over 60 characters, e.g. DKIM keys) are shown as their
  start and end only.

Parsing and comparing are plain functions, tested with sample zone text and
fake `dig` answers; `main()` only reads the file and runs `dig`, like
`next_version.py`.

## 6. Tunnels (AC19, AC21, AC24)

### 6.1 Four tunnels, one job each

| Tunnel | Runs on | How it runs | Route |
|---|---|---|---|
| `cucumber-production` | MacBook | `tunnel` service in production's compose project (exists since U0.4a) | `cucumber.…` → `http://app:8000` |
| `cucumber-staging` | Asus | `tunnel` service in staging's compose project | `cucumber-staging.…` → `http://app:8000` |
| `cucumber-admin` | MacBook | `cloudflared` (Homebrew) installed with **`sudo cloudflared service install <token>`**, so it starts at boot, not at login (AC24), **outside Docker** | `cucumber-ssh.…` → `ssh://localhost:22` |
| `cucumber-staging-admin` (Q1) | Asus | `cloudflared` from Cloudflare's apt source (suite `any`, since 26.04 may not be listed yet) as a systemd service, **outside Docker** | `cucumber-staging-ssh.…` → `ssh://localhost:22` |

- **Tunnels are managed in the Cloudflare dashboard** (Zero Trust → Networks →
  Tunnels), not with config files on the machines: each machine holds only a
  token. App tunnel tokens go in that environment's `secrets.env` as
  `TUNNEL_TOKEN`, with `COMPOSE_PROFILES=tunnel`; an admin token is given once
  to `cloudflared service install`. All tokens go in the password manager.
- **Each app tunnel reaches only its own `app`.** As built in U0.4a, every
  service shares compose's default network, so `tunnel` could reach
  `db:5432`, and through the host, the local network. Tunnel routes are set
  in the dashboard, so one wrong route (`tcp://db:5432`, `192.168.1.x`) would
  expose them. §11.1 splits the networks: `tunnel` shares a network only with
  `app`.
- **Updates.** Ubuntu's automatic updates cover only Ubuntu's own sources.
  Cloudflare's and Docker's apt sources are added to unattended-upgrades on
  the Asus. On the MacBook, `brew upgrade cloudflared` goes in the monthly
  check in its runbook.
- **SSH has its own tunnel, outside Docker.** SSH from away is most needed
  when Docker or the app is broken; a tunnel inside Docker would be down too.
  It also keeps the app tunnels from ever reaching the machine itself.
- **Outward only (AC21):** `cloudflared` connects out to Cloudflare; nothing
  is opened on the router. The check is in §10.3.

### 6.2 The HTTPS header

Django trusts `X-Forwarded-Proto: https` (U0.4a §4.3), which `cloudflared`
sets on every request. Checked once per environment after its tunnel is up:
logging in through the public name works (CSRF passes) and there's no
redirect loop. `app` is published on `127.0.0.1` only, so from outside the
machine the tunnel is the only way in. Any program on the machine itself can
still reach `127.0.0.1:APP_PORT`. If someone adds a name to a tunnel with no
Access application in front of it, the guard is `DJANGO_ALLOWED_HOSTS`:
Django refuses any name not on that list.

### 6.3 Raising HSTS

`DJANGO_HSTS_SECONDS` starts at 3600 (U0.4a §4.3). It is raised in each
`secrets.env`, followed by a deploy of the **same version** (the deploy's
`docker compose up -d` recreates the app with the new value; nothing else
changes):

1. `604800` (a week) the day AC19 passes on that environment;
2. `31536000` (a year) after 2 weeks with no HTTPS problems.

Recorded in the setup logs. HSTS is sent by Cucumber, so it covers the
`cucumber…` names only, never the website or email.

## 7. Access: the email check (AC19, AC20)

Cloudflare Zero Trust **free plan** (up to 50 people; Cloudflare may ask for a
card when choosing it; nothing is charged). Team name `southeastcanopy` (it
shows in the login address).

**Login method:** one-time PIN only (spec Q2: everyone has their own email).
Cloudflare sends a 6-digit code **only if the address is allowed** (AC20),
without saying whether it is.

**Lists** (Zero Trust → Reusable → Lists, type *Email*):

| List | Who | Changed by |
|---|---|---|
| `Cucumber staff` | Every staff email address, Owner included | Owner, in the dashboard. Runbook: add, remove, and *Revoke sessions* when someone leaves |
| `Cucumber admins` | Owner only | Owner |

**Applications** (self-hosted):

| Application | Address | Policy | Session |
|---|---|---|---|
| Cucumber | `cucumber.southeastcanopy.com` | Allow: `Cucumber staff` | 1 month (spec Q4's 30 days; the dashboard's wording) |
| Cucumber health | `cucumber.southeastcanopy.com/health/` | **Bypass: everyone** (uptime check, AC23) | — |
| Cucumber staging | `cucumber-staging.southeastcanopy.com` | Allow: `Cucumber staff` (spec Q1) | 1 month |
| Cucumber SSH | `cucumber-ssh.southeastcanopy.com` | Allow: `Cucumber admins` | 24 hours |
| Staging SSH (Q1) | `cucumber-staging-ssh.southeastcanopy.com` | Allow: `Cucumber admins` | 24 hours |

- The bypass covers `/health/` only, which answers "ok" or 503 and shows
  nothing else (U0.4a §12). Staging gets no bypass: nothing outside watches it.
- **The bypass matches the start of the path,** so any future URL under
  `/health/…` would be public too. A G2 test checks that `health/` is the only
  URL pattern starting with `health`. The monitor uses exactly `/health/`
  (`/health` redirects). Bot Fight Mode stays off, or it would block the
  monitor. If the chosen monitor can send custom headers, an Access service
  token replaces the bypass.
- **Access is the outer lock;** Cucumber's own login (U0.5) is the inner one.
  Also checking Cloudflare's signed header inside the app was considered and
  left out: `app` is reachable only through its tunnel or from its own machine,
  and `DJANGO_ALLOWED_HOSTS` refuses unknown names (§6.2). Revisit if that
  ever changes.

- **MacBook:** the `cucumber-admin` tunnel (§6.1) connects
  `cucumber-ssh.…` to the Mac's own SSH. Port 22 stays closed on the router;
  the Mac's firewall and "Administrators only" Remote Login stay as set up on

- **The Owner's laptop** (used away from home): `brew install cloudflared`,
  then in `~/.ssh/config`:
  ```
  Host cucumber-server-remote
    HostName cucumber-ssh.southeastcanopy.com
    User sawat
    ProxyCommand cloudflared access ssh --hostname %h
  ```
  The first `ssh cucumber-server-remote` opens the browser for the email
  code; after that it is plain SSH with the existing key, for 24 hours.
- **Asus (Q1):** the same with `cucumber-staging-admin` and
  `cucumber-staging-ssh.…`, user `staging-admin`, added to the Asus runbook.
  The Asus firewall also lets any device on the home and lab Wi-Fi networks
  reach SSH directly (192.168.101.0/24, 192.168.1.0/24). That is accepted:
  password login is refused and only keys work.

## 9. Uptime alert (AC23, Q2)

- A free outside monitor checks `https://cucumber.southeastcanopy.com/health/`
  every **3 minutes or less** if the free plan allows it, else 5, and G5
  records the real delay. With 5-minute checks the email arrives 5–10 minutes
  after the outage starts, while AC23 says 5. It emails the Owner when it fails, and again when
  it's back. It must look for the word `ok`, not just any answer (a Cloudflare
  error page also answers).
- **Which service is Q2.** Free plans' terms have been changing (at least one
  well-known free plan was limited to non-commercial use in late 2024), so the
  runbook says to read the terms at sign-up and pick one that allows business
  use.
- **Proof (AC23):** with the Owner's OK and outside working hours, stop
  production's app, wait for the email, start it again, wait for the "back"
  email. Both times recorded.
- The monitor's history also measures ADR-0001's "when to move to the cloud"
  triggers (outages over 4 hours, more than twice a month).

## 11. Container hardening (U0.4a G4 carry-over)

### 11.1 Every service in `compose.server.yaml`

| Service | Added |
|---|---|
| `app`, `migrate` | `read_only: true` with a `tmpfs` at `/tmp` (gunicorn's worker files, Python's temp files); `cap_drop: [ALL]`; `security_opt: [no-new-privileges:true]`; `pids_limit: 200` |
| `tunnel` | The same as `app` |
| `db` | `no-new-privileges`, `pids_limit: 300`, `cap_drop: [ALL]` with only what PostgreSQL's start-up needs added back (`CHOWN`, `DAC_OVERRIDE`, `FOWNER`, `SETGID`, `SETUID`). Not `read_only`: it writes outside its volume (`/var/run/postgresql`). (`read_only` with tmpfs at `/var/run/postgresql` and `/tmp` would also work; left for later, §16) |

**Three networks** (changed at G3, 2026-10-17). `backend` (`internal: true`,
no way out) holds `db`, `app` and `migrate`; `edge` holds `app` and
`tunnel`; `db-port` holds `db` alone. So `tunnel` can reach `app` and
nothing else in the project. `tunnel` needs no `/tmp` tmpfs. A G2 test
checks that `tunnel` and `db` share no network.

`db-port` exists because Docker opens no host port for a container that is
only on an internal network (tried on Docker 29: `127.0.0.1:5435` stayed
closed). The Owner chose to keep the port, for a desktop database app
reached from away over SSH (`ssh -L`, §8), over `db` having no route out.
The port stays `127.0.0.1` only.

Proved the way U0.4a's settings were: G2 tests read the compose file
(`test_compose_server.py`), and the deploy rehearsal
(`scripts/rehearse_deploy.sh`, in CI and locally) shows the app still starts,
migrates, serves its CSS and answers `/health/` under the limits. If the
rehearsal shows PostgreSQL needs one more capability, G3 adds exactly that
one and records why.

### 11.2 Production memory caps

U0.4a left production uncapped. Caps stop one runaway container from taking
all of Docker Desktop's 4 GB (Q3): **app 1 GB, database 1.5 GB, tunnel
128 MB** (≈2.6 GB of Docker Desktop's 4 GB). `secrets.env.example` gets them
as the production values, written the way compose expects: `1g`, `1536m`,
`128m`. Its comment "Production: leave blank" is replaced.
