# U0.10 · App shell & UI kit — Spec (G0)

**Unit:** [U0.10](../phase-0-foundations.md#u010--app-shell--ui-kit) · **Size:** M, proposed split into U0.10a and U0.10b ([Q1](#owner-questions)) ·
**Deps:** U0.5 (passed G6); U0.9 (passed G6) for the list pages · **Decisions:** D-16, D-17 (Resolved); D-26 (Resolved for now, revisit here, [Q8](#owner-questions))
**Status:** G0 draft · 2026-10-28 · waiting for Owner answers Q1–Q8 and sign-off

## Goal

Every Cucumber screen looks and behaves the same way, works one-handed on a
375 px phone, and can't be tripped up by a slow phone, a weak signal or a page
left open too long. Coded fields are always picked, never typed, from the
lists U0.9 keeps. Then the Admin gets the first real screens built on it: the
pages that edit those lists.

Today the app has a plain base page (U0.5) with its own small stylesheet, no
menu, no HTMX on any page, and Django's bare 403 for a stale form. Earlier
gates logged about twenty items for "the app shell"; this spec gathers them in
one place ([What is carried here](#what-is-carried-here)).

The unit has two halves of different kinds, and together they are more than
one build cycle ([Q1](#owner-questions)):

| Part | What | Who sees it |
|---|---|---|
| **U0.10a · Shell & kit** | daisyUI base page, menu, components, error states, the safety items (double tap, timeouts, CSRF page, CSP), existing pages moved onto the kit | Everyone |
| **U0.10b · List pages** | The Admin's pages for the reference lists, on the kit, calling U0.9's services | The Admin |

## Acceptance criteria

### U0.10a · Shell & kit

**Base page and assets** (ADR-0001 UI kit; U0.1 spike review)

- **AC1** *Given* any page, *then* it is built on the daisyUI 5 base page with Cucumber's theme ([Q4](#owner-questions)): the name, the menu, who is signed in, messages and the "Practice data" banner on staging (U0.5 AC21 kept). The CSS is compiled by the Tailwind standalone CLI with daisyUI's bundled plugin when the image is built and in CI; there is no Node toolchain.
- **AC2** *Given* any page, *then* every stylesheet, script, font and image comes from the app itself (no CDN, no other site at run time). htmx is a pinned file in the app's static files, checked against its published hash by a test.
- **AC3** *Given* any template, *then* it holds no inline JavaScript: no `<script>` with a body, no `on…=` attribute, no `hx-on`. Behaviour lives in static `.js` files. A test scans every template.
- **AC4** *Given* any page, *then* it is sent with a Content Security Policy that allows only the app's own scripts, styles, images and form targets, and no frames ([Q6](#owner-questions)). A page that breaks the policy is found by the E2E tests on staging, not by staff.

**Navigation** (SOP §7; U0.6)

- **AC5** *Given* a signed-in person, *then* the menu shows only the pages their role may open, read from the U0.6 matrix (`allowed`), not a second copy: today Home and Password for every role; Staff and Lists for the Admin. The page you are on is marked. A person with no role sees the "Choose a role" page as today (U0.6).
- **AC6** *Given* a 375 px phone held in one hand, *then* the menu and the page's main button are within thumb reach ([Q3](#owner-questions)), and any page opens in at most two taps from Home.

**One-handed at 375 px** (card acceptance)

- **AC7** *Given* every page at 375 px wide, *then* nothing scrolls sideways, every tap target (buttons, menu items, links in lists, the top bar's buttons, U0.5 G4) is at least 44 × 44 px, and text in inputs is at least 16 px (so iOS doesn't zoom). E2E tests check each page at 375 px.

**Form components** (SOP §2 principle 7; U0.9 S4, S8)

- **AC8** *Given* a coded field (stage, medium, location, genus, container type, count unit, event action, reason), *then* it is a dropdown built from the `references` service (`active_items`, in sort order; reasons from their list), never a text box, and the field holds no list of its own (U0.9 AC22). Each choice reads as code with label (`P1 · Multiplication`).
- **AC9** *Given* a record or history line that holds a switched-off item, *then* it shows the item's label and "(switched off)", found through `item` or an `all_items` reader that reads many rows in one query (U0.9 design §9).
- **AC10** *Given* a form with a date, *then* the date is filled in as today in Bangkok and can be moved back up to 7 days, never forward (SOP §2 principle 7, U0.2 Q5), picked, not typed. The week is shown next to it, worked out from the date ([Q5](#owner-questions)), and has no input. The service still checks the date itself; the field only stops honest mistakes.
- **AC11** *Given* a field the service refuses (`Refused` by rule name), *then* the message from the service is shown next to that field, in words, with the person's other answers kept.

**A slow phone and a weak signal** (issue #4; U0.1 spike review; D-17)

- **AC12** *Given* any form's Save (plain or HTMX), *when* it is tapped four times within a second, *then* one request is sent. Taps while sending are ignored, and the button shows it is sending. *When* the person comes back with Back, *then* the button works again. Checked by E2E on a slowed connection.
- **AC13** *Given* an HTMX save with no answer after 20 seconds (proposed; G1 sets the number above the server's own limits, AC15), *then* the page shows "Not confirmed: check your signal and tap Save again. If it was saved, you'll see *Already saved*." and Save works again. It never says "not saved", because the server may have saved it.
- **AC14** *Given* a request that fails, *then* the words say which failure it was: **no connection** ("You're offline or the signal dropped. Nothing was sent."), **server error** ("Something went wrong on our side. Tap Save again; if it keeps happening, tell the Owner.") or **busy** (AC15). No offline entry is built (D-17).

**The server's own limits** (U0.4a G4 review)

- **AC15** *Given* the app's database connection, *then* it has a `statement_timeout` and an `idle_in_transaction_session_timeout` beside today's `lock_timeout` (5 s); G1 sets the values, below gunicorn's 60 s. *When* any of the three is hit, *then* nothing is saved, the person sees "Busy, please try again", the answer is 503, and one log line names the limit.

**Stale forms and refusals** (issue #4; U0.6 G5 findings 3 and 4)

- **AC16** *Given* a form sent with an out-of-date or missing CSRF token (a login page left open, a second tab that logged out), *then* the person sees a page on the kit: "This page was open too long. Reload it and try again." with a Reload button, status 403. Nothing is saved, the token is not logged, and the log has one line.
- **AC17** *Given* any 403, *then* the log holds Cucumber's one "page refused" line and no traceback from `django.request`. A 404 and a 405 are one line each too. A 500 still logs its traceback.
- **AC18** *Given* the app starts on staging or production, *then* the log has no gunicorn `Control server error: [Errno 30] Read-only file system` line (U0.7, U0.8, U0.9 G5 findings).

**Lists, details, empty and error states**

- **AC19** *Given* a list page, *then* it uses the shared list layout: on a phone each row is a tappable card with its main words first; on a desktop a table. A list with nothing in it says what's missing and what to do ("No staff yet. Add the first person."), not a blank page.
- **AC20** *Given* a detail page, *then* it uses the shared detail layout: a title, the facts as label / value pairs, and the actions the role may take as buttons at the bottom.
- **AC21** *Given* a 403, 404 or 500, *then* the page is on the kit with the menu (if signed in), says in words what happened and offers Home. The 500 page needs no database.

**Existing pages moved onto the kit** (U0.5, U0.6, U0.7)

- **AC22** *Given* the login, home, password, Staff list, Staff detail, add-staff and staff-password pages, *then* they use the kit, and every U0.5, U0.6 and U0.7 test that checks behaviour passes unchanged. A test that checks markup may change, listed in the G2 note with its reason.
- **AC23** *Given* the home page, *then* it greets the person and shows the pages their role may open (AC5), with an empty state until Phase 1 brings work to do.
- **AC24** (U0.5 G4) *Given* the Password page, *then* it answers only GET and POST (others 405); an empty POST shows the form's errors instead of the blank form; saving the new password and clearing its change-due mark happen in one transaction.
- **AC25** (U0.5 G4) *Given* the Staff list, *then* it reads every account's lock in one query, not one per person (a query-count test with 1 and 20 people).

**Translation** (D-16; SOP §2 principle 9)

- **AC26** *Given* every template, *then* every word a person reads goes through the translation tags; the U0.5 check covers all templates, not only the account pages. *Given* Python text shown on a screen (form errors, messages, the words for a refusal), *then* it goes through `gettext` too, checked by a test. Only English is shipped.

### U0.10b · List pages (from U0.9 Q4)

- **AC27** *Given* the Admin, *when* they open Lists, *then* they see the stages, media codes, locations, genera and container types, each item with its code, label and whether it is on or off, stages in sort order. The event actions and count units are shown read-only, marked "fixed".
- **AC28** *Given* the Admin adds a media code, a genus (code and name) or a container type, *then* the U0.9 writer saves it and it is in its dropdown at once. A refusal (wrong code format, a code already used, …) shows U0.9's message next to the field and nothing is saved. Stages and locations have no Add (U0.9 Q5).
- **AC29** *Given* the Admin edits a label (a genus: its name), *then* only the label changes; a refusal is shown next to the field.
- **AC30** *Given* the Admin switches an item off, *then* the form asks for a reason from the `archive` list (dropdown) and an optional note, and the item drops out of the dropdowns but still reads on old records (AC9). Switching back on asks for no reason. Locations have neither (U0.9 AC9).
- **AC31** *Given* any change on these pages, *then* it goes through U0.9's writers only, so it is audited and checked for role; the pages pass no `via` (U0.9 G4 L4) and hold no rule of their own.
- **AC32** *Given* a Supervisor, Tech, Read Only person or one with no role, *then* Lists is not in their menu and its addresses answer the 403 page (AC21).
- **AC33** ([Q7](#owner-questions)) *Given* a label or genus name, *then* control, format and line-break characters are refused (Unicode categories Cc, Cf, Zl, Zp) and it is stored NFC-normalised before the length and name checks (U0.9 G4 L2, L3); and two items of the same list can't share a label in any letter case (L8).
- **AC34** (gate focus moved from U0.9) *Given* the Owner on a phone at 375 px, *then* they can relabel a medium, add one and switch one off with a reason, one-handed.

## Out of scope

- **The global search box**, pending [Q2](#owner-questions): there is nothing to search until plants exist (U1.1).
- **Thai text** (D-16): only English ships; the check makes Thai possible.
- **Offline entry** (D-17) and installing the app on a phone's home screen (a PWA).
- **Dark mode** and a second theme ([Q4](#owner-questions)).
- **Phase 1 screens** (plants, batches, events, review queue) and the **audit trail page** (U0.7 spec: after the first Phase 1 screens).
- **Editing the reason lists** (U0.9 Q7) and **adding stages or locations** (U0.9 Q5).
- **Alpine.js and TypeScript islands**: added by the first screen that needs one (ADR-0001). U0.10's components need only htmx and small static scripts.
- **Staff accounts on production** (U0.5 Q2): staff UAT runs on staging's practice accounts.
- **Rate limits, 2FA** (U6.1).

## Size

**M, split in two** ([Q1](#owner-questions)): U0.10a (M) is the kit, the
build step, about ten safety and logging items and seven existing pages moved
over; U0.10b (S) is three forms and a list page on top of U0.9's writers, plus
the label rules. Built together they are more than one build cycle (gates.md:
split), and U0.10b can't be designed until the kit's components are.

## What exists already (found in the code, 2026-10-28)

- `accounts/templates/base.html`: plain base page; `core/static/core/cucumber.css` (179 lines, "until U0.10 brings the UI kit"). No Tailwind, daisyUI, htmx or Alpine in the app; the spike (`spike/u0.1-ui-kit`) loaded daisyUI from a CDN with `data-theme="light"`.
- Pages: login, home (empty), password, Staff list / detail / new / password, deactivate and reactivate; `core` 403, 404, 500 templates and the practice banner.
- `test_base_page.py` checks that the account pages' words are marked for translation; Python-side text is not checked.
- Settings: `lock_timeout=5s` only; `LOGGING` sends `django` WARNING and above to the console, which is where the 403 traceback comes from; no CSP header; no `CSRF_FAILURE_VIEW`.
- Dockerfile: gunicorn `gthread`, 2 workers × 4 threads, `--timeout 60`; the container is read-only, so gunicorn's control server can't write to `/home/cucumber`.
- `week` is not stored anywhere (SOP §4: calculated); nothing defines how it is numbered yet ([Q5](#owner-questions)).
- `references.reading`: `active_items`, `item`, `check_active`, `stage_at_or_after`; no `all_items`, no reader for reasons. Writers `add_item`, `edit_label`, `switch_off`, `switch_on`, Admin only.
