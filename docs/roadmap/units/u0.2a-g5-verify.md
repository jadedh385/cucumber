## Owner UAT: SOP §5 walk-through

U0.2a is the database itself, so the walk-through goes straight to it: plain
SQL as `cucumber_app`, the user the running app logs in as. This is spec
story S1: bad data can't get in, even through the Django admin or raw SQL. A
few steps also try as the table owner, to show the triggers stop it too.
Every refusal is checked by its rule name from design §7.1, next to the
message staff would see.

**Run it yourself:** `uat/u0_2a.sh` (needs `docker compose up -d`). It makes a
fresh throwaway database, `cucumber_uat`, prints every step (what was tried,
the rule that refused it, the message staff see) and saves it to
`uat/u0_2a-result.md` on your machine (result files aren't committed).

### Found at this G5, and fixed

**A negative loss gave staff the wrong message.** A loss of −2 was refused,
so no bad data got in, but by the rule for a loss's shape, which shows
*"Something went wrong; nothing was saved. Please tell the Admin."* instead of
*"Quantities can't be negative."* PostgreSQL checks a table's rules in name
order, and `event_loss_shape` comes before `event_qty_not_negative`. The
same happens for every action that moves units (intake, out, contamination,
subculture, split, quarantine). The G2 test had used a Correction, which has
no shape rule, so it didn't catch this.

**Owner, 2026-10-12: fix it in the service.** The shared save path
(`insert_event` in `events/writing.py`) now refuses a negative quantity by
`event_qty_not_negative` before the database sees it, so staff get the plain
message. Five new tests, written first and seen failing (loss, out,
contamination, intake, and a loss with a negative `qty_in`). The database
itself still refuses plain-SQL rows by the shape rule; that is correct, and
the walk-through now shows both.

## Timing note (10× a small nursery)

Same scale as U0.2b (Owner, 2026-10-12: today ~300 plants, 1,000 open
batches, 100 entries a day). Loaded into the walk-through's throwaway
database on the MacBook dev machine (PostgreSQL 17 in Docker): **3,006
plants, 10,003 batches, 360,004 events**. Then single writes as
`cucumber_app`, each its own transaction, 30 runs each. Every rule and
trigger runs on these.

| Write or lookup (plain SQL, as the app) | Median | p95 |
|---|--:|--:|
| Register a plant (name checked against 3,000) | 1.4 ms | 2.8 ms |
| Open a batch | 0.8 ms | 1.8 ms |
| Save an entry (all event rules and triggers) | 1.1 ms | 2.8 ms |
| Update a batch's count | 1.1 ms | 2.1 ms |
| Review an entry (one review per entry) | 0.8 ms | 1.4 ms |
| Find a plant by name (duplicate search) | 1.0 ms | 1.5 ms |
| One batch's history (36 entries) | 0.8 ms | 1.7 ms |

The rules and triggers add no delay anyone would notice. The service-level
timings (saves with locks and the projection, the review queue) are in the
[U0.2b timing note](u0.2b-g5-verify.md#timing-note-10-a-small-nursery).
**For U1.10 (V.2 move):** a bulk load of 360,000 events in one statement took
19.6 s with every rule and trigger on, so loading V.2's history won't need
the triggers switched off for speed. The load script was one-off; a new one,
`uat/timing_10x.sh`, came in U0.4b (2026-10-18) for the production Mac re-run.
