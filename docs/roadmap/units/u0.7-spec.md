# U0.7 · Audit trail & append-only store — Spec (G0)

**Unit:** [U0.7](../phase-0-foundations.md#u07--audit-trail--append-only-event-store) · **Size:** M ·
**Deps:** U0.2b (passed G6), U0.5 (passed G6), U0.6 (passed G6) · **Decisions:** D-07 (Resolved)
**Status:** G0 passed · 2026-10-20 · signed off by Jade (Owner); Q1–Q5 answered, all as recommended

## Goal

Make Cucumber able to answer "who changed this, when, from what to what, and
why" for everything that matters, and make that answer impossible to edit.

Two halves, and most of the first is already built:

1. **Append-only store** (already true; U0.7 proves it again from outside).
   Events, operations, reviews, status changes, SKUs and `audit_log` can't be
   updated or deleted by the app user; triggers refuse it (U0.2a). U0.6 built
   the Void tree and the 10-minute Undo. U0.7 adds tests that try to break
   them through the services **and** through raw SQL, as the card asks.
2. **Audit trail** (new). Today the `audit_log` table exists but nothing writes
   to it. After U0.7 every change to plants, batches, reference lists, vendors
   and staff accounts leaves an `audit_log` row (who, when, before, after,
   reason), whichever way the change was made. The one-line log entries from
   U0.5 (AC30), U0.6 (AC6) and U0.4a (feature flags) move in as audit rows.

Also here: the **reason rule** for archive / retire / deactivate / void, and
**staff anonymisation** on request (PDPA, D-07).

No plant, batch, list or vendor screens exist yet (Phase 1, U0.9), so those
tables are audited from the database side now and the screens get it for free.

## User stories

| # | As a… | I want… | So that… |
|---|---|---|---|
| S1 | Owner | every change to plants, batches, lists, vendors and accounts recorded with who, when, before and after | I can see later how something came to be as it is |
| S2 | Owner | the record kept even if someone changes data by a side door (a script, raw SQL, a screen built later) | the trail can't be skipped by accident |
| S3 | Owner | no role, not even the app itself, able to edit or delete a past event or audit row | the history can be trusted in a dispute or an audit |
| S4 | Owner | a reason required whenever something is voided, retired, archived or deactivated | "why" is never missing |
| S5 | Tech | to undo my own entry within 10 minutes, and be refused after | I can fix a slip, but not rewrite history |
| S6 | Owner | a former staff member's personal data removed on request while their work stays | I meet a PDPA request without breaking the records |
| S7 | Owner | to be told if someone switches off the protections (disables a trigger, truncates a table) | tampering is noticed, not just made hard |

## Acceptance criteria

**Append-only store** (built in U0.2a/U0.6; U0.7 proves it from outside)

- **AC1** *Given* an UPDATE, DELETE or TRUNCATE on `events`, `operations`, `event_reviews`, `plant_status_changes`, `skus` or `audit_log`, *when* run as `cucumber_app` by raw SQL, *then* it fails and the row is unchanged. Same through the Django ORM and every service.
- **AC2** *Given* the same UPDATE and DELETE run as the database owner (the migration user), *then* the triggers still refuse them. TRUNCATE and `DISABLE TRIGGER` are the accepted owner-only exception (U0.2a G4); AC15 notices them.
- **AC3** *Given* the 10-minute Undo (U0.6 AC13), *then* it is refused after 10 minutes by the database clock (`undo_too_late`) and for an event the person didn't save, and a pass writes a Void, never a change to the event. The U0.6 tests already cover this; U0.7 keeps them in its suite and adds the raw-SQL attempt.

**Writing the trail**

- **AC4** *Given* an insert or update to a row of an **audited table** (`plants`, `batches`, reference lists, `vendors`, staff accounts and their role), *then* one `audit_log` row is written in the **same transaction**: `actor_id`, `at` (database clock), `table_name`, `row_pk`, `action` (`insert` / `update`; also `delete` when a role or a flag's group is removed, `truncate`, `lock_lifted`, `guards_accepted`), `before`, `after`, `reason_code` (from the `reasons` list), `note`, `via` (how the change came in, AC6) and `db_user` (the database login, set by the database). If the audit row can't be written, the change is not saved. *(Reworded at G1, 2026-10-20, Owner: [design §11.1](u0.7-design.md#111-spec-wording-to-change-at-sign-off).)*
- **AC5** *Given* the change was made by a **service, a management command, or raw SQL as `cucumber_app`**, *then* it is audited all the same ([Q1](#owner-answers)): the trail does not depend on the caller remembering.
- **AC6** *Given* a change by an SSH command with no signed-in person (`cucumber_admin`, `cucumber_flag`), *then* the actor is a reserved **System** account (inactive, can't log in), and the audit row's `via` says which command ran (design Q2). *(Reworded at G1.)* A change to an audited table with no actor set at all is refused.
- **AC7** *Given* only some fields changed, *then* `before` and `after` hold the **changed columns**, not the whole row. Projection-only batch columns (`live_count`, `stage_code`, `quarantined`, open/closed) are not audited (U0.2 design §2.7, M7).
- **AC8** *Given* any audit row, *then* it holds **no password, hash, session id or personal data** (name, email): staff are referred to by id (AC12 depends on it). A test scans every audit row written in the suite for these.
- **AC9** *Given* the audit rows, *then* the only way to read them in this unit is the database or an Admin SSH command (`cucumber_audit`: list rows by person, table, row and date). No role can edit or delete one (AC1).

**Moved in from the app log** ([Q2](#owner-answers))

- **AC10** *Given* an account added, deactivated, reactivated, password given, lock lifted or role changed (U0.5 AC30, U0.6 AC6), or a feature flag switched (U0.4a), *then* the change is an audit row and the plain log line stays too. Logins, failed logins, locks and logouts stay in the app log only: they are not data changes.

**Reasons** (D-07)

- **AC11** *Given* any Void, Retire, Archive or Deactivate of a plant, batch, vendor, reference item or staff account ([Q3](#owner-answers)), *when* no reason is given, *then* it is refused by rule name (`reason_required`) and nothing is saved. A reason is a code from the `reasons` list plus an optional note. The rule is in the database as well as the service, so a later screen can't skip it.

**Anonymisation**

- **AC12** *Given* the Admin runs `cucumber_anonymise` for an account (by email, confirmed by typing `ANONYMISE`, [Q4](#owner-answers)), *then* the account's name becomes `Former staff #<id>` and its username and email `former-staff-<id>@cucumber.invalid` (U0.5 keeps usernames email-shaped), it is deactivated, its sessions, password, login failures and change-due mark are cleared, and its events, reviews and audit rows keep pointing at the same id. Nothing else changes. *(Reworded at G1.)*
- **AC13** *Given* an anonymised account, *then* it can't log in or be reactivated, and the anonymising is itself an audit row (who ran it, which id, when; no personal data).
- **AC14** *Given* the last active Admin, *then* anonymising refuses it (`account_last_admin`, as U0.5).

**Alerts**

- **AC15** *Given* the protections (the append-only and audit triggers, and the revoked grants), *then* a command `cucumber_check_guards` reports any that are missing, disabled or changed, and exits non-zero. It runs at every deploy and a failure stops the release ([Q5](#owner-answers)).

**Tests** (card: G2 gate focus)

- **AC16** *Given* every append-only table and every audited table, *then* a test attacks it through the service, the ORM and raw SQL, as `cucumber_app` and as the owner, and fails if any attack changes a past row or skips the audit row. The owner's TRUNCATE is the one exception (AC2): it must write a `truncate` audit row and stop the next deploy until accepted (AC15). *(Reworded at G1.)*
- **AC17** *Given* the list of audited tables in the code, *then* a test fails if a model's table is neither on it nor on the short list of tables deliberately not audited (events and the other append-only tables, sessions, login failures, projections). A new table can't ship unaudited by accident.

## SOP and deck sources

- SOP §2.5 and §5.6: events are append-only; fixes are Void or Correction with a reason.
- SOP-10 Fix a mistake: Undo for your own entry, within 10 minutes.
- D-07: no hard deletes; reason on every void/retire/archive/deactivate; PDPA anonymisation and sandbox wipe are the only exceptions.
- Deck 03 "Audit Trail": user, time, before/after on every write.
- Carried in: U0.2a G4 (audit every write to plants, batches, lists, vendors; alert on DISABLE TRIGGER / TRUNCATE), U0.4a G1 (record flag changes), U0.5 AC30 and U0.6 AC6 (move log lines in), U0.5 (staff anonymisation).

## Out of scope

- **A screen for reading the audit trail.** AC9 gives the Admin an SSH command. A page is added when the app shell (U0.10) and the first screens (Phase 1) exist.
- **Audit rows for events and reviews.** They are their own record (U0.2 design §2.7).
- **Plant, batch, list and vendor screens** and their services (Phase 1, U0.9). Their tables are audited from the database now.
- **Sandbox wipe** (U6.5), **backups** (U0.11), **2FA** (U6.1).
- **Scheduled alerting** (a daily check that posts to Discord). AC15 checks at deploy; a schedule belongs with monitoring (U6.x).
- **Protecting against the database owner.** The owner can still TRUNCATE or disable a trigger (accepted, U0.2a G4); AC15 notices it.

## Size

**M.** One migration (audit triggers on the audited tables, the System account, the reason check), a way to pass the acting person to the database, three management commands (`cucumber_audit`, `cucumber_anonymise`, `cucumber_check_guards`), moving the three log sources in, and the attack tests. No new tables.
