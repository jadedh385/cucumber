## Restore steps (as rehearsed)

For staging; production is the same with `production` in place of `staging`.
Restore a copy taken *before* a deploy into the version that was running when
it was taken (the copy's name says which deploy it was taken before; `current`
said what ran). Until U0.11 writes the full restore runbook, do this with Claude.

```bash
cd ~/cucumber/staging/src          # its compose file matches the running version
export IMAGE_NAME=cucumber-staging CUCUMBER_VERSION="$(cat ../current)"
dc() { docker compose -p cucumber-staging --env-file ../secrets.env -f deploy/compose.server.yaml "$@"; }
copy=../backups/2026-10-16-1151-before-main-141c7f9ed2c1.dump   # the copy to restore

dc stop app                                                      # 1. no writes during the restore
dc exec -T db pg_restore --list < "$copy" > /dev/null            # 2. the copy reads
dc exec -T db psql -U postgres -d postgres -c "DROP DATABASE cucumber WITH (FORCE)"   # 3.
dc exec -T db pg_restore -U postgres --create --exit-on-error -d postgres < "$copy"   # 4.
dc run --rm -T migrate python manage.py pending_migrations       # 5. expect {"pending": [], "unknown": []}
dc start app                                                     # 6.
# 7. /health/ says ok (the deploy command's check, or curl with the Host and X-Forwarded-Proto headers)
```

- **`--create` matters.** It brings back the database's own settings, including
  "only Cucumber's two roles may connect" (`docker/postgres/init/01-roles.sh`).
  Restoring into a database made by hand would lose that.
- **`-T` matters**, as for the backup: without it the copy is corrupted on the way in.
- If step 5 lists `pending` migrations, the copy is older than the running
  version: deploy the version named in the copy's file name first, then restore.

## Findings

1. **`--source` can take over a real version's image name** (found by a slip
   during this G5, fixed on the spot). `--source` builds under the version name
   it is given. A build from a scratch folder named `2026.10.1` re-tagged
   `cucumber-staging:2026.10.1`. The next real deploy of `2026.10.1` rebuilt the
   tag, but Compose didn't restart the app (same image name), so it kept running
   an untagged image until `up --force-recreate`. Nothing broken ran and no data
   changed. `--source` is hidden and staging-only. **Suggested fix (U0.4b G3, or a
   small PR now):** name `--source` builds `source-<time>` and refuse a version
   tag with `--source`. **Fixed 2026-10-16** (Owner: fix now): `--source` builds are
   named `source-<time>` and take `main` only; a failed deploy after one leaves the clone alone.
2. **A deploy from a different folder restarts the database too** (a few seconds
   more downtime). Compose labels the project with the folder it was started
   from; changing folder recreates every container. Normal deploys always use
   `staging/src` and leave the database running (checked: same start time
   before and after). Only `--source` changes folder. No change needed.
3. **Scripts now run from `~/cucumber/tools`** (a clone on `main`), as design §6.1
   says. Phase 5 ran them from `staging/src`. That works for `main`, but a tag
   deploy would check out older deploy code, which then refuses Python's cache
   folder. Runbook updated.
4. **`uv` isn't on the path for one-off SSH commands** (`ssh cucumber-staging
   'uv …'`). Use `ssh -t cucumber-staging` and type the command, or wrap it in
   `bash -lc '…'`. Runbook updated.
5. **The U0.2b walk-through imports `pytest`** through the test helpers, which
   the server image rightly leaves out. On staging it ran with pytest 9.1.1
   added for that one run only. Fine for now; when walk-throughs become a
   regular staging step, move the helpers it needs out of `tests/`.
