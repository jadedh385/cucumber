## Exception: rollback rehearsal

The runbook's rehearsal is "deploy the release, deploy back to what ran before,
deploy forward again". For U0.7 the middle step cannot work: `2026.10.3` does not
know the three new migrations (`accounts.0007_system_account`,
`core.0006_audit_trail`, `references.0004_reason_lists`), and the deploy command
stops with "The database has 3 changes this version doesn't know … Restore an
older copy instead, or type yes to go on". Typing yes would run the old code
against a database whose audit triggers refuse its writes.

So the only way back past U0.7 is **restoring the copy taken before the deploy**
([release.md, restore a copy](../../runbooks/release.md#restore-a-copy-production)),
which was not rehearsed on staging for this release. The Owner chose to sign off
without it, on 2026-10-22: the app was stopped during the deploy, the business
does not rely on the app yet, the deploy command rolls itself back when its final
check fails, and the plan after release is to **roll forward** (fix in a new
version), not back. Staging ran the release forward only (`main-1908ed24dfd6` →
`2026.10.4`, `Done`, 40 s).

## Findings

1. **Rollback past U0.7 means restoring a copy.** The release runbook's staging
   rehearsal ("deploy back to what ran before") does not apply to a release with
   migrations. The runbook should say so for U0.7 and rehearse the restore.
   Follow-up with the `audited()` change below.
2. **Staging's direct address timed out**, as production's did in U0.6; the
   `-remote` alias worked. Not a fault in the release.
3. **A deploy question needs a keyboard.** The rollback run waited silently for
   a typed answer. Worth a note in the runbook that a run with no output for
   more than a minute is probably waiting at a question.
4. **Not checked in this G6:** a sign-in on production after the release (the
   one-time sign-out, D5, and the Staff page). Not run by Claude; the Owner's own
   check is optional.
