## 2. How a change reaches the trail

```
service / command / raw SQL
   │  BEGIN
   │  set_config('cucumber.actor_id', '7', true)        ← audited(by, …)
   │  set_config('cucumber.via', 'app', true)
   │  set_config('cucumber.reason_code', 'deactivate_left_company', true)   (only when one is needed)
   │  set_config('cucumber.note', 'moved to Chiang Mai', true)
   │  UPDATE auth_user SET is_active = false WHERE id = 12
   │      ├─ BEFORE trigger  <table>_reason_required → no reason? raise reason_required (§4.2)
   │      └─ AFTER trigger   <table>_audit
   │             changed columns (minus ignored, personal ones masked) → none? stop
   │             actor_id missing?  raise audit_actor_required (§4.1)
   │             INSERT audit_log (actor, now(), table, row, action, before, after, reason_code, note, via)
   │  COMMIT  (the change and its audit row together, or neither: AC4)
```

`set_config(…, true)` lasts until the transaction ends, so a pooled or
reused connection never carries one person's id into the next request.
A rollback, or a savepoint rolled back, undoes the setting as well.

## 3. Naming the person (`core/audit.py`, AC4–AC6)

### 3.1 `audited()`

```python
@contextmanager
def audited(
    by: User | SystemActor,
    *,
    via: str = "app",
    reason: Reason | None = None,  # code + optional note (§6)
) -> Iterator[None]:
    """A transaction in which every audited write names `by` (design §3).

    Opens `transaction.atomic()` and sets the four `cucumber.*` settings for
    it. On the way out, normal or not, it puts back the values that were
    there before (usually empty). Nested for a different person it raises
    (a programming error, not a refusal).
    """
```

- **Why "put back" (review H1).** Inside an outer transaction, `atomic()`
  is only a savepoint. Releasing a savepoint keeps `set_config(…, true)`
  values; only a rollback undoes them. Without putting them back, the
  person would stay named for the rest of the outer transaction. That
  covers every test (each runs inside a transaction) and the login's
  `one_try_at_a_time` lock.
- `SYSTEM` is the reserved System account (§5.2). It is looked up by its
  fixed username **on every call**, never cached: a test that empties the
  database (`transaction=True`) removes it and `restore_system_account()`
  adds it again with a new id (review H2). Commands with nobody signed in
  use it (AC6); `via` names the command.
- Data migrations can't import app code (the repo's rule), so
  `db_rules.AS_SYSTEM_SQL` gives them the same `set_config` lines as plain
  SQL, naming System by username and `via = 'migration'` (review M4).
- `via` is `app` for pages and services, the command's name for an SSH
  command, `migration` for a data migration, and `sql as <role>` when raw
  SQL doesn't set it ([Q2](#11-owner-questions)).
- The reason note is trimmed, and is at most 500 characters
  (`reason_note_too_long`).

### 3.2 Nobody named, nothing saved (AC5, AC6)

The audit trigger refuses an audited change when `cucumber.actor_id` is
unset or empty (`audit_actor_required`). This applies to everyone: the
running app, `psql` as `cucumber_app`, and the owner. A service that forgets
`audited()` fails the first time its test runs, not in production.

Raw SQL may set the setting itself and name anyone. That is accepted:
anyone who can run raw SQL as `cucumber_app` already has the app's
password. The aim is a trail that can't be **skipped**, not one that proves
who typed the SQL. `via` is likewise whatever the caller says. A raw-SQL
change that doesn't set it shows `sql as cucumber_app`, but raw SQL could
claim `app`. What the caller **can't** choose is set by the database
(review M3): a `BEFORE INSERT` trigger on `audit_log` itself,
`audit_log_stamp`, sets `at = now()` and `db_user = session_user` on every
row, whatever the insert said. A row the app forges by hand therefore
still shows when it was written and by which database login.

### 3.3 Where `audited()` goes

| Caller | Person | Reason |
|---|---|---|
| `add_account`, `set_role`, `reactivate`, `give_new_password` | the Admin | — |
| `deactivate(by, account, reason)` | the Admin | required, `deactivate` list ([spec Q3](u0.7-spec.md#owner-answers)) |
| `lift_lock` | the Admin | — (writes its own row, §5.4) |
| own password page: the **whole POST branch** of the `password` view, because `is_valid()` checks the old password and that can re-hash it (review M4) | the person | — |
| login form (`authenticate`) | System, `via="login"` | — (only a password re-hash can be written, §4.3) |
| `events.save_once`: the one transaction behind `save_operation`, `split`, `close`, `void`, `correct` (review M4) | `recorded_by` | events carry their own reason (U0.2) |
| `reclassify_genus` | the Admin | — |
| `cucumber_admin`, `cucumber_flag`, `cucumber_anonymise`, `cucumber_check_guards --accept` | System, `via=<command>` | anonymise: `deactivate_pdpa_request` (§7.2) |
| data migrations that touch an audited table | System, `via="migration"` | — |

`audited()` opens the transaction, so in the services it replaces the
`transaction.atomic()` already there. Nothing moves outside a transaction
that wasn't already in one.

## 4. The database side (`db_rules.py`, migration `core 0006`)

### 4.1 `cucumber_audit()`: one function, every audited table

An `AFTER INSERT OR UPDATE OR DELETE … FOR EACH ROW` trigger. The trigger's
arguments say how each table is read, so the one function serves every
table:

```sql
CREATE TRIGGER plants_audit AFTER INSERT OR UPDATE ON plants
  FOR EACH ROW EXECUTE FUNCTION cucumber_audit('id', 'name_key', '');
--                                key column ─┘     ignored ─┘   masked ─┘
```

1. `to_jsonb(OLD)` and `to_jsonb(NEW)`, with the **ignored** columns taken
   out of both.
2. INSERT: `after` is the whole new row. UPDATE: `before` and `after` hold
   only the columns that differ (AC7). DELETE: `before` is the whole old row.
3. If no column differs, **no row is written and no person is needed**. So
   Django's `last_login` stamp, a projection refresh and a save that changes
   nothing write nothing.
4. **Masked** columns keep their name, but the value becomes `"changed"`
   (`"set"` on insert). An audit row can then say a name or password changed
   without holding it (AC8).
5. Needs `cucumber.actor_id`, else `audit_actor_required` (§3.2).
6. Inserts the `audit_log` row: `at` is `now()`, the database clock, the
   same instant as the change (AC4).

`SECURITY DEFINER` is **not** used. The trigger inserts as whoever made the
change, and `cucumber_app` already has INSERT on `audit_log`.

Every new function has `SET search_path = pg_catalog, public` and names
its tables `public.audit_log`, `public.reasons` and so on (review M1).
Without this, a temporary table called `audit_log`, made by whoever is
connected, would catch the audit rows instead of the real one. On
production `01-roles.sh` already revokes TEMP from PUBLIC; the guard
check confirms that it stays revoked (§8.1).

`to_jsonb` uses **column** names (`stage_code`, `created_by`), not
Django's field names (`stage_id`). The lists below are column names. The
test that pins the batch list to `projected_columns()` maps one to the
other through `field.column` (review L6).

| Table | Key | Ignored (not audited) | Masked | Delete? |
|---|---|---|---|---|
| `plants` | `id` | `name_key` (generated from `full_name`) | — | no (`plants_no_delete`) |
| `batches` | `id` | `live_count`, `quarantined`, `stage_code`, `status`, `closed_at`, `voided_at`: the projection's columns, exactly `projected_columns()` plus `voided_at` (AC7) | — | no |
| `genera`, `stages`, `media_codes`, `locations`, `reasons` | `code` | — | — | no |
| `vendors` | `zoho_contact_id` | `synced_at` (the Zoho sync stamps it on every run, U3.2) | — | no |
| `auth_user` | `id` | `last_login` | `password`, `username`, `email`, `first_name`, `last_name` | no (the trigger refuses it, §4.4) |
| `auth_user_groups` (the role) | `user_id` | `id` | — | yes: removing a role |
| `waffle_flag` | `id` | `modified` | — | flags are never deleted (U0.4a grants) |
| `waffle_flag_groups` | `flag_id` | `id` | — | yes: a group taken off a flag |

**The role** uses the same function (review L3: no special trigger, and
`replace_role` stays as U0.6 built and tested it). Changing a role is
therefore two rows in one transaction, `delete` {group_id: 3} then
`insert` {group_id: 2}, both keyed by the account's id. `cucumber_audit`
shows group ids as role names and flag ids as flag names, so one account's
or one flag's history reads as one story (review L2).

### 4.2 `cucumber_reason_required()`: the reason rule (AC11)

A `BEFORE UPDATE` trigger, given a column and its "off" values:

| Table | Column → off value | Reason list |
|---|---|---|
| `genera`, `stages`, `media_codes`, `locations`, `reasons`, `vendors` | `active` → `false` | `archive` |
| `auth_user` | `is_active` → `false` | `deactivate` |
| `plants` | `status` → `retired` | `retire` |
| `plants` | `status` → `voided` | `void` |

When the row moves **into** an off value and `cucumber.reason_code` is
empty, the trigger raises `reason_required`. The reason code is then
checked against the list that matches the action
(`reason_wrong_list`), so a "Duplicate entry" void reason can't retire a
plant. An unknown code is refused by `audit_log.reason_code`'s foreign
key. The service checks the same thing first (§6), as the event services
already do with `check_reason`, so a person gets a message instead of a
database error.

Events need nothing new: a Void or Correction without a reason is already
refused by `event_reason_required` (U0.2a), and Undo is a Void. A batch is
voided by voiding its events, so its own `status` is a projection column
(not audited, §4.1).

### 4.3 What is deliberately left out

- **Logins.** Django stamps `last_login` (ignored), and on a password
  re-hash after a Django upgrade it rewrites `password` during login. The
  login form's `authenticate` runs inside `audited(SYSTEM, via="login")`,
  so a re-hash is recorded as `password: changed` by System, instead of
  failing the login. Logins and failures stay in the app log (spec Q2).
- **Events and the other append-only tables** are their own record (spec,
  out of scope).

### 4.4 TRUNCATE is noticed, not stopped (AC2, AC15, [Q3](#11-owner-questions))

`cucumber_app` has TRUNCATE on nothing (U0.2a grants), so only the owner can
truncate. Stopping the owner is out of scope. Instead, an
`AFTER TRUNCATE … FOR EACH STATEMENT` trigger on every append-only and
audited table writes one `audit_log` row: `action = 'truncate'`, the table,
`actor_id` empty, and `via = 'sql as <session_user>'`. If `audit_log`
itself is truncated, its own trigger writes that row into the emptied table,
so the trail still shows it was wiped. `cucumber_check_guards` fails while
such a row hasn't been accepted (§8.2).

The test suite's clean-up between database tests also truncates. In the
test database that writes these rows, which no test reads except the
TRUNCATE tests. `actor_id` may be empty only on `truncate` rows (a check
constraint), because a flush also empties `auth_user`, so the System
account may be gone.

Also on `auth_user`: a `BEFORE DELETE` trigger (`auth_user_no_delete`,
the U0.2a `cucumber_no_delete()`). Accounts are deactivated or anonymised,
never deleted (D-07). Until now only the missing grant stopped a delete.

## 5. Data model and migrations

Run order: `references 0004` → `accounts 0007` → `core 0006`. The triggers
come last, so the rows the migrations seed write no audit rows and need no
person.

### 5.1 `references 0004_reason_lists` (AC11, [Q1](#11-owner-questions))

- `reasons_applies_to_valid` widened: `void, correction, loss` + `retire`,
  `archive`, `deactivate`.
- Seeds the three new lists. Codes follow `reason_code()` from 0002, e.g.
  `deactivate_left_company`:

| List | Labels (all active unless marked) |
|---|---|
| `deactivate` | Left the company · On leave · Security · Other · *PDPA request* (inactive: only `cucumber_anonymise` uses it) |
| `retire` | No longer grown · Mother plant lost · Other |
| `archive` | No longer used · Duplicate · Entered by mistake · Other |

  Plant **Void** reuses the existing `void` list.
- **Undo** refuses while any `audit_log` row or event uses one of the new
  codes. Otherwise it disables `reasons_no_delete` for the delete only,
  removes the seeded rows and narrows the check again.

### 5.2 `accounts 0007_system_account` (AC6, AC12, AC13)

- **System account**: `username = email = 'system@cucumber.invalid'`,
  `first_name = 'System'`, inactive, unusable password, no role. `.invalid`
  can never be a real address, so it passes `auth_user_username_is_email`
  and can't clash with staff.
- **`auth_user_anonymised_stays_off`**: `CHECK (NOT (username LIKE
  'former-staff-%@cucumber.invalid' AND is_active))`. An anonymised account
  can never be switched back on, even by raw SQL (AC13).
- **`auth_user_system_stays_off`**: the same for `system@cucumber.invalid`.
- Pre-check: names any account already using `@cucumber.invalid`, instead
  of a raw constraint error.
- **Undo** refuses while any `audit_log` row names the System account.

### 5.3 `core 0006_audit_trail` (AC4–AC8, AC15)

`audit_log` gains:

| Column | Type | Why |
|---|---|---|
| `reason_code` | text, FK → `reasons.code`, null | the picked reason (AC11) |
| `note` | text, null | the optional note: today's `reason` column, renamed (below) |
| `via` | text, not null | `app`, a command, `login`, `migration`, `sql as <role>` (AC6, [Q2](#11-owner-questions)) |
| `db_user` | text, not null | the database login that wrote the row, set by `audit_log_stamp` (§3.2), never by the caller |

`audit_log` has no rows yet (nothing has written to it), so new NOT NULL
columns need no default for old rows. The existing `reason` column is
**renamed** to `note` in the same step. No row is lost, and the model's
field becomes `note`. Other changes:

- `actor_id` becomes nullable, with `audit_log_actor_required`:
  `CHECK (actor_id IS NOT NULL OR action = 'truncate')`.
- `audit_log_action_valid`: `action IN ('insert', 'update', 'delete',
  'truncate', 'lock_lifted', 'guards_accepted')`.
- Indexes for `cucumber_audit`: `(table_name, row_pk, at)`, `(actor_id, at)`.
- The functions `cucumber_audit()`, `cucumber_reason_required()`,
  `cucumber_truncate_noticed()` and `audit_log_stamp()`, and the triggers in
  §3.2, §4.1, §4.2 and §4.4.
- `REVOKE INSERT, UPDATE, DELETE ON auth_user_user_permissions FROM
  cucumber_app` (review L1). Roles are groups, so nothing uses per-person
  permissions. Without the grant, a permission given straight to an account
  can't slip past the trail.
- **Undo** refuses while `audit_log` has any row (as core 0004 does for
  plant data). Otherwise it drops the triggers and functions and puts the
  columns back.

### 5.4 Rows the app writes itself

Two changes leave nothing in an audited table for a trigger to see, so the
service inserts the row itself. Both are inside `audited()` and use the
same columns:

| Change | Row |
|---|---|
| Lift the lock (AC10) | `action = 'lock_lifted'`, `table_name = 'auth_user'`, `row_pk = <account>`, `after = {"failures_cleared": 4, "networks_lifted": 1}`. Counts only: a network address can identify a person, so it stays in the app log. |
| Accepting a noticed TRUNCATE (§8.2) | `action = 'guards_accepted'`, `table_name = 'audit_log'`, `after = {"truncate_rows": [ids]}`, note required. It counts only when `db_user = 'cucumber_owner'`, so the app can't silence the alarm by writing one (review M3). |

### 5.5 Rollback

On staging the undo runs in order (`core 0006` → `accounts 0007` →
`references 0004`), and only before any audited change has been made. After
the release, any change writes an audit row, so **going back past this
release means restoring the copy**, as with U0.6. The G6 rehearsal checks
both: the undo on a fresh staging copy, and the refusal once a row exists.

## 6. Rules and messages (core `MESSAGES`)

| Rule | Where | Message |
|---|---|---|
| `reason_required` | service + trigger | "Choose a reason." |
| `reason_wrong_list` | service + trigger | "That reason doesn't fit this change. Choose another." |
| `reason_note_too_long` | service | "The note can be at most 500 characters." |
| `audit_actor_required` | trigger | "This change can't be saved because it doesn't say who made it." (A programming error: also logged as an error with the table name.) |
| `account_anonymised` | service + check | "{name}'s details were removed (PDPA), so the account can't be switched back on." |
| `account_is_system` | service + check | "The System account can't be changed." |
| `account_last_admin` | service (existing) | as U0.5, now for anonymising too (AC14) |

Every service that switches something off takes `reason: Reason`, a frozen
dataclass `(code: str, note: str = "")`, and refuses `None` with
`reason_required` before opening the transaction.

## 7. SSH commands

All three are SSH-only and Admin-only, like `cucumber_admin`. Only the
Owner has the server login (U0.4a), so there is no role check in the code.

### 7.1 `cucumber_audit` (AC9)

```
cucumber_audit [--person <id or email>] [--table plants] [--row 42]
               [--since 2026-10-01] [--until 2026-10-20] [--limit 50]

2026-10-20 14:03  #3 (app)            auth_user 12  update  is_active: true → false
                  reason: deactivate_left_company "moved to Chiang Mai"
2026-10-20 14:05  System (cucumber_flag)  waffle_flag lab_screens  update  everyone: null → true
```

Read-only. It runs as `cucumber_app`, which may SELECT `audit_log`. Times are
in Bangkok time. Newest first, at most `--limit` rows, and the total is
given. An email is looked up to its id; an anonymised account is found by
id only. People are shown by id: the Owner looks the id up on the Staff
page, so the output holds no names (AC8).

### 7.2 `cucumber_anonymise` (AC12–AC14)

```
$ manage.py cucumber_anonymise
Email: gene@example.com
Gene (#12) will become "Former staff #12". Their name and email are removed
for good; everything they saved stays under #12. This can't be undone.
Type ANONYMISE to go on: ANONYMISE
#12 is now Former staff #12.
```

Inside one `audited(SYSTEM, via="cucumber_anonymise", reason=PDPA_REQUEST)`:

1. Lock the account and the Admins (`lock_for_account_change`). Refuse the
   last active Admin (`account_last_admin`), System (`account_is_system`)
   and an account already anonymised.
2. `first_name = 'Former staff #12'`, `last_name = ''`,
   `username = email = 'former-staff-12@cucumber.invalid'` (the account must
   keep an email-shaped username: U0.5's `auth_user_username_is_email`),
   unusable password, `is_active = false`.
3. Remove its sessions, login failures and change-due row. Its role is kept,
   like any deactivated account (U0.6 Q3).

The trigger writes the audit row: `first_name`, `username`, `email`,
`password` `"changed"`, and `is_active` true → false if it was on, with the
PDPA reason. That row is AC13's record, and it holds no personal data.
Events, reviews and audit rows already point at `#12` and are not touched.
The plain log line `account anonymised account=12` stays too.

### 7.3 `cucumber_check_guards`: see §8.

## 8. The guard check (AC15, [Q3](#11-owner-questions))

### 8.1 What it checks (`core/guards.py`)

One list, `GUARDS`, with each entry naming the migration that adds it.
Entries whose migration hasn't run yet are skipped, so the same command
works before and after the U0.7 migrations.

| Kind | Checked by | Fails when |
|---|---|---|
| Trigger | `pg_trigger` | missing, `tgenabled` not `O`/`A` (disabled or replica-only), calls another function, or its timing/events (`tgtype`) or arguments (`tgargs`) differ, e.g. `plants_audit` remade with every column ignored (review M2) |
| Function | `md5(prosrc)`, `prosecdef`, `proconfig` against `GUARDS` | the body, SECURITY DEFINER or the `search_path` setting was changed |
| Grant | `EXPECTED_PRIVILEGES`: an explicit table → privileges map for `cucumber_app` (core 0003, 0005, accounts 0001's DELETE grants, U0.7's revoke), checked with `has_table_privilege` and `has_any_column_privilege` | any table's privileges differ from the map in either direction, including column grants and new tables (default privileges) |
| The app role | `pg_roles`, `pg_auth_members`, `pg_db_role_setting`, `has_database_privilege`, `has_schema_privilege` | `cucumber_app` is superuser or a member of the owner role, has `session_replication_role` set (that would switch every trigger off for it), may create TEMP tables or create in `public` (§4.1, review M1) |
| TRUNCATE | `audit_log` | a `truncate` row newer than the last `guards_accepted` row written by `cucumber_owner` |

The output is one line per failure, naming the table and what is wrong, and
the command exits 1. When nothing fails it prints `All N protections on.`
and exits 0.

A test runs the check on a freshly migrated test database: it must pass,
and every trigger the migrations made must be in `GUARDS` (so a new
protection can't be left out of the check). The function constants are
compared there too, so changing a function in a migration means updating
its constant on purpose.

### 8.2 Accepting a TRUNCATE

```
$ manage.py cucumber_check_guards --accept "staging reset with practice data"
These were truncated: events (2026-10-21 09:12, sql as cucumber_owner), ...
Accepted. The deploy will go on.
```

Writes a `guards_accepted` row (System, note required). It runs through
the migrate service, as `cucumber_owner`; only such a row counts (§5.4).
The Owner runs it after deciding the truncate was theirs. If they didn't do
it, the copy from before the truncate is the way back.

### 8.3 At deploy

- **Step 3b (new), before the copy:** `compose run --rm migrate python
  manage.py cucumber_check_guards`, as the owner, against the database as
  it is. A failure stops the deploy before anything changes: "The
  database's protections are not all on: … See the release runbook."
- **Step 5b (new), after migrating:** the same command again, now with
  the new version's guards. The compose file doesn't change (review H4).
  On failure: "The database was updated, but its protections are not all
  on: … The app was not restarted, so <previous> is still running. See the
  release runbook." The restore line follows. This only happens if a
  migration itself broke a protection, which CI catches first.
- CI runs the check after `migrate` on a fresh database, in the deploy
  rehearsal job.

What this can't see: the owner disabling a trigger, changing rows and
enabling it again between two deploys. That is the accepted owner exception
(spec, out of scope). Catching it needs an event trigger, which only a
PostgreSQL superuser can create.

## 13. How G2 proves it

- **AC16 attack matrix, generated.** For every table in `APPEND_ONLY`
  (core 0003's list) × {UPDATE, DELETE, TRUNCATE} × {`cucumber_app` raw
  SQL, owner raw SQL, ORM}: refused and the row unchanged, apart from the
  owner's TRUNCATE, which must write a `truncate` row. For every table in
  `AUDITED`: an insert and an update through raw SQL as `cucumber_app` with
  no person named → refused (`audit_actor_required`); with a person → exactly
  one audit row with the changed columns only.
- **Every service writes its row as the person.** One test per §3.3 row
  checks `actor_id` and `via` (and the reason where one is needed).
- **Owner raw SQL on audited tables (AC16, review M5):** with nobody named,
  refused just as for `cucumber_app`.
- **Test setup (review H1–H3).** An explicit helper `as_system()` (a
  context manager around `audited(SYSTEM, via="test")`), used by the
  builders that write audited tables. It is not autouse for the whole
  suite. The builders are:
  - **`rows.py`:** `make_user`, `make_vendor`, `make_plant`, `make_batch`,
    `update()`, `give_sku`
  - **`stock.py`:** `make_staff`, `restore_reference_rows`, and
    `deactivated_tech`, which now also passes a reason
  - **`test_as_app_user.py`:** `people`
  - **U0.2a schema tests:** the raw UPDATEs that retire or void a plant now
    set a reason

  Because `audited()` puts the person back (§3.1), a service called after a
  builder still has nobody named. A test pins that: builder, then a write
  with no `audited()`, gives `audit_actor_required`.

  `restore_system_account()` sits next to `restore_reference_rows()` for
  `transaction=True` tests, and the restore also brings back the new
  reason lists. Tests count audit rows **written since the test started**
  (by id), because flush `truncate` rows build up across runs with
  `--reuse-db`. The "fresh database passes the check" test accepts its own
  flush rows first.

  Expected size: about 10 builder edits and 15–25 existing tests touched.
  That fits in M.
- **Reasons (AC11).** Each off switch in §4.2: no reason → `reason_required`,
  nothing saved; a reason from the wrong list → `reason_wrong_list`; the same
  through raw SQL.
- **AC8 scan.** After the suite, every audit row's JSON is searched for
  every test account's email and name, `pbkdf2_`/`argon2`, and session keys;
  none may appear.
- **AC17.** §9's two lists against `pg_tables`.
- **Undo (AC3).** The U0.6 tests stay as they are, plus a raw-SQL UPDATE of
  an operation's `recorded_at` to fake an older save, which is refused.
- **Anonymise (AC12–AC14)**, **`cucumber_audit`** (filters, Bangkok
  times, no names), **`cucumber_check_guards`** (each kind in §8.1 broken
  one at a time on a throwaway connection, then put back), **AC10** (each
  of the six account changes and a flag switch writes an audit row and
  keeps its log line).
- **Migrations:** each pre-check and each guarded undo.
- **E2E (phone):** deactivate with no reason, then with one.
