## Goal

Fix the database shape for plants, batches, events, reference lists, users and
audit, so every Phase 1 unit builds on the same tables. Every SOP §5 rule is
enforced by a database constraint, by a service guard, or has a written reason
why it can't be.

## User stories

| # | As a… | I want… | So that… |
|---|---|---|---|
| S1 | Owner | every SOP rule to have a named place where it is enforced | bad data can't get in, even through the Django admin or raw SQL |
| S2 | Owner | events that can never be edited or deleted | the history is trustworthy for review and metrics |
| S3 | Developer (Phase 1) | one agreed schema with field names and types | U1.x units don't redesign tables one by one |
| S4 | Owner | counts and stages that always match the event history | nobody can type a number that disagrees with what happened |
| S5 | Supervisor / Admin | reviews recorded without changing the event | review doesn't break append-only (SOP §5 rule 8 vs rule 10) |

## Acceptance criteria

One per behaviour. Each one becomes at least one schema test at G2.

**Rule-to-enforcement**
- **AC1** *Given* the design note, *when* the Owner reads the rule table, *then*
  every SOP §5 rule (1–13) has a row naming a DB constraint, a service guard, or
  a written reason.

**Plants (SOP §5 rules 1, 3, 4, 9, 12, 13)**
- **AC2** *Given* a plant with status `Portfolio`, *when* it is saved without an
  SKU, *then* the database rejects it.
- **AC3** *Given* plant A has SKU `PHL001`, *when* plant B is saved with
  `PHL001`, *then* the database rejects it.
- **AC4** *Given* a plant with genus code `PHL`, *when* it is saved with SKU
  `HYA001`, *then* the database rejects it.
- **AC4a** *Given* a plant with SKU `PHL003`, *when* its SKU is cleared or
  changed without a genus change, *then* the database rejects it (Q1).
- **AC4b** *Given* `PHL005` is reclassified to genus `ANT`, *when* the Admin
  saves it, *then* it gets a new `ANT` SKU, `PHL005` is listed as its former
  SKU, a search for `PHL005` finds the plant, and no other plant can ever get
  `PHL005` (Q1).
- **AC4c** *Given* plant `PHL` `Pink Princess` exists with status `Retired`,
  *when* a `PHL` plant named `pink princess` or `'Pink  Princess'` is
  saved, *then* the database rejects it (Q6).
- **AC4d** *Given* that plant is `Voided` instead, *when* a new `PHL`
  `Pink Princess` is saved, *then* it is accepted (Q6).
- **AC4e** *Given* a plant named `Philodendron ???` or a blank name, *when*
  it is saved, *then* the database rejects it (Q6).
- **AC5** *Given* a plant with source `Purchase` and no vendor or `zoho_ref`,
  *when* it is registered, *then* it is accepted and appears on the
  "Zoho link missing" list (Q2).
- **AC5a** *Given* a purchased plant missing its vendor or `zoho_ref`, *when*
  it is set to `Portfolio`, *then* the database rejects it (Q2).
- **AC5b** *Given* a plant with source `Gift`, `Propagated` or `Unknown`, *when*
  it is saved with a vendor or `zoho_ref`, *then* the database rejects it.
- **AC6** *Given* any plant row, *when* a DELETE is run as the app's DB user,
  *then* it fails.

**Batches (rules 5, 6, 7, 9)**
- **AC7** *Given* a batch with origin `Subculture`, `Split` or `Quarantine`, *when* it is
  saved without a parent batch, *then* the database rejects it.
- **AC8** *Given* a parent batch for plant A, *when* a child batch for plant B
  points to it, *then* the database rejects it.
- **AC9** *Given* a batch at location `Lab`, *when* it is saved with no stage,
  *then* the database rejects it. *Given* a batch at `Nursery`, *then* a blank
  stage is accepted.
- **AC10** *Given* a batch with live count 3, *when* its live count is set to
  −1, *then* the database rejects it.
- **AC11** *Given* a batch with live count > 0, *when* its status is set to
  `Closed` or `Voided`, *then* the database rejects it.
- **AC12** *Given* plant A already has an open batch at `Nursery`, *when* a
  second open batch for plant A at `Nursery` is created, *then* it is
  accepted (Q7: no standing-batch rule).
- **AC12a** *Given* batch B010 with 100 units, *when* 40 are split off with a
  note, *then* a child batch with parent B010, the same location and stage,
  holds 40, B010 holds 60, and both events share an `operation_id` (Q7).
- **AC12b** *Given* a batch at 0, *when* `Close` is logged, *then* its status
  is `Closed`; *when* that Close is voided, *then* it is `Open` again and
  `closed_at` is cleared (Q7).
- **AC12c** *Given* a closed batch, *when* any event other than a Void of its
  Close is logged, *then* the service rejects it (Q7).

**Events (rules 7, 8)**
- **AC13** *Given* any event, *when* an UPDATE or DELETE is run, as the app's DB
  user or as the table owner, *then* it fails.
- **AC14** *Given* a `Void` or `Correction` event, *when* it is saved without a
  reason, *then* the database rejects it.
- **AC15** *Given* event E is already voided, *when* a second `Void` for E is
  saved, *then* the database rejects it.
- **AC16** *Given* an event with negative `qty_in` or `qty_out`, *then* the
  database rejects it.
- **AC16a** *Given* a `loss` event, *when* it is saved without a reason or with
  `qty_out` = 0, *then* the database rejects it (Q4).
- **AC16b** *Given* a normal event dated more than 7 days before it is saved,
  or more than 5 minutes in the future, *then* the database rejects it (Q5).
- **AC16c** *Given* a Correction that restates an event's date as 3 weeks ago,
  *then* the database accepts it (Q5).
- **AC16d** *Given* a batch at 48 on Saturday and +10 on Sunday, *when* a count
  of 50 dated Saturday is entered on Monday, *then* the count's difference is
  +2 and the batch total is 60 (Q5, service).
- **AC16g** *Given* 100 units Monday and a count of 98 dated Wednesday, *when* a
  loss of 5 dated Tuesday is entered on Thursday, *then* the batch total stays
  98, the count's difference shows +3, and the loss is flagged "dated before a
  count" for review (the count wins, architect review H2).
- **AC16e** *Given* a Subculture that made child batches B011–B013, *when* any
  of its events is voided, *then* every event of the operation is voided in
  one transaction and B011–B013 become `Voided`; *given* B012 already has a
  later Count, *then* the void is refused and names that event (Q8).
- **AC16f** *Given* a Split that moved 40 units from B010 to B015, *when* it is
  corrected to 30, *then* both events get a Correction in one operation:
  B010 +10, B015 −10 (Q8).
- **AC17** *Given* an event whose quantity would take the batch below zero,
  *when* two users save at the same moment, *then* exactly one succeeds
  (row lock + live count check).

**Reviews (rule 10)**
- **AC18** *Given* event E has a review, *when* a second review for E is saved,
  *then* the database rejects it.
- **AC19** *Given* a review row, *when* an UPDATE or DELETE is run, *then* it fails.
- **AC19a** *Given* the Admin logs an event, *when* it is saved, *then* a review
  row by the Admin is written in the same transaction and the event never
  appears in the queue (Q3).
- **AC19b** *Given* an unreviewed event is voided, *then* it leaves the queue and
  the Void appears in the Admin's queue (Q3).
- **AC19c** *Given* a Supervisor adds a Correction to a Tech event, *then* the
  original gets a review row in the same transaction and the Correction
  appears in the Admin's queue (Q3).

**Reference lists**
- **AC20** *Given* stage `P2` is used by a batch, *when* someone tries to rename
  or delete code `P2`, *then* it fails; deactivating it is allowed.
- **AC21** *Given* the stage list, *then* sort orders are unique and `A1` sits
  between `P2` and `P4`.

## Out of scope

- Services, screens and permissions (U0.6, U0.7, U1.x). This unit makes the
  tables and the database-level rules; services that call them come later.
- ID formatting and concurrency-safe sequences in detail (U0.8). This unit only
  reserves the columns.
- The general audit trail mechanism (U0.7). This unit fixes its table shape.
- Prepared media lots (`media_lot`, U3.5), protocols (U4.x), settings such as the
  global `min_saleable_qty` (U5.2). Columns are added when those units arrive.
- Data migration from V.2 (U1.10).

## Open questions for the Owner

These came out of turning the SOP into tables. Each one has a recommendation;
the design note assumes the recommendation until you say otherwise.

| # | Question | Recommendation |
|---|---|---|
| Q1 | When a `Portfolio` plant is demoted to `Collection`, does it keep its SKU? (SOP §5 rule 1 says SKU is set "only when Portfolio".) | ✅ **Answered 2026-10-10 (Jade): static SKU.** Assigned on first promotion; never changed, cleared or reused; re-promotion reuses it. Portfolio **requires** an SKU; other statuses keep theirs. **Only exception, genus reclassification (option B):** the Admin changes the genus, the plant gets a new SKU for the new genus, and the old SKU becomes a *former SKU*. It stays searchable and is never reused. |
| Q2 | SOP-1 has Tech record the Zoho expense reference at registration, but §7 says only the Admin can see Zoho references, and the expense may not be in Zoho yet. | ✅ **Answered 2026-10-10 (Jade): option C.** Vendor and `zoho_ref` can both be completed later. At registration Tech picks the vendor if listed, otherwise types the seller in the source note. Purchased plants missing either show on a **"Zoho link missing"** list for the Admin's weekly review. A purchased plant **can't be promoted to Portfolio** until both are set (DB). Tech can see vendor names; only the Admin sees `zoho_ref`. Multi-plant expenses: convention left to U1.9. |
| Q3 | Reviews: SOP §4 puts `reviewed_by` / `reviewed_at` on the event, but events can't be updated (rule 8). | ✅ **Answered 2026-10-10 (Jade): separate `event_reviews` table** (option B), insert-only, one review per event; events stay strictly append-only. **Admin's own events are auto-reviewed** at save (option i). **Voided events leave the queue**; reviewing the Void covers both. A reviewer's Correction or Void marks the original reviewed in the same save. |
| Q4 | `qty_contaminated` duplicates the `Contamination` and `Quarantine` events (SOP-4 logs contaminated units as their own event). | ✅ **Answered 2026-10-10 (Jade): drop the column** (option A). Contaminated units are counted once, as `Contamination` / `Quarantine` events. Rules: one form, separate operations; credit goes to the batch's maker (its intake), not the finder; `Contamination` on a batch still under quarantine isn't counted again; a released jar still counts. **Plus a new `Loss` action** with a required reason, for deaths that aren't contamination. |
| Q5 | Can `occurred_at` be set in the past (logging yesterday's work today)? Principle 7 says the date is filled automatically. | ✅ **Answered 2026-10-10 (Jade):** defaults to now; staff can pick a date **up to 7 days back**, never in the future, the same for every role. Entries more than 24 h late are flagged in review. Older work is logged today with the real date in the note, and a **reviewer fixes the date with a Correction** (not their own entry); Corrections aren't bound by the 7-day window. `recorded_at` always holds the real save time; Undo counts from it. A backdated `Count` is compared with the total as of its own date. |
| Q6 | Should the app block a second plant with the same genus + name? | ✅ **Answered 2026-10-10 (Jade): yes, blocked by every plant except a `Voided` one**, Retired included. Buying a retired cultivar again goes onto its old record (same PLT, same SKU, full history); the Admin brings it back. The check **ignores case, extra spaces and quote marks**; the name is stored as typed. **No more `???` names:** unidentified plants also get a human-readable name. The full naming standard (species vs cultivar, in-house names, nicknames, Thai names, format checks) is **parked as D-19**. |
| Q7 | Can a `Closed` batch be reopened? | ✅ **Answered 2026-10-10 (Jade): closing is a `Close` event; a wrong close is fixed by voiding it** (Undo within 10 minutes, or a reviewer later), which reopens the batch. No separate Reopen; new stock never goes into a closed batch. A batch closes only at 0; when an event brings it to 0 the app asks "Close this batch?". **The one-standing-batch-per-plant rule is removed** (SOP §4): a batch is any group of plants tracked together, any number per plant per location. **New `Split` action** moves units into a child batch with a note (e.g. a pre-order, or a different protocol). Transfers go into a new batch by default, or an existing open batch of the same plant. Pre-orders and reservations parked as **D-20**. |
| Q8 | Voiding an event that created other events (a `Subculture` that made child batches, a `Split`, a `Transfer`, a `Quarantine`). | ✅ **Answered 2026-10-11 (Jade): all events from one action share an `operation_id` and are voided together** (one Void, one review item); batches the action created become `Voided`. **Refused if any batch it created has later events**: the app names them (e.g. "B012 has 1 later event: Count, 14 Oct") so they are voided first; no cascade. If the action really happened but a number was wrong, use a Correction instead. **Correcting a Split, Transfer or Quarantine quantity changes both sides together**, so units never appear or disappear. |
